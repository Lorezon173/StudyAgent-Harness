## 4. 关键决策与边界

- 已确认决策：
  - 新栈协作主体是 `app/`，核心为 5 Agent 的事件驱动协作环，而非 `app_old/` 的旧 LangGraph 实现。
  - Agent 之间不得直接调用；协作依赖 EventBus、事件所有权白名单和 `parent_id` 因果链。
  - Critic 是语义层：评估用户文本掌握度、混淆、矛盾、低自信，并仅在 `purpose=teaching` 时评 RAG 质量。
  - Curator 是结构层：消费 `MasteryAssessed`，更新掌握图谱与画像，并依据 PREREQ 关系产出前置薄弱信号；它不做用户文本语义判断。
  - RAG 的职责链不可混淆：Retriever 做机械检索状态；Critic 做证据语义质量；Orchestrator 决定后续路由。
  - 本窗口对学习文档的更新是项目内知识沉淀，不是功能/架构/API 变更，因此 README 不需要因这次更新而改动。
- 明确不要做的事：
  - 不要将 `app/specs/event_map.yaml` 当成运行时订阅来源；实际订阅来自 Agent 的 `subscriptions` 与装配线。
  - 不要把 Critic 扩展为读图谱/判前置，或把 Curator 扩展为判文本语义，除非先完成架构方案、用户确认和契约调整。
  - 不要在共享工作树使用 `git add -A`、`git add .`、`git commit --amend`，也不要碰无关未提交文件。
  - 不要把 RAG 工作文档区的 `plans/` 当成任何窗口可自由修改的文件；该区有主控单写者约束。
- 仍未定论、不能当作事实的点：
  - 是否需要把协作评估从测试驱动的离线 benches 接到 API、CLI 或在线监控，尚未提出需求或经过设计决策。
  - 协作级冲突消解指标是否应从当前代理指标改成精确的“Critic/Curator 观察冲突 + 屏障消解”指标，尚未进入批准的实现计划。

## 8. 风险与坑点

- **共享工作树风险**：当前 `git status` 中有大量 RAG、API、迁移、测试与文档改动；不要重置、暂存、批量 add、批量格式化或提交它们。
- **文档路径迁移风险**：RAG 工作文档已从旧 `docs/designs/` / `docs/rag-foundation-status/` 路径迁移到 `docs/rag-work/`；新窗口引用时应以新路径为准，并通过 git 状态判断迁移尚未提交。
- **旧栈混淆风险**：分析当前协作实现时应使用 `app/agents/`；不要把 `app_old/agent/` 的 LangGraph 旧实现当成当前主链路。
- **事件映射混淆风险**：`app/specs/event_map.yaml` 是规范映射，不是运行时订阅真源。
- **RAG 触发误解**：Retriever 不会因每个用户回答自动运行；只有 Orchestrator/Conductor 发出 target 为 retriever 的 `ActionRequested` 才会检索。
- **持久化表述风险**：本窗口只核实了协作环内 Curator 对内存 `MasteryGraph` 的更新及 API 层存在持久化路径；若要改动或断言数据库事务细节，必须先回读 `app/api/_persist.py`、对应 Store 和调用路径。
- **评估成熟度风险**：协作评估代码存在，但 README 与实现都表明 benches 尚未接入在线 API/CLI；不得表述为“已有在线实时协作监控”。
