# RAG MVP 修订执行方案审阅

日期：2026-10-15。对象：[修订执行方案](2026-10-15-rag-mvp-execution-plan.md)。本轮对照现有代码、DEC、在线 spec 和上一轮核验；未修改生产代码、原方案或冻结契约，未执行真实 PG、embedding 或正式书籍 baseline。

## 审阅结论

S0→S6 的主顺序可以保留，写入/评测可信性先于正式摄入的安排合理；旧问题已有明确承接。建议补齐下面三项 P1，再将 S0 对应契约视为可冻结。两项 P2 应纳入相关执行包细节。这里的优先级按常规 review 使用：P1 为应在相关实施前解决的问题，P2 为应补充的边界；不替换原方案 R01～R22 或全局 BLK 编号。

## 发现

### RV-01 / P1：正式 baseline 缺少“20 题全部有效执行”的放行不变量

方案位置：S4 的 G4（第 128 行）、E2 的资产约束（第 177 行）、G6（第 151 行）。

G4 只要求执行情况真实、报告可审计；E2 依赖“现有资产 validator”。但 `rag_d.py:114-116` 会跳过非 `verified_v1` 题，`:216-218` 运行时再次跳过，`:226` 不检查结果数量就可标 completed。因此，“20 条题目记录”不保证“20 道黄金题都经过有效检索”。即使补好 R01 的检索失败状态传播，这条零调用成功路径仍然存在；诚实记录一次 inconclusive 也不能等同于取得完整 baseline。

本轮受控复现：向真实 validator/runner 提供 20 条 draft 题，替换文件读取、后端识别与评测 agent，结果为 `status=completed`、`evaluate_calls=0`、`result_count=0`。没有连接真实数据库。

建议：正式题集必须恰有 20 个非空且唯一的题 ID，全部为已验证状态且通过 gold 校验；运行完成必须满足有效题数=20、失败数=0、未跑数=0。只有这时可用 completed 或 completed_judge_degraded 放行 G4；基础设施失败报告保留为尝试记录，不放行 G4/G6。新增“全 draft、部分未验证、重复题 ID、首题失败”回归。低召回仍可如实完成，不增加质量分数阈值。

### RV-02 / P1：证明绑定了数据库和文本策略，却未绑定 embedding 身份

方案位置：S2-02（第 100 行）、E3 字段表（第 187～197 行）、S6-01（第 146 行）。

当前字段只检查 embedding 维度及目标索引，没有记录摄入时实际使用的模型/部署身份。`embedding.py:28` 从实例参数或当前 settings 选择 model，`:85-88` 按该 model 请求向量，`PgVectorProvider` 可在另一个进程重新构造服务。于是摄入后若切换到同维度的另一模型，现有计划列明的目标、ID、计数、维度核验仍可能全部通过，却使用不同向量空间查询旧索引。这里是配置变化触发的设计缺口，不是已发生模型切换的事实。

建议：attestation、baseline 报告及在线验收共同绑定无密钥的 embedding 配置指纹，至少包含实际模型/部署标识、维度、影响向量生成的参数；存在可取得的版本标识时也记录。S4/S6 对照实际查询配置，发生不匹配就阻断旧索引准入；若服务端别名不能锁定版本，明确记录该限制。新增“同维度但不同模型配置”拒绝用例。不要求重构全部 provider。

### RV-03 / P1：正式迁移的测试目标传递路径尚未闭合

方案位置：S2-01/02（第 99～100 行）、E4（第 203 行）。

E4 说 fixture 从配置的独立测试目标执行 Alembic，但 `alembic/env.py:20-22` 会从 `settings.database_url` 重新生成 URL，并覆盖 `config` 的 `sqlalchemy.url`。当前真实 PG fixture 使用 `TEST_PG_URL`；如果实施时只把该值传给 Alembic Config，迁移仍可能指向 settings 对应的另一库，违背“独立测试目标、不清空已有业务库”的边界。事后输出目标证据不足以防止迁移先执行到错误资源。

建议：在 S0/E4 明确唯一的迁移目标注入方式，确保 env.py 实际消费 fixture 的目标；在任何 DDL/清理前核对实际连接的数据库、schema 和独立测试资源标识，并确认测试目标与基线/业务目标不同。新增 settings 指向 A、fixture 指向 B 的对抗用例：只允许 B 变化，A 不发生迁移。不在本轮直接修改迁移入口。

### RV-04 / P2：已提交但证明未落盘的恢复只有原则，没有可执行契约

方案位置：E3（第 183、199 行）、S3-05（第 114 行）。

禁止自动重复摄入是正确的，但“由明确恢复步骤核对现有产物”尚未给出所需状态来源。当前 `IngestResult` 只暴露 doc ID 和计数，`knowledge_ingestion.py:81` 发起写入前也没有输出计划清单的接口；provider 在提交后才返回，而稳定 chunk ID 不含 run ID、数据库又允许 append-only 重复行。若进程在提交后、任何运行清单写出前退出，恢复方未必持有本轮期望 identities，也不能只靠 ID 集合区分已有行与本次写入。

建议：为单书隔离库选择明确且最小的恢复方案，例如写库前持久化无正文运行意图与计划清单，要求首次目标为空并记录前态；恢复命令只读核对行的完整数量、身份及 scope/owner，吻合后补写证明，不再次 index。无法唯一核实时保持阻断，给出人工处置路径。明确计划清单由产品 service 如何提供，避免 runner 复制另一套提取/切块实现。补“提交成功后、证明落盘前退出”的验收。

### RV-05 / P2：judge 降级没有覆盖非有限值与缺失分数

方案位置：S4-04（第 125 行）、E2 状态规则（第 175 行）。

`retriever.py:319` 将 RAGAS 调用设为不抛单项异常；`:323-335` 对分数直接 float/round，缺字段部分回填 0，随后无条件 `degraded=False`。因此只规划“judge 不可用/抛异常”不能完整保证 enrichment 状态可信。

本轮用受控 judge 结果向真实 evaluate 注入 faithfulness=NaN，另两项正常；输出仍为 `degraded=False` 且 faithfulness 为 NaN。没有调用真实 judge，也没有验证某个实际服务会产生 NaN。

建议：按指标验证存在性、数值类型、有限性和合法范围，缺失或无效分数记录为不可用并标明 judge 降级，不填成有效 0 分；机械指标保持有效。序列化时禁止 NaN/Infinity，并覆盖“部分分数缺失、NaN、Infinity”回归。不新增整体完成状态也能实现。
