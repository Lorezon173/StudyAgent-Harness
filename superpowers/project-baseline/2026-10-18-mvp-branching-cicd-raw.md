## 2. 将需求收敛成五项交付

1. **一页项目地图**：明确当前版本、下一版本、当前任务、阻塞和放行条件；日常不必遍读所有 spec。
2. **一条普通教学 MVP 闭环**：用户能登录、发起教学、保存消息、重新打开自己的会话；教学连续性的具体承诺写入验收。
3. **一个可重建的共同基线**：固定提交、依赖锁、配置清单、数据库迁移和可追溯镜像；由新环境复现，不能仅在现有开发目录工作。
4. **一套隔离开发与串行集成方式**：短期功能分支 + 独立工作目录；每个 PR 有范围、验收与回退说明。
5. **一条受检查约束的发布路径**：PR 回归 → main 对应提交检查 → 镜像 → 本地/服务器测试环境 → 正式环境；能够查明当前运行版本并恢复到上一兼容版本。

判断完成与否看这些结果，不以规划文档数量或已开分支数量判断。

## 4. 版本范围：先形成普通教学 MVP

### 4.1 工程起点与产品 MVP 分开命名

**工程起点**：用来开始修复和开发的已记录提交与可复现环境。它可能仍有缺口，标为候选或工程基底。

**产品 MVP**：目标用户能走完下面的验收流程，且构建、数据库迁移、回归和运行证据齐全。达到后才打产品版本标签，例如 `v0.1.0`（实际标签名先检查是否已使用）。

另有 RAG 的“20 题检索基线”，它是评测结果，不是 Git 起点，也不是普通教学 MVP 的前置。

### 4.2 首版包含与后置内容

首版包含：现有登录/注册流程、真实 LLM 普通教学、会话与消息持久化、历史列表和重新打开、用户隔离、可理解的失败提示、Docker 启动、回归与发布恢复能力。现有五 Agent 和掌握度存储先按需复用，不开展新的架构重构。

后置：书籍上传/正式摄入、基于书籍证据回答、完整 RAG 20 题验收、LightRAG、BM25、复杂 PDF 版面、时序复习、完整 DeepEval 评估建设。后置表示版本排期建议，不删除成果、不改变既有验收记录。

首版继续使用 PostgreSQL + pgvector 基础设施，是减少现有在线契约变动的建议。它不要求先完成真实书籍导入或 embedding 评测。需要核查无材料时是否有路由触发检索，并明确定义普通教学行为；不能承诺当前代码天然不会请求 embedding。若希望普通教学完全不装配 RAG，须另做模式边界设计并确认，不能悄悄放宽已有 RAG fail-fast 契约。

### 4.3 建议验收脚本

1. 在新工作目录按锁文件安装、构建镜像，用明确配置启动专用数据库与应用。
2. 用户 A 登录，创建会话，输入学习问题，真实模型返回教学回复。
3. 记录回复的保存状态；两条消息与会话确实提交成功。持久化失败时页面明确告知，不能把“回复生成”显示成“已保存”。
4. 刷新页面或重新登录，可看到会话列表，打开后消息顺序、角色与内容一致；应用容器重启后仍可读取。
5. 在同一会话继续教学，约定的前文信息仍生效。建议首版实现有限窗口的连续上下文；若只承诺历史回看，必须明确写成范围缩减，不能称为上下文恢复已完成。
6. 用户 B 无法读取或写入 A 的会话；过期/无效登录、模型超时、数据库写入失败都有明确结果。
7. CI 覆盖以上可确定行为；测试环境再验证真实 LLM。记录提交、镜像摘要、迁移版本、检查结果与已知限制。

## 5. 阶段职责，以及你需要理解到哪一层

| 阶段 | 负责的工作 | 主要产物 / 放行条件 | 你需要掌握 |
|---|---|---|---|
| 需求与版本取舍 | 决定本版用户能做什么，哪些后置 | 版本目标、范围、验收场景 | 必须理解使用结果与取舍 |
| 设计 / spec | 定义模块边界、接口、状态与失败语义 | 可检查且无关键歧义的契约 | 重点理解输入输出、数据归属、失败后果 |
| 执行计划 | 把设计拆成可独立交付的工作包 | 每包依赖、改动范围、验证方式 | 理解顺序、阻塞和完成判据 |
| 编码与 PR | 在隔离目录完成一包，控制影响 | 可审阅差异、必要测试与说明 | 看行为变化、风险与证据；按需读函数 |
| 集成验收 | 验证新旧功能及真实依赖一起工作 | 对应提交的回归、PG/浏览器/模型证据 | 理解测了什么、没测什么、哪些失败阻断 |
| 发布与运行 | 把已验证产物部署并观察 | 版本记录、环境冒烟、恢复路径 | 知道当前版本、健康状态及如何恢复 |

日常只看“当前里程碑 → 当前一包 → 依赖/阻塞 → 验收结果”。不需要把所有函数、字段、历史审阅都记住；只有契约争议、失败或重要取舍时才下钻。

旧编号的翻译：**S = 产品能力阶段；T = 可派发工作包；G = 用证据判断能否放行的关卡**。三者是同一工作从不同角度的描述，不是三份独立待办。

## 6. 三种组织方案与建议

| 方案 | 收益 | 代价 / 适用条件 |
|---|---|---|
| **推荐：保留历史，收敛 MVP，main + 短分支** | 复用现有能力，减少长期合并面，按小包验证 | 先处理未提交成果，建立可复现基底 |
| 长期 develop + 多条长期功能分支 + release 分支 | 可支持多版本发布列车 | 当前会增加集成层、状态与合并成本；有明确多版本维护需求时再考虑 |
| 新仓库 / 大幅重写最小系统 | 目录表面简单 | 易丢掉鉴权、事务和测试成果，也要重做迁移与验收；当前证据不足以支持重写 |

建议保留单仓库与现有四层架构，通过版本范围缩小交付面。物理删除所有暂时不用的模块不是建立 MVP 的必要条件。

## 7. 如何安全整理当前工作，再建立分支

以下是待确认的执行顺序，本轮没有实际执行 Git 变更。

1. **短时停止共享目录写入并盘点**：分别记录 HEAD、暂存、未暂存、未跟踪内容和各成果归属。备份应覆盖未提交文件；另存必要的本地忽略资产，避免遗漏。密钥与私有正文不进入 Git。
2. **保存当前整合成果**：在归档分支/备份中保存工作区快照，或将可分离的已验收成果按依赖提交。T02/T03/T04 若已交织，先保留可恢复整批快照，再准备逻辑 PR，不按文件名强行拆分。
3. **选择工程候选**：从已记录的 main 提交在干净工作目录构建和检查。`6324b94` 只是当前候选，不是已经验证的干净基线。失败就记录并修最小阻塞；只有候选缺陷无法小修时，才评估更早提交。
4. **逐包补齐 MVP**：基底配置、会话恢复、必要连续上下文、CI 与部署依次经 PR 集成。归档中的 RAG 改动按真实依赖选择性集成；仅当 MVP 直接依赖时才纳入，避免把整批 RAG 都变成首版前置。
5. **验收并固定版本**：新目录/环境复现成功后记录提交、锁文件、镜像、迁移与证据，发布首版标签。后续普通功能和 RAG 功能均从最新已集成 main 开分支。

分支负责隔离提交历史；**独立 worktree/工作目录负责隔离未提交文件**。多个 Agent 在同一个目录里切换分支，仍会混写工作区和暂存区。

建议同时最多两个编码工作包，集成与部署串行。同改 `assembly.py`、数据库迁移、共同类型等共享边界的任务，先固定接口，再排合并顺序。不要把每份 spec 自动变成一条长期分支。

## 9. CI：如何检查旧功能是否受到影响

建议检查集按成本与依赖分层，而非只跑本次改动文件的测试：

| 检查层 | 建议内容 | 触发与阻断 |
|---|---|---|
| 快速确定性检查 | 锁文件与工具版本、后端 lint/现有非集成回归、前端 `npm ci` 后 test/build | 每个 PR 必跑；失败不得合并 |
| PG 集成 | CI 专用 PG + 正式迁移；鉴权、会话归属、消息原子写入、失败回滚；注入确定性 LLM | 关键 PR / 合并候选；必需环境缺失或关键测试 skip 不算通过 |
| 浏览器关键路径 | 登录 → 新会话 → 回复 → 历史重新打开；前端保存失败状态 | 关键路径变更和发布候选；使用专用环境与可控模型替身 |
| 镜像验证 | 构建真实 Dockerfile；在隔离配置下启动，验证页面/API与数据库就绪 | PR 构建；main 相同提交验证成功后才推送发布产物 |
| 真实服务冒烟 | 真实 PG 与真实 LLM 的少量固定场景、时延/调用成本记录 | 受信测试环境/发布候选；不可用标失败或未确认 |
| AI 质量评测 | 固定教学场景人工复核；后续接入 RAGAS/DeepEval 与检索指标 | 单列质量证据，按版本约定门槛；不能用模型波动替代软件回归判断 |

确定性 LLM 替身只用于测试。真实上线不能静默使用 fake。PR 默认不依赖付费模型、线上凭据或真实书籍；外部分支 PR 不获得部署密钥。

目前集成 fixture 的目标守卫仍有后续计划，不能直接把会创建/清理表的现有测试接上业务库。必须先确认专用测试目标、连接来源与变更前保护，迁移/清理限定在 CI 资源。可以复用 T05 的已确认设计，但首版接入的子集不等于整个 RAG T05/T07 已验收。

依赖安装建议使用锁文件约束，明确 Python/Node 与 lint 工具版本；根据测试实际导入确定 dev/eval 等 extras。先修复真实缺口，不通过大面积忽略报错或增加 skip 制造绿灯。

CI 只能检测已覆盖的回归，不能证明所有旧功能绝对不受影响。每个新功能必须补与风险匹配的行为验证；现有回归保留并在集成后运行。

## 10. CD：先本机 Docker，再单台服务器

建议链路：

```mermaid
flowchart LR
    A[功能分支与独立目录] --> B[PR检查与审阅]
    B --> C[main对应提交检查]
    C --> D[构建并推送版本化镜像]
    D --> E[服务器测试环境]
    E --> F[真实服务冒烟与用户验收]
    F --> G[晋级同一镜像到正式环境]
    G --> H[部署记录与运行检查]
```

1. **本机阶段**：用 Docker 验证新环境启动、配置、迁移、会话恢复；先完成 B1～B4。可使用本机构建镜像；服务器发布候选要有对应的不可变摘要与检查记录。
2. **服务器测试阶段**：单台服务器运行隔离的测试实例、数据库与存储卷，端口/域名、配置和凭据区分生产。是否同机双实例取决于服务器资源；资源不足时再选本地测试加单实例部署，不能共享测试与生产数据。
3. **正式发布阶段**：测试通过后晋级同一镜像 digest，由显式发布动作触发。先采用持续交付：自动检查与部署准备，用户决定何时正式发布。稳定后再讨论全自动生产发布。
4. **发布门禁**：构建/推送/部署依赖同一 main 提交检查成功；tag 也必须核对该提交的成功证据，不能用任意 tag 绕过。不要让独立 Release 流水线越过失败 CI。
5. **恢复与记录**：记录 release ID、Git SHA、镜像 digest、迁移 revision、部署时间、冒烟结果、上一兼容版本。不要将可变 `latest` 当唯一恢复凭据。
6. **数据库发布**：本地可复用现有容器启动迁移方式；服务器迁移建议成为明确的串行步骤。恢复旧镜像的前提是 schema 仍兼容；破坏性迁移需要备份与恢复验证，不能声称回退镜像就能恢复数据。
7. **并发控制**：同一环境只允许一个部署过程；main 可继续集成，生产只晋级已验收版本。单服务器先接受可控重启窗口，不承诺零停机或百分比灰度；需要这些能力时再引入代理切流/双实例等设计。

GitHub 可用分支保护/规则集要求 PR 检查，用 Environments 表示 staging/production 并限制密钥和发布来源，用 concurrency 防止同环境部署争抢。具体可用能力取决于仓库可见性和账号计划，本轮未核实；若无环境审批能力，可先用受限的手动发布工作流实现明确晋级。

依据：[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow)、[分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[部署与并发控制](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments)。这是结合项目情况提出的流程建议，不是 GitHub 强制要求采用该发布顺序。

## 11. RAG 后续如何接回来

普通教学 MVP 发布后，先把归档成果与新 main 对齐，确认首批 T02/T03/T04 的集成回归，再恢复领域排期。

| RAG 能力阶段 | 对应任务与放行关系 | 应向用户解释的结果 |
|---|---|---|
| S0 契约与准备 | T00、T01；前者已冻结，后者资源仍 blocked | 接口说清、资源有据可查 |
| S1 可信性 | T02/T03/T04/T09/T10 → G1 | 写入与报告真实，不产生假成功 |
| S2 真实环境 | T05 + T01 + G1 → T07 → G2 | 真实 PG/迁移/权限与向量配置可验证 |
| S3 正式摄入 | T08 + G2 → T11 → G3 | 指定书真实进入索引，并可核对证明 |
| S4 检索评测 | T09 + G3 → T12 → G4 | 20 题全部有效执行，报告可追溯 |
| S5 在线证据 | T06/T10/T04 + G3 → T13 → G5 | 当前轮授权证据真正进入 Tutor |
| S6 联合验收 | G4 + G5 → T14 → G6 | RAG 产品闭环与回归一起验收 |

T06 可在契约固定后提前做离线实现，不强行改成整条串行；真实执行仍遵循既有 DAG 和目标资源独占。T05/T08/T09 先关闭已有计划审阅问题，再进入编码。后续按可独立验收的小包建分支。

G4 当前强调执行完整与结果有效，并未定义新的最低召回率。本建议不添加该门槛；产品发布所需质量标准应另行确认。普通教学 MVP 的版本与 RAG G6 也不能混为同一次验收。

## 12. 文档与日常管理的最小调整

- README 只承担“这是什么、怎么启动、当前版本、到哪里看”，不继续累积每一轮审阅摘要。
- 根 TODO 后续收敛为项目级看板：**当前：普通教学 MVP；下一版：书籍 RAG；以后：检索增强/复习/复杂 PDF**。每一项链接领域清单，不复制 T 包状态。
- RAG 主清单保留本领域当前状态；spec 负责契约；执行计划负责步骤；evidence 负责证明；handoff 负责历史交接。历史交接不反向覆盖当前事实。
