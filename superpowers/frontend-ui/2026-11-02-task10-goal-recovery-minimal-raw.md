## 第一层：模块总览

### 1. 目标、生产入口与完成条件

目标是完成原有会话恢复、真实教学发送和持久化验收。眼前只处理有证据的核心阻断：请求已经 inconsistent 后，用户在 `/chat/:sessionId` 的“重新查询”入口连续启动两次原请求 GET 与消息核验；较新核验确认可信内容冲突后，较旧核验的正确页面不得解除冲突、解锁发送或清理副本。较新仅发生 503 等无结论失败时，仍须允许身份有效的较旧可信成功恢复。

本次完成条件同时包括：该实际 UI 交错有准确复现或不可达证据；若确认缺陷，最小修复及对照通过；Task10 完整范围 OCR 审阅有逐文件覆盖；真实浏览器通过正常入口完成会话恢复、切换、真实模型问答、保存读取与跨账号拒绝；真实 PostgreSQL 重启后消息仍可读取。静态推导、模拟页面测试、HTTP 200、测试数量或 OCR 无发现均不替代真实验收。

沿用 React 18/TypeScript/Vite、现有 controller/store、账号 generation、request/attempt、消息分页、localStorage 副本与现有后端接口。不新增依赖、后端接口、API wrapper、缓存格式或持久化引擎。可信服务端代码维持原信任边界；网络响应、模型文本及本机候选必须按现有身份/内容约束验证。真实模型内容不提供关联授权，persisted=true 仍须由权威消息读取确认。

## 第二层：子模块概述

### A. 真实页面交错复现

职责：用实际页面、AuthProvider、store/controller 和按钮驱动，不直接调用内部 confirmCompleted 制造目标交错。受控网络只安排同一合法请求的消息页返回顺序。输入是可信 completed 请求、既有冲突和两次用户点击；输出是网络时序、完整候选身份、可见消息/错误/发送门禁/副本及额外 POST 次数的证据。

先在现有 App/RTL 业务测试中确定 UI 可达，再在真实浏览器通过页面重现该受控交错；两者均明确使用受控后端结果，不称真实模型验收。若现有按钮单飞或生命周期使交错不可达，不绕过按钮插入内部状态；写出不可达证据并复核静态结论。

### B. 局部请求关联证据次序（条件实施）

职责：在既有 `confirmCompleted` 的提交边界区分新可信冲突与新无结论失败。数据流仍为原请求 GET、snapshot/messages 核验、状态发布、精确副本清理。异步操作只在相同账号代次/用户/session/request/attempt 及完整 payload/response/baseline 身份内比较先后；source 候选独立核验。

当前有效来源发布的较新可信冲突必须阻止更早操作的 matched、错误回退和 cleanup；在既有冲突之后启动、且没有再遇更新冲突的全新可信重查仍可以恢复。503、游标故障、超时、来源变更/读取失败和身份失效不得推进可信冲突证据。维持原 latest 语义保护已匹配成功不被旧失败/冲突回退，不将本次局部次序变成“仅最新请求允许成功”。

### C. 分页合同与来源保护

职责：沿用原 v1.2 精确查找规则，不另建扫描器。按 opaque cursor 前翻；目标 user/assistant 可跨页，取得两角色、已越过目标 turn 或 cursor 耗尽即结束查找。不得为排查本次竞态强制读取目标之后的全部历史或解码 cursor。缺角色尚可继续分页、网络中断和版本滞后保持未确认；可信基线下合法结束仍缺角色或内容矛盾，按原精确查找段保留 inconsistent 和副本；无可信 baseline 走原 unassociated 与显式继续合同。若真实数据触及原条目歧义，先记录并提请合同确认，不能偷偷改变旧断言。

身份失效或本机来源不再可证，不得发布成功/冲突、清其他 writer 副本或抹掉原文。请求关联状态、当前 UI request sequence、教学/画像版本、活动门禁和历史 cursor 仍各有原资格，不因新增证据比较互相覆盖。

### D. 完整审阅与真实验收

职责：将受控复现、自动回归、OCR、真实浏览器/模型和真实 PG 结果分别归档。完整审阅按项目 OCR preview/rule 的全部文件清单、完整上下文和调用链进行，审阅先报告后修复；外围建议先按原目标判定本次/后续/接受限制/证据不足，不自动扩大范围。

## 第三层：子模块详细实施设计

### A. 复现函数与证据数据

复用 `web/src/pages/Chat.test.tsx` 的页面挂载、请求响应控制和用户交互辅助函数。测试场景命名应直述“已有冲突双重查，新冲突后旧成功不得清副本”和“已有冲突双重查，新网络失败后旧成功可恢复”。辅助函数输入为同一 request/attempt 的可信 snapshot、两组延迟页和 source 候选，输出为可逐个释放的响应句柄及请求记录；只复用/补足所需辅助，不新增通用故障框架。

时序：先从合法请求实际走到 inconsistent；点击重查 A，使其历史页挂起；再点击重查 B，确认两者都在已有冲突状态启动；B 返回可核验内容矛盾，观察警告和禁发；A 最后返回正确消息。断言 B 冲突仍存、错误可见、发送不可用、本人及其他 writer 副本均未错误清理且没有重复 POST。另行运行 B=503/游标失败、B 来源失效及随后用户主动新重查成功的对照。

记录 user/generation、session/request/attempt、payload/response/baseline、writer/writeId/kind/phase 与候选完整内容、操作起止序列、URL、GET/POST 次数、消息 ID/内容和状态。token/密码与模型密钥不得写证据；账号标识以验收用测试账号记录。

### B. 函数、字段与提交条件

`confirmCompleted(id, requestId, ticket, source)` 保持现有输入和异步返回契约；`associationCurrent` 继续核完整请求身份，`sourceCurrent` 继续核候选，`cleanupMatchedRequest` 仍只在本次真实发布 matched 后调用。无需改变外部调用方/API。

条件修复优先复用已有 `associationRuns`：每个精确身份域保存单调启动序号、活动运行数及最近有效可信冲突的操作序号；每次调用捕获自身操作序号与相应域实例身份。若现有 key 仅含 request/attempt，则记录内必须核完整 payload/response/baseline 身份，不能借用同 key 的不同事实。source 使用既有完整候选核验，不为不同 writer 错误共享来源授权。

“可信冲突发布”以操作启动序号为顺序：只有仍有效、仍满足原发布资格的冲突写入，才能推进冲突证据；普通异常不能推进。成功提交前，在同一同步状态变更边界核当前身份、来源、UI 资格与较新冲突序号，若有比自身更新的可信冲突则返回不变并禁止 cleanup。后续新重查序号晚于已有冲突，可在全部既有校验通过后恢复。不得仅比较 initial.association 的字符串，也不得用全局最新开始序号否决所有旧成功。

操作全部结束后释放本域记录；新请求/attempt/账号不能继承旧证据。finally 只回收自身域实例，避免旧 finally 删除替换实例。新字段不持久化、不包含历史正文、不建立跨刷新保证；状态规模与当前在途关联数相关，不随全部历史增长。若这组字段仍不足以在局部代码表达合同，先说明根因和新增必要性，再修订计划，不直接叠加框架。

### C. 必要回归与错误分类

对照必须包含：旧失败不覆盖新 matched；新可信冲突不被旧成功覆盖；新 503 后旧成功可恢复；新来源失效不推进冲突且警告/重查可用；新用户主动一致复核解除旧冲突；同账号新 generation、其他账号、会话、request、新 attempt、UI sequence 以及不同 payload/baseline 不借用或覆盖结果；其他 writer 副本完整保留。检查成功写入内消息 ID 内容冲突分支与 catch 使用相同证据规则，但不取消原 message/profile/activity 门禁。

分页只补与原合同相关的必要对照：目标两角色跨页、超过首屏、合法耗尽/越界、网络中断/版本落后/游标回环与无 baseline。真实后端契约未证实的异常空页不当作已证实永久丢失；对原计划歧义单独呈报，不顺手重构。

### D. 验收与停止条件

先定向行为回归，再完整已有前端测试与构建；冻结前后源和测试哈希及退出码。OCR 按完整 Task10 范围取 preview、获取每文件规则、逐文件读 diff 和源码，报告覆盖 total/reviewed/skipped/coverage_rate 与未验证范围。审阅意见先裁决与原完成条件关系，确有范围内修复则回到已确认设计及必要复验。

审阅通过后，真实浏览器访问实际前端及后端，使用独立非生产账号和专用数据库，不修改既有用户数据库。保留原 Task10 v1.2“代码审查后的功能验收”全部相关场景：注册/登录、选本人已有画像新建会话、输入草稿、A/B 切换、真实模型提问与后续教学、persisted=true、权威消息 ID/内容及服务器读回、重新读取/刷新/重登恢复同一会话，以及**正常退出成功**。正常退出须观察保存结果明确、退出完成和再次登录后的实际恢复，不能用刷新/重登替代退出保存门禁的验收。

另列**真实后端慢生成 A→B 后 A 完成归位**：A 发起真实模型生成尚在途时切到 B，在 B 保留/编辑草稿并核其界面；等待 A 的实际后端完成，核 A 的消息与状态只归 A 桶、不污染或打断 B，回到 A 可读取权威持久消息。普通空闲 A/B 切换及受控延迟 fetch 不替代这项真实后端验证。采用主动检查请求/进程/消息状态跟踪进展，不使用 sleep 强制等待。

失败、冲突、断网及恢复的 UI，须通过独立测试服务的可控故障或安全隔离账户实际操作，分别核可见错误、原文/副本保留、发送门禁、明确恢复出口与恢复后的真实结果，保留实际请求结果和截图；不能用 HTTP 200 掩盖真实模型失败。受控服务故障与真实模型正常/慢生成结果分开标记。若断网、冲突或其他故障无法在专用环境安全制造，逐项标记未验收并说明原因，不影响现有用户数据，不用 mock 通过结果补成真实验收。

使用真实 PostgreSQL，在明确测试环境和数据边界后重启服务并读取相同消息；用另一测试账号通过真实请求确认拒绝访问原 session/request/messages，同时核对应跨账号 UI 不泄露数据。分别记录运行环境、入口 URL、时间、请求标识、实际状态与截图/日志。受控响应、SQLite 和静态网页不替代这些证据；环境缺失则明确剩余项，不宣称完成。上述场景在配套计划任务 5 逐项映射，任一未完成的原核心验收都保持未完成。
