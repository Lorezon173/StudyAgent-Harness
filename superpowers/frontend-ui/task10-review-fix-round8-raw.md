# Task10 第八轮审查修复：三层详细设计（raw）

依据：`docs/delivery/study-workspace-goal/evidence/Task10/review7-final-product-code-review.md`；继承 Task10 原计划及前七轮所有已批准约束。已有 inconsistent 时两次重查的时序及空页分类均未经审查者实测，不得称为线上事故。本设计和实施计划须先通过独立计划复审，之后先真实业务复现，未获审查前不编码。

## 一、模块总览

目标：用针对具体请求身份的**可信关联证据代次**区分同一请求的多次有效重查，避免已有冲突时较新确认的冲突被更早成功覆盖、错误清除和误删副本；同时新查询仅网络失败、游标异常或来源失效时，保留符合原门禁的旧可信成功恢复。不同账号、session、request、attempt、payload/response/baseline、候选来源与 UI sequence 不能混用；多层并发不能依赖仅检查 `initial.association` 的布尔状态。

后端只读核查：`SessionService.load_messages` 以会话为范围，按 turn、role 顺序和 ID 倒序分页、页内返回正序；`commit_turn` 在同一业务事务中依次 flush user/assistant，再更新状态、完成请求并由外层 commit。此为代码契约，不是本轮真实 PostgreSQL 已通过的证明。原 Task10 v1.2 的 `docs/superpowers/plans/2026-10-27-task10-round1.md` 第 214～216 行规定可信 baseline 下必须读到唯一 user/assistant；网络中断、页未读到目标或 snapshot 版本落后保持未确认，完整读取仍缺角色或内容不符为 inconsistent；第 218 行无可信 baseline 为 unassociated。第 225 行将“历史记录缺失”与“无可信基线”并列，文字范围有歧义，不能据此宣称所有缺消息均 unassociated；须据第 214～216 行具体条件、后端契约及真实测试交叉核对，并在独立计划审查中明确。不能仅凭空页推断数据丢失。

## 二、子模块概述

### 2.1 可信证据代次与关联操作

现有 `associationRuns` 以 generation/session/request/attempt 跟踪 latest 与 active；`associationCurrent` 仅基于启动时和当前 association 的 matched/inconsistent 布尔关系，无法区分两个均从 inconsistent 开始的重查。先通过真实 UI：建立已验证的 inconsistent，请求两次重查，第一次页挂起，第二次先返回可信矛盾并完成，随后第一次返回正确旧消息；观察 association/status、错误、发送门禁、本人及其他 writer 副本、POST 次数。该路径尚未实测。

设计按具体身份分组的证据状态，而非把 association 状态视为证据代次：至少含账号 generation/user、session、request ID、attempt、不可变 payload/response/base/profile/node、可信 baseline 与其来源/候选验证上下文；UI request sequence 单独限制当前气泡写入。每次关联有安全且不会 ABA 复用的运行序号，并捕获启动时对应可信冲突证据版本。**只有当前账号、请求/attempt、原内容及候选来源在发布瞬间仍有效的、完整验证后的可信矛盾**才能按适当次序推进冲突证据代次；更早开始且捕获旧代次的成功不能覆盖该冲突或清副本。任何较旧失败/冲突仍不能覆盖更新的 matched。

同一旧冲突之后启动的主动重查，若期间没有更新可信冲突、没有更高 attempt/身份变更，按所有 baseline 与消息验证可安全解除旧冲突；较新网络失败、游标失效或来源失效本身不增加可信冲突代次，不能仅由于较新启动就一律禁止旧可信成功。若更新操作证据尚在途，不提前假设成功或失败；以真实 UI 测试明确并控制可见提示。新的可信冲突必须能在 UI 保留原文、阻止重复发送并可主动重查，不得被旧成功误解锁。

### 2.2 分页完成、缺失与不确定

严格区分读取过程与已穷尽的事实：后端正常分页只在存在超出 limit 的记录时返回 next_cursor，因此空页却带 next_cursor 与当前实现契约不符；对此应按异常或不完整读取保守重试，不能仅因局部空页断言角色缺失或真实数据丢失。网络 503/超时、cursor 循环或非法 cursor、页读取失败、snapshot 版本落后、不完整但仍有下一页等属于不可证明/可重试，不把它们提升为可信内容冲突代次。若权威身份与版本成立、分页合法连续，且合法 cursor 链已耗尽、在所有已读页内及跨页方向校验通过的前提下仍缺 user/assistant，依据原第 216 行标为 inconsistent、保留证据和副本，并提供重新核查；在已通过分页身份与顺序验证的记录中，目标回合重复角色或目标内容与可信 request/response 不符，或者合法页与当前同账号同会话已验证缓存的同 ID 内容不同，构成可信矛盾；同一次服务端分页读取内/跨页的重复 ID 不论内容相同或不同，均是异常未完成，不推进冲突代次，具体见第五节。无可信 baseline 不由内容/时间推测 turn，继续遵守 unassociated 的既有明确出口。

原计划第 225 行措辞在一般历史缺失与无基线关系上有歧义，本设计不把所有未确认一概放入 unassociated；若实施中发现在已批准契约下无法判断哪种状态，应记录具体输入并先修订/复审，不推断真实数据已丢失，不改后端。所有失败须明确用户下一步，并保留草稿、本机候选及活动门禁。

### 2.3 多层并发、来源与退出

至少验证三重或更深重查、较新冲突后再较新成功、同一代冲突重复确认、旧成功先/后到、新网络失败、source 变更与读取失败；当前真实确认冲突可由用户发起下一次完整、同身份有效的新证据来解除。旧来源在读取中变更时，`sourceCurrent` 的读失败/变化警告必须仍可见；不能因为一个已失效的新来源占据 latest 而永久吞掉另一个有效来源的唯一失败或重查出口。若 UI 只能显示来源变化警告而无旧网络错误，需实际验证用户可点击旧来源并完成，不假定 warning 自动等价于解决所有失败。

同 ID 不同 writer、writeId、payload/baseline 的候选不能混用可信证据或自动清除；请求来源在读取后变化仍无法通过 Storage 实现跨窗口原子互斥，不承诺原子性。只对原 writer/完整候选/仍匹配身份调用已批准的精确清理，其他 writer/未知损坏记录保留并显式提示；两真实 Provider 作为模拟 Storage 的范围验证。账号换代后旧回调不得改变新状态，attempt 和不同 request 的代次互不污染，运行表在所有相关操作终结后清理，不得由旧 finally 清掉新项。原画像、活动、历史前沿、草稿和其他错误继续各自单调。

## 三、详细实施设计

### 3.1 证据与操作标识

对 `associationRuns` 建模：每个请求身份的运行项至少跟踪不可重复的操作序号、当前在途对象与可信冲突证据代次；每个操作捕获开始时的可信代次、请求身份、attempt、准确 payload/response/baseline 和来源信息。数据结构可采用计数与稳定对象令牌或等价方案，但须说明何时增长、何时可清、账号切换如何使旧令牌失效、source 失效是否推进证据及三层并发的仲裁。不能单纯使用 latest 开始序号拦截所有旧成功，也不能仅比较 inconsistent 布尔值。

在发布冲突、成功、错误和清理前重新验证 current auth、record identity、source 有效性和相应证据次序；允许的有效冲突按来源、原请求及完整分页事实推进代次。成功时如果存在其启动之后产生的更新可信矛盾，不改变 inconsistent/status/error、不 merge 未验证消息或清任何候选。新主动操作的证据若验证一致，且自启动无更新可信矛盾，方可解除旧冲突。仅失败/过期/无效来源不冒充冲突。UI sequence 保护当前请求显示，不让后台 A 覆盖 B；不要为绕过 UI 切换而破坏独立 request 的合法完成。

### 3.2 完整分页与证据分类

逐分支核 `confirmCompleted` 的快照、cursor 循环、消息分组与异常类型。将“已完成合法分页且可信目标缺失/重复/内容冲突”与“页还未完成、页不可取、版本落后、无效游标”区别处理；若收到空页却有新 cursor 的异常响应，不得将它当作可证明已读完或真实内容冲突；仅在合法 cursor 链已耗尽、已观测页顺序均通过检查时才适用已完成缺失；仅凭一次观察到更小 turn 不提前停止，以便发现后续响应回跳。按原 v1.2，对有可信 baseline 的已完成缺失仍保守 inconsistent；无 baseline 仍 unassociated，绝不自动删本机副本。所有新规则先用 UI 交错和页请求顺序验证，不能仅因现有代码结构替代事实。

### 3.3 可见恢复、清理与风险

继续使用第七轮 inconsistent 明确查询入口。证据代次要在 **成功进入可信状态的原子客户端更新** 与副本清理间保持一致；任何 `sourceCurrent` 检查失败不得发布成功或冲突，并应保留与本机状态有关的错误及手动重试。无法写/读/删除存储时维持旧警告，不以局部消息匹配掩盖其他 writer 的风险；匹配后只删当前 writer 实际已确认且内容完全相同的候选，保留其他来源。前后异步读写有不可消除的跨标签窗口竞态，必须在测试/报告中如实说明。

完成测试后冻结至少 46 个输入文件，完整定向、全量前端测试和构建、前后 SHA；停止任何源码/测试修改后由独立 subagent 审查完整 Task10。真实浏览器、模型、persisted=true 与消息读回、PostgreSQL 重启和跨账号拒绝另行验收，未完成不得宣称完成。

## 四、分页顺序及回跳验证（独立审查修订）

### 模块总览

原计划允许在已越过目标回合时停止，但这建立在服务端按约定排序的前提上。为了识别异常响应而不把后续页可能回跳的目标误判为缺失，本轮在需要判定缺失时采用更保守的规则：**不因看到一个较小 turn 就提前结束**，沿服务端提供的 opaque cursor 继续到合法耗尽，并核验已观察到的每页及相邻页方向。若资源、超时或游标错误使读取提前停止，状态为未确认并允许重试，不当作已完成缺失。找到并验证完整目标消息时仍按既有规则决定匹配，同时对已读取的所有页执行顺序校验；不因此宣称未来未读页或多次 HTTP 请求的全局一致性。

### 子模块概述

使用 DTO 可见 `(turn_index, role_order, id)`：`role_order` 与后端一致，user=0、assistant=1、其他字符串=2；检查 `turn_index` 是非负安全整数、id 为正安全整数、role/content 为字符串、items 为数组，cursor 为 null 或非空字符串。按元组比较每个非空页内部严格升序；每个后续较旧非空页，其最大元组须严格小于前一非空页的最小元组。相同消息 ID 在单页或不同分页重复，即使内容相同也不符合当前后端严格游标契约，作为异常未完成处理；相同 ID 不同内容同样应提示异常，不得把乱序/重复用作可证明缺失或允许清理。区别后端分页返回的重复与当前 store 已有的相同 ID：后者仍需校验完整内容一致，并按原逻辑去重，不能因严格分页而丢弃既有消息。

cursor 只用于原样发送、判 null、校验字符串并检测重复；客户端不解码其内容、不从 cursor 推导消息键。空 items + 非 null cursor 与当前后端实现不符，保守提示异常/可重试；空 items + null 在已验证的当前链终点表示已观测耗尽。页内倒序、非整数/负 turn、无效 id、相同 id、跨页大于或等于前沿及回跳均为未确认，不推进可信冲突代次、不合并部分新页、不清副本。独立于分页的新可信内容矛盾，仍需保证其消息来自身份和排序均已验证的页，不把无效页视为证据。

### 详细实施设计

检查每次 `snapshot.messages` 与后续 `loadMessages` 返回值，在读取器的局部缓冲内验证；维持已见 ID 集、cursor 集和上一非空页的最小元组，逐项验证并在每页结束时检查新页最大元组严格小于上页前沿。同一次分页响应链内重复 ID（同或不同内容）和不相干元组均为异常未完成，不能推进可信冲突代次。与之不同，经过身份/顺序校验的合法页与同账号同会话当前可信缓存同 ID 异内容是可信矛盾，依旧推进代次并保留双方证据；比较时若缓存发生并发变化或来源不可信则停止并重查。只有合法 cursor 终止时仍缺目标，才按有可信 baseline 的原契约保守 inconsistent；如果遍历失败、超时、被用户中断或出于资源限制未穷尽，继续显示可重查，不宣称缺失。对排序已通过且目标两条已找到的路径保持既有 identity/payload/response/baseline 和 ID 内容一致检查。

当前 `Chat.test.tsx` 的 `associates completed requests by trusted turn while deduplicating overlapping pages` 夹具中，第一页包含 user、下一较旧页却包含同一 user 及更新的 assistant，违反后端严格向旧的元组顺序。先记录新规则对原夹具的真实 RED；再将跨页 fixture 调整为最新页 assistant、较旧页 user 的合法顺序，保留按可信 turn、消息内容与唯一渲染断言；另外针对 store 已缓存同 ID 同内容的合法再次加载保留去重测试，对缓存同 ID 不同内容保留冲突测试。不能以删除测试或降低 ID 冲突门禁来掩盖行为变化。测试中此前因未校验而接受的重复后端页，应改为验证异常提示、不清副本及可重试，并保留原始记录。

须明确此校验只约束**已读 DTO 和可观察序列**；每次 HTTP 请求之间可能发生服务端变动，客户端无法从 opaque cursor 和局部响应证明跨请求为同一原子数据库快照。一个“已穷尽”的客户端分类只是按已验证响应链和现有服务端契约的保守判断，不等于真实持久化已永久缺失或数据库已验收；真实服务与并发事务验证仍单独进行。

## 五、重复编号来源与长历史安全续读（独立复审 v2 修订）

### 模块总览

重复 ID 按**来源**区分，而非仅按内容：同一次服务端 snapshot/分页链中同 ID 重复，违反当前严格游标契约，属于读取异常/未确认；一条已通过该链身份、字段、顺序验证的消息与同账号同会话中当前可信缓存的同 ID 内容不同，是两份可信内容相矛盾，应保守标记 inconsistent 并推进该请求的可信冲突代次。前者不可推进冲突代次；两者均保留原缓存、未确认副本与手动重查，不宣布数据库永久缺失。涉及的缓存若身份、来源或并发有效性不能证明，则退回未确认/重查，不臆造可信冲突。

### 子模块概述：结果分类和错误可见性

1. **页链内部重复 ID**：页内或跨页相同 ID，无论内容相同还是不同，均说明响应链不符合严格顺序/唯一约定；停止本次读取，显示“历史分页异常，请重新查询”，不写入局部页、不判完整缺失、不推进可信冲突代次、不清候选。若较早仍有效操作随后取得全部可信一致消息，其成功可按既有身份/其他门禁继续；不能以异常链把该成功一概作废。
2. **合法页对可信缓存同 ID 同内容**：可作为同一条消息去重；既有历史不变，继续正常关联，满足所有身份和完整证据后才清本人允许项。
3. **合法页对当前可信缓存同 ID 不同内容**：确认两者来自当前用户/会话、其来源验证、合法排序、身份及请求/attempt/来源均仍有效，且比较到提交之间缓存版本未变；为可证明的冲突，记录清楚警告、推进对应请求的可信冲突代次，保留原缓存和副本，关闭发送并提供主动重新核对。较早启动的正确旧结果不能覆盖该新冲突或删除副本；之后用户主动进行的新一代完整验证，只有能证明一致且原门禁满足才可恢复。
4. **缓存已过期/不可信、账号或消息版本在途变化**：不能从旧缓存构造可信冲突；中止该次证据提交，保留已有较新状态与副本，展示可重试/冲突状态，重新获取同身份权威数据。该规则也适用于匹配后再次主动校验，不得静默解除已有冲突。

### 子模块概述：有界批次、取消和续读

一次用户发起的缺失核查按每页最多 50 条、每批最多 20 页（不含初始 snapshot）或 8 秒逻辑截止执行，先到者结束本批并让出调度；未暂停时自动排至队尾，无需逐批点击。每 checkpoint 至多一个未完成读取，同一 request/attempt 允许两个独立关联。用户暂停、离开或换代立即使批次业务令牌失效；已有 fetch 不保证物理中止、仍占额度至结束，当前代有效 401 仍触发认证失效。预算到期时若 fetch 尚在途，其迟到业务数据丢弃，等待其结束后自动排队重验；用户已暂停则仅在用户继续后排队。同 checkpoint 在旧请求结束前不发第二个，界面可立即退出。IDB 写入的失效和提交边界依第八节。

核查 checkpoint 改为按账号隔离、分批事务写入 IndexedDB，工作内存只保留固定数量的正在处理页与小型状态；身份、来源、前沿、冲突证据和崩溃重验规则见第七节。继续前必须验证最新认证 request、snapshot/head 及来源；不能将 checkpoint 当成跨 HTTP 事务快照。

有效 checkpoint 沿原 opaque cursor 自动跨批继续，保留 ID、cursor 和排序前沿；UI 展示进度及暂停，用户暂停或异常恢复时提供继续。取消、账号换代、浏览器中断或本机配额不足只暂停核查并保留副本，不按累计页数、ID 或字节设置永久上限。

### 详细实施设计

分别设计 begin、continue、cancel、恢复及安全持久化职责，输入精确请求身份与来源，输出已匹配、可信冲突、可继续、身份过期、用户取消或读取/存储异常；checkpoint、401 及物理边界依第七节，原副本与不相关警告不受影响。

增加两种真实 UI 并发测试：新读取的页内/跨页重复 ID（同/不同内容）在旧合法成功之前完成，应显示异常、不得推进可信冲突代次，旧成功在其他条件满足时仍可匹配；新读取的**合法有序页**与当前可信缓存同 ID 异内容先完成，应显示冲突/禁发并推进证据代次，旧成功不能覆盖、不能清本人或其他 writer。还需验证页面内容/消息数量、请求 association/status、禁发、精确副本与随后重查，而非只看错误文案。若该冲突是缓存并发变更/身份无效导致，则按过期处理，不能推进。

## 六、并发作用域、排队与资源公平（独立复审 v3 修订）

### 模块总览

选择**每个独立关联操作各有 checkpoint，允许同一请求的两个独立关联并发**。这保留任务 1 的真实页面交错以及已批准的可信冲突证据代次，而不是通过全局单飞使竞态消失。第 5 节“一个当前页 fetch”仅约束**同一个 checkpoint**，不约束所有同 request 的其他操作。限制均位于一个当前页面的 JavaScript 运行实例内；不同浏览器标签/Provider 的内存不共享，绝不声称进程内限额是跨页面锁或存储原子性。

### 子模块概述：独立操作、额度与公平

一个操作标识包含账号 generation、user、session、request、attempt、不可重用 operationId，以及可选的 source kind/writer/writeId/完整内容、payload/response/baseline；**即使来源相同，用户两次明确重查也可创建两个相互独立的操作与 checkpoint**，以真实复现“旧页在途、新冲突先完成”；单一 checkpoint 的继续按钮只继续其自身，不偷换成另一次全新核查。每个关联操作同一时刻最多一个 in-flight 网络请求（包含它独立发起的快照或消息页）；相同 request 的已有 `readRequest` 请求可以按原身份去重，但每个消费者必须分别验证其候选和结果，任何共享查询不等于共享 source 授权。

同一账号代次/session/request/attempt 最多同时有 **2 个实际运行或底层 fetch 未结束的关联操作**；整个页面实例最多 **4 个**此类操作；每个页面实例最多保留 **8 个**操作 checkpoint（包括运行、排队和暂停）。这些限制只覆盖关联核查，不声称约束其他业务请求。每个关联的 20 页/8 秒批次预算分别独立；每个运行操作在内存仅保留有限页，累计验证数据持久化至 IndexedDB，容量受设备真实配额而非固定总历史页数限制，详见第七节。单个 writer/source 在同一请求最多占 2 个 checkpoint，第三次重复点击不新建，提示已有核查；其他 writer 在同 request 的两个运行名额已满时可排队或主动取消，不因来源不同被隐式丢弃、合并或清理。

当运行名额不足但 checkpoint 总容量未满，新操作进入可见 FIFO 队列，页面展示该操作/来源“等待核查”并提供取消；不发它的 request GET、snapshot 或分页请求，也不清副本。排队选择遵循先进先出：检查队首请求是否受本请求 2 名额限制；若受限则按入队顺序取首个符合条件的操作，避免一个 request 阻塞其他 request；它释放名额后原队首仍优先。轮转一个已暂停/继续的 checkpoint 时需重新排队到队尾，避免单一长会话长期霸占 4 名额。若 8 个 checkpoint 已满，拒绝新增并显示“核查任务较多，请先结束或继续已有任务”，不悄然丢失用户操作；用户可主动停止/放弃 checkpoint（只释放本次核查资源，保留请求及副本）后重试。该规则为队列已接收任务提供可观察的公平机会，并非承诺恶意网络永不返回时绝对无等待。

### 子模块概述：暂停、在途请求与 source 隔离

某 checkpoint 的 8 秒截止使该批业务令牌失效并让出逻辑等待；已有 fetch 仍计入 request 2 与全局 4 额度至返回或原 120 秒超时，迟到业务数据不发布，当前代有效 401 仍失效认证。旧 fetch 未结束前不得为同 checkpoint 发下一请求；结束后未被用户暂停的任务自动排队，重验身份、source、snapshot/head 和证据代次，用户主动暂停则等其继续。其他 checkpoint 可在剩余额度内独立运行，换代后旧物理请求仍占全局额度，旧 finally 只释放自身。

运行前、从队列入场和跨批继续时分别校验账号、session/request/attempt、当前 source 精确候选和 baseline 等；排队期间失效则释放该队列项并保留来源变更警告，不从其他 writer 的相同 request 借用凭据或冲突/成功结论。证据操作顺序在**真正入场并开始有效验证**时分配；同一 request/attempt 的两在途操作比较可信证据代次，较新可信冲突先完成可阻止较旧成功，新网络失败/失效不推进代次。暂停后重新继续属于原 checkpoint 的新批次，必须按本设计重新读取快照、验证身份/页头/证据代次，不能因 resume 复用旧的已验证授权。

### 详细实施与可验证边界

单 checkpoint 跟踪其独立 batchToken、operationId、source、前沿、已见集合、预算和未决 fetch；队列/额度管理跟踪操作对象身份、待运行与底层未结束两种占用，以便旧 finally 只能释放自己的额度。无 source 的内存来源与持久 source 分开；同 ID 不同 payload/baseline 不共用 checkpoint。界面须能区分同时存在的两个核查（例如按来源“本页/其他页面”、发起顺序或保存时间作普通用户可理解的标签），各自显示进度、继续、停止或等待；取消一个不影响其他 writer/任务、草稿、已完成请求及副本。记录具体资源满、排队、释放、换代与 checkpoint 失效状态，不能用 `sleep` 等待异步测试。

真实 UI 测试必须先在旧代码复现任务 1 的两次同请求独立关联并发，新设计实现后仍允许前两个独立操作各自发起，证明新可信冲突先发布时旧成功不会覆盖；页内重复异常对照旧成功可恢复亦需并发。另测第三次同源点击受限、另一 writer 在同请求排队并最终入场、不同请求在全局空余配额并行；用延迟旧 fetch、逻辑停止、继续、队列取消、账号换代和持续多批与物理配额失败验证真实网络计数上界、状态、候选和公平顺序。所有异常顺序与无真实物理取消的限制须在实现报告中说明。

## 七、401 认证例外与无固定总上限的持久续读（独立复审 v4 修订）

### 模块总览

本节替换原先的内存 checkpoint 和 200 页/10,000 ID/4 MiB 总上限：对合法历史不按累计页数、累计 ID 或累计字节设置永久产品上限；保留每次 20 页/8 秒与第六节每操作、每请求、每页面的在途并发上限。长历史的已验证页链元信息按页增量写入用户隔离的 IndexedDB 检查点，工作内存仅保留固定数量的操作元信息和每操作一页消息，不把整条历史装入 React/store。

必须如实区分软件预算与物理能力：IndexedDB 受浏览器实际配额、可用磁盘、持久存储策略和设备影响，不存在物理无限存储；现有 API 的 `response.json()` 会先解析完整响应，后端 DTO 没有严格字节上限，因此即使将查询 `limit` 设为 1，单条异常巨大的消息仍可能超出设备内存。本设计只把应用长期保留的数据规模限制到固定数量的单页和小状态，**不能承诺任意单个 HTTP 响应的固定字节内存上限，也不能保证浏览器遭遇内存耗尽不崩溃**。如需严格的任意大小单条流式处理/服务端过滤/跨页快照，须先另行计划客户端 API 流式协议或后端能力并审批，不能假装已有。设备/存储暂不可用时显示具体暂停、保留原本机副本、允许重试、换设备或退出；checkpoint 仅在当前浏览器本地，另一设备不能接续其游标进度，需重新认证并从可信首页重扫，不以该情况宣称永久完成或伪造匹配。

### 子模块概述：认证异常与逻辑停止

当前 `apiGet` 内部先根据捕获的认证票据、原 token 和 user 判定 401，再向调用者返回错误。逻辑停止、超时、离开或取消只能禁止该操作迟到的**业务结果**发布到会话、消息、错误代次和副本；已启动的 checkpoint 事务依第八节处理；不允许屏蔽认证层对仍然有效的当前账号当前代次的 401。该 401 必须按现有规则失效认证、执行既有备份/恢复警告流程并导航登录，无论关联操作是否已被用户停止。若请求在发出后账号已换代，即使 user 或 token 字面相同，旧票据的 401 也不得使新账号失效。迟到的普通成功、503、无效页只清理其自身物理在途资源，不产生业务写入；不声称逻辑停止能物理 abort，在途仍受原 120 秒超时且按第六节占用名额。

### 子模块概述：有限内存与可持续进展

每个操作启动或续批时使用现有 loadSnapshot(id, 50)，并用 loadMessages(id, { cursor, limit: 50 }) 传递原 opaque cursor。后端接口上限为 100，50 为本任务有界默认值；每批至多 20 页或 8 秒，自动公平轮转。逐页验证身份、DTO、严格顺序、页界、cursor、已见 ID 和缓存重叠后，以单个 IDB 事务写本页完整 DTO、索引及前沿；不把完整历史装入 store。索引在 IDB 内增量查询；每操作最多一页、全局最多四个操作的页暂存，不表示单响应有固定字节上限。每页事务与账号换代的精确时序依第八节。

浏览器实际存储足够时可跨任意多批自动前进，UI 显示进度与暂停；用户暂停后提供继续。配额失败、IDB 不可用、事务中断或异常页链时暂停并显示具体原因及重试/保留退出，不推断目标缺失；恢复后从最后经身份重验的完整事务前沿继续。没有有效前沿时提示重新开始，禁止自动删除其他用户、writer 或原副本。

验证到目标消息后仍须满足原 request/turn/response 与当前缓存同 ID 的完整一致性，再原子更新客户端关联并按现有精确身份清理本 writer 允许项。不得把已扫描的全部历史页装入 store 造成内存与页数线性增长；若目标回合不在当前连续展示链中，保留原 `messages`、historyIds 和旧 cursor 前沿，用可解释的“已核对的原请求记录”显示两条真实服务端消息（带真实 ID，禁止合成文本），并在正常上翻到该回合时去重/合并；不把相隔历史伪装为连续。现有加载历史仍可按原游标逐页访问。该产品表现须在用户真实 UI 测试中核实，不因匹配而遮掉原历史或影响其他请求。

### 子模块概述：身份隔离、跨批校验与重启

IndexedDB 以用户/会话/request/attempt/随机 operationId 和 source writer/writeId 为命名空间；不保存认证 token，不能把不同账号或不同 writer 的暂存数据合并或向当前账号展示。checkpoint 包含原 payload/response/baseline 与完整来源内容、head 的 session/profile/state_version 与首消息页/opaque cursor、已读前沿、请求 ID/attempt、可信冲突代次及当前 batch 进度；这些本机暂存包括学习历史内容，并非加密或保密边界，同设备用户可能具备浏览器数据访问能力；界面只向已认证的原用户显示，实际认证与服务端授权仍由后端执行。

每次自动或显式续批先以当前账号执行权威 request GET 与本人 snapshot，重新核对 user/session/profile、request/attempt/payload/response/persisted、baseline 和精确 source，验证 snapshot 版本、首页内容及 cursor 与 checkpoint 兼容，检查可信冲突代次和缓存 messageEpoch/重叠 ID。刷新或重新登录后新建账号代次和缓存 epoch，逐条以 IDB 中 DTO 对照已恢复缓存；不可跨代直接比较旧 epoch。身份、来源、状态或已观测 head 不兼容时暂停、保留副本，提示重新核查；不得静默无限从头重试，cursor 不解码。

浏览器刷新/崩溃后可发现并显示**同一已认证用户**的可恢复 checkpoint；旧 generation/operation 不能直接继续，必须创建新代次并完成上述服务端请求、snapshot/head、source 和本机缓存重新校验，证明不满足则安全暂停。若原来源仅存在旧页内存且无法持久证明，不能恢复原 checkpoint，必须保留可能存在的本机数据与警告并从用户确认的新证据重新开始。崩溃在单页 IndexedDB 事务中途时，只能恢复最后完成事务的前沿；缺元信息、索引不一致、被浏览器淘汰或遭破坏时不能声称进度有效，提供重新核查且不删原备份。IndexedDB 提交原子性并不等于电源故障下绝对持久或后端跨 HTTP 原子快照；真实浏览器和故障验收必须单独记录。

### 详细实施及验证

新增项目私有核查临时存储接口（IndexedDB），限定在已批准前端白名单或经复审批准的专用前端文件；每页一次事务写入 ID/元组、原 cursor 和 checkpoint 边界，重复 ID 或 cursor、页内跨页不合法即暂停。使用现有参数 messageLimit/limit=50，不改 API wrapper、不解析 cursor；不得在内存累积全部历史或 ID。事务中止与提交后的隔离依第八节。

真实路由和 API wrapper 测试当前代及旧代 401、迟到成功/503、账号切换和副本保护。超过 10,000 条历史采用受控生成，每页最多 50 条，自动批次无需逐批点击，断言页请求数量与 ceil(N/50) 同阶并单列每批 snapshot/request 重验、目标与耗尽两种终态、用户操作次数、事件循环响应及多请求公平；记录实测时间和不满足时的可用出口。另覆盖无限 cursor 可暂停、配额失败恢复、刷新/崩溃、candidate 变化、多 writer、事务受控时序；不重复 POST、不伪造连续历史。

**授权与范围：** 本设计仅用于用户已授权的多会话持续恢复、消息核对和原有保护，不引入未经用户决定的永久历史长度产品限制；使用浏览器本地 IndexedDB 和必要的已有页面交互来完成该范围。涉及重新定义服务端协议、将学习内容发送到新外部服务或改变全局浏览器权限时，必须先另行设计并取得适用授权。

## 八、事务失效边界与自动公平批次（独立复审 v5 修订）

### 模块总览

本节约束第五至七节：用户此前已授权多会话恢复与持续对话，IDB 仅用于本机关联核对暂存，不改变服务端或另发外部服务。每页最大 50 条符合后端现有 1–100 限制；20 页/8 秒仅是逻辑批次预算，不保证网络或 IDB 物理操作在 8 秒内结束，也不承诺单响应固定字节上限。已观察消息严格排序、重复与缓存冲突验证不可省略；网络多次读取、localStorage 和 IDB 不是共同原子快照。

### 子模块概述：受控事务与资格隔离

启动 IDB 事务前重核账号 generation/user、操作/批次、请求 attempt、证据代次、缓存版本与 source；失败即不启动。事务开始后将事务句柄登记至所属操作，停止、离开、换代、证据/source 失效或预算到期被观察到时，立即失效业务令牌并同步尝试 transaction.abort()；不在事务内部等待网络。abort 成功且触发 abort 事件时本事务写入回滚，仅保留先前已提交前沿；若 abort 抛错、事务已进入提交或结果不明，不虚称回滚，等 complete/abort/error 或崩溃重启判定，视为可能已提交且隔离。身份/source 的跨标签变化只有被观察并复核时才能触发，不能承诺它与 IDB 原子同步。

事务 complete 后即使页面发布前失效，提交数据仍可能存在，但该旧操作没有向当前界面发布进度、matched 或冲突、清副本的资格；由当前认证用户重新发起恢复并完整重验 request、snapshot/head、source、attempt、证据与缓存，才可采用合格前沿。不同账号绝不展示、续用旧数据；同用户重新认证亦不沿用旧 generation 或 token。崩溃后以实际持久可读事务和一致性检查判断，不把未知提交当确定成功或失败；无法完整验证则提示重新开始并保留原副本。清理首选保守保留，用户明确放弃后仅在新事务中按完整命名空间、operationId 和记录版本核对一致才删该操作暂存；不清 localStorage 原副本、不删他人或其他 writer，检查不成立或读取失败则不删并提示。跨标签同时修改不能由客户端声称绝对互斥。

### 子模块详细实施与验收

存储接口需能登记/撤销唯一 transaction 句柄、请求 abort、跟踪 complete/abort/error、隔离未知结果，输入完整操作身份和预期版本，输出已提交、已回滚或待重新验证；发布入口独立重核当前资格。调度器以一个 checkpoint 一个在途、同 request 2、全页面 4、总 checkpoint 8 为界；批次结束释放运行权并将同一 checkpoint 排到 FIFO 队尾，跳过受同 request 限制的队首，使用事件循环让步让交互和其他任务获得运行机会；不新建 checkpoint 或自动 POST。超时后底层 fetch 仍在途时先等待结束，不重叠重发；用户暂停后不得自动恢复。

先在旧产品的真实路由/UI 测试可达的业务：双重查时新可信冲突先于旧成功发布、长历史恢复/排序及用户操作；逐项记录实际响应、状态、副本、请求数、日志和退出码。若行为已通过或交错不可达，照实记录，不虚报 RED；旧实现尚无本轮 IDB checkpoint，模块缺失、导入/编译失败不算既有业务缺陷。针对新存储能力先写能加载、能执行的行为契约测试，用明确标记未实现的可执行占位适配器记录能力尚不存在和相应行为断言未满足，不将它归因旧产品。建立最小真实 IDB 接口后，再执行真实浏览器事务测试和可控适配器测试并逐项 RED→GREEN：事务前失效不写；事务进行中失效并验证真实 abort/回滚；complete 后发布前换代/停止不发布，换代隔离、同用户重验；abort 抛错/结果未知、关闭崩溃与重启、source/attempt/证据/缓存和其他 writer 改变、读取及安全清理失败均保留原备份。真实浏览器验证 IDB 事件和边界；无法受控的异常由适配器补充并标明，不能冒充真实浏览器。保留当前代与旧代 401 的真实 wrapper 测试，保存各阶段原始日志和退出码。

长历史验收使用 N=10,050 条合法消息，在受控真实路由按页生成，统计消息页请求、snapshot/request 重验及用户点击分别报告；无失败与无状态变化时消息页请求不超过 ceil(N/50)，另按实际批次数分别计重验，不能以每条一次冒充优化；一次启动后无需每批点击。验证 20 页/8 秒后自动让步、另一个 request 排队得到运行、页面输入或暂停可响应、暂停不重发且继续后前进、异常无限链可停止，且每次仍执行排序/身份/冲突检查。记录测试环境与真实服务的耗时和请求数；真实服务达不到可用性能时明确报告，保留暂停、重试、保留备份退出及其他设备重新扫描出口，不声称突破设备和后端限制。
