# Task10 第三轮审查修复：三层详细设计（raw）

设计输入：`docs/delivery/study-workspace-goal/evidence/Task10/review2-final-product-code-review.md`，继承 `superpowers/frontend-ui/task10-review-fix-round2-raw.md` 与已审通过的第二轮计划。本文仅为设计，不授权跳过独立计划审查，不包含实现代码。

## 一、模块总览

目标是使历史链同步失败不吞掉同一可信快照中的独立画像及活动观察，同时先用真实业务交错验证 POST 后请求查询被后续观察取代的风险；只有业务 RED 成立后才对该风险实施必要修复。独立审查已确认前者的异常路径；后者是静态推导，尚未业务复现，不预断它是实际故障，也不把 HTTP 200 或请求完成等同于消息持久化。

沿用 React、TypeScript、现有 workspace store/controller、鉴权票据、请求查询、消息关联、分页与本机恢复设计；不更改后端、API、依赖或本机恢复格式。快照按消息历史、画像、教学状态、活动观察分领域处理，领域内仍须各自满足身份、版本、观察次序及请求关联条件。消息桥接是历史发布的事务边界，并非其他领域的成功条件。保留原有草稿、副本精确身份、跨 writer 保护、状态冲突、异步旧结果隔离及路由选择保护；不能为了展示或自动恢复放松发送门禁。

## 二、子模块概述

### 2.1 身份验证与独立快照合并

输入为用户代次、会话 ID、加载序号、活动 epoch/观察序号、当前会话缓存及服务端快照。先验证当前账号与快照会话/画像归属，再分开评估画像 revision、教学 state_version、活动观察及历史桥接；无效身份不能更新任何领域。最新加载序号控制加载结果及历史错误；活动 epoch 和观察序号共同控制活动状态，旧观察不得清空或覆盖较新请求和门禁。画像只按已有 revision 规则递增；同版本不同内容保留旧值并提示冲突，旧版本不回退。教学状态按既有 state_version 规则，不能因为历史失败而宣称历史同步成功。加载快照为旧教学版本时保留既有旧版本处理及独立画像语义。

活动快照为 running 时保留可信请求身份并驱动已有查询/轮询；若观察已过期或不足以证明可安全发送，保持现有阻塞或 uncertain，不能用旧 idle 清除较新运行状态。没有旧会话缓存时，历史失败保留加载错误，不伪装完整可用。独立更新也必须防止非本账号数据进入 store。

### 2.2 连续历史与未关联继续

`connectSnapshotHistory` 的分页数据先临时汇集、身份与连续性检查通过后一次发布；网络失败、无效或回环游标、相同 ID 内容冲突均不能写入部分新页。失败保留原 `messages`、`historyIds`、`nextMessageCursor`、`visitedMessageCursors`、分页错误/进行中状态和消息版本；明确显示历史同步失败并保留重试入口。一次已有上翻与新加载交错必须继续遵循原票据及游标规则，不得覆盖新的分页结果。成功重试须真正连接旧链并再清除对应历史错误，不能把不相交的新旧消息简单拼接。

未关联继续也会读取快照与桥接历史：桥接失败不将请求标记为已继续或已匹配、不清副本、不释放活动门禁；同一有效快照中的画像和活动按各自身份及观察规则独立合并。仍须验证请求 ID、序号、attempt、association，较新请求或账号代次出现后旧结果不得写入；随后用户重试成功应补齐并正确延续旧游标。继续操作既有“新活动存在或观察发生变化则保守阻塞”的限制不可削弱。

### 2.3 POST 后旧请求查询竞态（待复现）

业务假设：发送得到已匹配的 POST 响应后，其 request GET 被切回会话的较新活动观察淘汰；若新快照不列出已完成请求，原路径捕获 `StaleObservation` 即返回，可能遗留 preparing。该行为尚无交错测试证明。先以真实路由、控制器、延迟请求和明确的 HTTP 次序观察；若不能复现应记录结果并核查假设，禁止编造 RED 或为该假设添加无必要产品改动。

若复现，恢复仅针对同账号代次、同会话、同请求 ID 与发送序号；旧 GET 结果绝不发布，也不覆盖较新 attempt、已匹配/终态、新请求或较新的活动观察。恢复动作只重新查询既有请求，不能再次 POST 或凭 POST 成功认定已持久化；应在去重查询已释放后触发受控的复核，网络错误保留原文与本机副本并提供可重试的未知状态，避免无限立即循环。running 继续既有轮询；completed 仍经真实消息读取、身份及基线关联确认后才显示完成并精确清理本 writer 副本。另有活动请求时维持门禁；账号变化或请求已被替代时旧流程无副作用。无后台进度时界面提供明确的重新查询出口，避免永久 preparing。

## 三、子模块详细实施设计

### 3.1 快照领域拆分

- 检查并必要时提取快照身份验证函数：输入鉴权票据、目标会话、快照；输出是否可信，验证 user/session/profile 关系，失败不改变 store。仍保护快照结构及版本字段。
- 检查并必要时提取画像合并函数：输入当前画像与快照画像 revision、内容，输出更新、保留或同版本冲突提示；不把画像变更绑定到消息桥接完成。
- 检查并必要时提取活动合并函数：输入票据、活动 epoch/观察序号、当前 session/request/pending、快照；输出可合并的活动与需要查询的请求。只有当前观察可发布其活动；过期/存在不确定性必须保留或加强门禁，不能取消已有较新锁。活动字段与教学字段按域处理，避免将旧 session 对象整体覆盖较新活动身份。
- 调整 `applySnapshot`/加载入口的协作：历史桥接成功时沿用完整合并；失败时允许可信且仍有效的独立领域更新，失败状态和旧历史前沿分开提交。错误写入仍须验证 load sequence。保存请求 ID、请求序号与 attempt，不构造与服务端不符的请求。
- `continueUnassociated` 使用等价领域规则，但其释放继续操作额外依赖原请求身份、completed/unassociated、快照 state_version 及活动安全检查；中间失败不改变 continued 标志。

### 3.2 分页连续性

保留 `connectSnapshotHistory` 的临时 ID 映射与访问游标集合：每页检查 ID 内容一致性、有效游标及已访问游标，直到接上现有历史链。返回前任何异常不提交消息及游标。并行上翻要以消息版本/现有分页票据判断发布时前沿，成功桥接不得回退已推进的旧游标；失败不重置任何前沿。历史错误与画像冲突错误分别可见，不互相吞掉。异常的旧账号/旧加载不发布错误或领域更新。

### 3.3 请求复核（条件实施）

- 检查 `send`、`readRequest` 的共享在途去重、`reconcile`、`schedulePoll` 和 `confirmCompleted`：对被淘汰的 POST 后 GET，在其 Promise 从去重表移除后，根据账号/请求/序号与权威终态判断是否仍需一次复核；不得重复复核导致忙循环或覆盖已有更高 attempt。
- 复核入口继续走现有请求身份、payload、baseline、attempt 和消息关联校验；若通用 `reconcile` 不足以校验本机 baseline，应补足而非绕过。保留 POST 前草稿及 linked/request 副本，查询失败只能提示与保守等待；成功关联后仍按现有 exact writer/完整候选与读写失败规则清理。
- 定时器按既有用户/会话/请求隔离，账号变更失效；新观察进行中产生竞争时不抢占或篡改其结果。失败有明确用户可重试出口；相同请求的并发查询去重，不得自动创建第二个发送请求。

## 验证与范围

业务 RED 必须使用真实 store/controller 和路由用户交互，模拟网络仅控制交错，不使用纯内部状态断言冒充端到端行为。覆盖新旧观察、账号切换、较高画像 revision、running 门禁、桥接 503/游标错误/同 ID 冲突、成功补洞、旧 cursor 与上翻、continue 路径；竞态另覆盖仅一次 POST、completed 消息持久化验证、running、失败与较新终态。复用第二轮原有门禁、精确清理、多 writer、路由和存储失败回归。冻结源文件及测试 SHA 前后相等，完整测试和构建有原始退出码；独立审查整个 Task10 后才能进入真实模型、数据库重启、跨账号及浏览器验收。具体执行顺序及范围以配套计划为准。
