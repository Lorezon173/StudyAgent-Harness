# 多会话、主题画像与页面重构：补充需求原稿

日期：2026-10-23。状态：需求草案，待确认；未实施。延续同目录 ui-options-raw 的探索，本文对产品功能和导航布局的要求优先于旧 HTML 的布局示例。后续 spec 必须追溯本文。旧 HTML 尚未反映本文。

## 用户明确提出的要求

- 提供多个会话窗口及对应前后端接口，可以随时切换并继续对话。
- 按用户保存每个 session 离开时的状态，下次进入能够恢复。
- 学习画像与 session 内容相关；同一知识块的会话共用一份画像。
- 新建会话时提示选择已有画像或新建画像主题；画像主题归属于用户。
- 左侧栏只承担会话导航，按主题和画像聚合，同主题会话进入对应子框。
- 知识库、学习画像入口置于右上角；账号信息固定在左栏底部，即整体左下方。

## 第一层：模块总览

目标：由单活动聊天页升级为可恢复的多会话学习空间，实现“账号 → 主题画像 → 多个学习会话 → 消息与教学状态”的关系。会话历史连续性与学习画像连续性分别维护。

沿用 React/TypeScript/Vite、FastAPI、SQLAlchemy 和数据库持久化。不在本需求中决定视觉风格、添加新的存储服务或宣称既有线上服务已完成。用户未明确的产品选择在文末单列。

建议采用一个主题对应一份画像、一个会话当前绑定一份主题画像的模型：主题作为左栏分组名，画像是该主题下的学习状态，避免先引入“主题目录”和“画像目录”两套重复层级。此模型为建议，需确认。

同一用户不同主题的画像分别维护；同一主题各会话独立保留消息、教学进度和草稿，但学习评估汇入共享画像。画像共享不等于混用完整聊天历史。不同账号的主题、会话、消息、画像与恢复状态均须隔离。

## 第二层：子模块概述

### 1. 会话导航与工作区

左侧上方为新建会话按钮，中部为可折叠主题子框及其会话列表，底部固定账号和退出入口。选中态清晰；列表可滚动而账号区不随之滚走。组内建议按最近更新排序，显示生成中、未保存或失败状态。

中部显示当前会话，右上角设置知识库和学习画像入口；画像默认打开当前会话绑定的主题画像，同时允许切换查看本人其他主题。窄屏会话栏收为抽屉，仍保留相同信息关系。

建议第一版采用“左栏切换、中央单个活动窗口”，各后台会话独立保留状态。真正同时并排显示多个会话窗口属于待确认的另一种展示要求。

输入为当前用户、主题组、会话摘要和活动会话标识，输出为会话选择/创建等操作。切换采用会话标识校验请求结果，旧请求不能覆盖新窗口。

### 2. 会话保存与恢复

保存不只依赖退出事件：每轮消息及教学状态成功提交后即持久化；草稿与界面状态采用自动保存，切换或正常离开再触发补充保存。关闭、崩溃、断网时不能假设浏览器退出回调一定执行。

恢复分三类：消息记录；模型需要的历史上下文、摘要、当前主题/教学阶段/模式；用户界面状态（草稿、阅读位置、最近活动会话）。前三者不应混成同一份无版本 JSON。界面状态建议按用户和会话保存，跨设备同字段覆盖规则待确认。

恢复接口先鉴权，再加载已提交消息和对应版本教学状态；长历史允许摘要加最近若干轮，但不得把整个用户所有会话直接混入提示词。模型接收到的上下文应足以承接旧问题，不只是页面重新画出气泡。

保存失败明确标记未保存并可重试；无服务端确认不得显示“已保存”。恢复失败保留当前内容并提供重试，不把失败伪装为新会话。断流区分生成未完成与已生成未提交；重试需幂等，避免重复消息或重复画像更新。

### 3. 主题画像管理与归属判断

新建流程：打开创建面板 → 选择已有主题画像，或填写新主题名称/说明 → 创建会话并进入。会话从创建时就有明确画像归属，避免先聊后丢失关联。

同知识块的判定建议以用户选择为权威，系统根据内容推荐现有主题或提示可能的主题偏移，用户确认后调整。禁止未经确认自动合并画像。仅名称相似不足以认定相同知识块；分类依据和理由须可解释。

共享画像记录主题内知识点、掌握程度、薄弱点和评估依据；新增展示字段以实际后端数据为准。每次更新能追溯来源会话、消息/回合和时间。用户总览是主题画像的汇总视图，不等于直接将不同主题分数简单平均。

会话中出现主题偏移时建议提示继续原主题或另建主题会话，默认不移动历史数据。既有会话改绑、画像合并、历史证据迁移是待定规则，未经设计不自动执行。

### 4. 服务端接口、数据与并发

所需契约包括：当前用户的主题画像列表/详情/创建，分组会话列表，创建会话并绑定主题，加载会话快照及消息，保存界面状态，携带会话标识和幂等键的教学请求。具体 URL 和兼容策略在正式 spec 定稿，不将上述契约描述成已存在的 API。

同一会话同时发送的请求需排序或拒绝重叠；不同会话可以独立运行。共同画像的并发更新需版本校验、串行化或等价防丢失机制。切换会话不应把生成中的回复写进当前显示的另一会话；关闭页面后生成任务是否继续需要单独确定。

旧用户级画像不能无依据拆分为多个主题：建议放入“历史画像／待整理”范围，旧会话列入“未分类”，由用户归类。迁移时保留原记录、来源和关联，禁止复制旧分数到所有新主题。

## 第三层：详细实施设计（文字描述，无代码）

以下为候选函数与字段，不代表已实现或冻结。

- listTopicProfiles：输入认证身份和分页条件，输出仅属于本人的主题摘要、画像标识及版本；空列表引导新建。
- createTopicProfile：输入名称、范围说明，输出持久化后的主题画像；相似名称提示复用，由用户决定。
- createSession：输入认证身份、选定主题画像标识和可选会话标题，验证归属后输出新会话及初始状态版本。
- listGroupedSessions：输入认证身份和分页条件，输出按主题画像分组的会话摘要；组内分页，避免全量历史阻塞首屏。
- loadSessionSnapshot：输入会话标识，输出有一致版本的消息、教学状态、画像引用与界面恢复信息；不存在和无权访问分别按既有安全契约处理。
- buildTeachingContext：输入已提交历史、有效摘要、当前问题、会话教学状态与对应主题画像，输出受上下文长度约束的教学输入；不得使用其他主题的聊天记录。
- submitTurn：输入会话标识、用户消息、请求幂等键和版本，输出生成状态、回复、持久化状态与版本；重复请求不重复记账。
- commitTurnAndProfile：输入回合结果、教学状态和有证据的画像变更，原子提交或采用明确一致性协议；父会话先 flush、子消息后写入，同轮只 commit 一次，失败完整回滚。
- saveSessionViewState：输入会话标识、草稿、阅读锚点和版本，输出确认版本及保存时间；节流自动保存，冲突不静默覆盖未提交草稿。
- suggestTopicMatch：输入当前文本、当前主题及本人候选主题，输出候选主题、理由和不确定性；不直接执行合并或迁移。
- switchSession：输入目标会话标识，补充保存当前状态，加载目标快照，仅应用与当前目标一致的异步响应；分别维护各会话生成状态和草稿。

候选数据结构：

- 主题画像：id、user_id、name、scope_description、version、created_at、updated_at；学习节点/边及评估证据必须增加对应画像作用域。
- 会话：id、user_id、profile_id、title、created_at、updated_at、state_version、教学状态引用。
- 消息／回合：session_id、顺序号、role、content、request_id、提交状态及时间；持久化唯一约束与幂等设计配套。
- 教学快照：session_id、schema_version、version、current_topic、teaching_mode、teaching_stage、summary、summary_until_message_id；摘要来源可追溯。
- 界面恢复状态：user_id、session_id、draft、阅读锚点、version、updated_at；草稿是否跨设备同步待确认。
- 画像证据：profile_id、session_id、消息/回合标识、知识点、评估结果、时间和版本，避免丢失溯源或重复累加。
- 前端按 session_id 建立状态映射，每项包含消息、草稿、加载状态、生成状态、保存状态及版本；活动会话标识单独存储。

## 可验收的用户场景

1. 同一账号创建两个会话，分别输入；切换不串消息、不丢已保存草稿，重新登录能找到各自会话。
2. 在会话中讨论某概念，离开后重新打开，历史可读；继续追问“刚才那个例子”时，模型上下文实际含有对应历史或有效摘要。
3. 两个会话选择同一主题画像；一个会话产生有依据的掌握度更新，另一个能读取该主题最新画像，但不会混入前者完整对话。
4. 不同主题画像独立，其他账号无法通过替换任何相关 ID 读写本用户数据。
5. 新建时可复用画像或新建主题；同主题会话显示在左栏同一子框内，右上入口与左下账号位置符合要求。
6. 生成中切换、断流重试、数据库失败、同画像并发更新均无串写、重复回合或静默丢更新；保存失败可见。
7. 使用开启外键的 SQLite 验证事务顺序与回滚，并以真实 PostgreSQL 重启后仍可恢复、跨账号拒绝、persisted=true 完成验收；HTTP 200 不代替持久化验收。

## 待确认的产品决策

1. “多会话窗口”是左栏切换中央窗口，还是同时并排显示多个窗口？建议先采用前者。
2. 是否接受主题与画像一一对应、每个会话绑定一个主题画像？跨主题内容默认提示另开会话，避免自动污染画像。
3. 系统判断同知识块是否仅提供建议、由用户确认？建议如此，暂不自动合并已有画像。
4. 草稿是否跨设备同步，以及关闭页面后正在生成的任务是否继续？这些会影响恢复状态与后台任务范围。

本文为需求补充及候选三层设计，等待用户校正上述决策。未更改产品代码、数据库或已发布页面。
