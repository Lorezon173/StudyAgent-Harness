# Task10 第四轮审查修复：三层详细设计（raw）

设计来源：`docs/delivery/study-workspace-goal/evidence/Task10/review3-final-product-code-review.md`，继承 Task10 原计划与前三轮 raw、实施计划及审查；其中第三轮审查后新增的测试必须保留。本设计仅供独立计划审查，审查通过之前不实施。审查指出的两个缺陷均为源码静态推导，尚无对应业务交错实证；先按可控网络顺序复现，不能将风险写成已实测故障。

## 一、模块总览

目标：在未关联请求的旧历史桥接失败与较新会话加载交错时，不让旧错误覆盖新结果；在教学快照比活动观察旧、教学版本又更高时，确保 session 与教学状态、来源、版本成组一致，且不丢失较新活动锁；补齐第三轮自动恢复复查的请求替换、attempt、其他 writer 组合验证。仅当业务测试证明风险成立时实施必要修复；若不可达或测试通过，记录证据与原因，不增加猜测性代码。

沿用 React、TypeScript、现有客户端 store/controller、认证代次、观察票据、历史桥接和请求关联机制，不更改后端、API、数据格式或持久化协议。保持第三轮已批准要求：历史页完整连续后再发布，消息与旧游标保留，活动观察单调、未知须保守，画像独立按 revision 处理，用户草稿和各 writer 恢复副本严格保护。由较新活动观察保留下来的字段不应被旧观察覆盖；教学字段取自同一可信教学版本。模拟测试和真实持久化验收分别记录。

## 二、子模块概述

### 2.1 未关联继续的迟到错误

`continueUnassociated` 捕获账号票据、原请求 ID、sequence、attempt、association、活动 epoch/sequence 以及当前 load sequence。静态路径表明：桥接失败时内层 `applySnapshot` 可以因 load sequence 过期拒绝旧快照，但外层 catch 仍可能仅凭未改变的请求身份写入历史及请求错误。本轮先用真实路由交错：旧 continue 桥接页延迟，新 `loadSession` 成功且同一请求及 attempt 不变，最后旧页 503；检测成功页、同步提示、请求错误和门禁，验证是否出现过期错误。

必要修复需使继续操作的成功及失败分支分别核对账号、请求身份、最新 load 和活动观察；过期错误不得清除或替换较新的历史错误、请求错误、画像、活动或游标。不能因为新 load 到来而吞掉当前有效的失败警告，也不能把请求标记为已继续、解除活动锁、删除副本。401 换代、另一个请求/attempt、并发上翻、更新画像等沿用既有独立保护。不能把每个新的活动观察都机械地当作允许清除未关联请求的依据；不能因延迟回调抢占路由。

### 2.2 session 与教学状态的版本一致性

`WorkspaceSession` 具有 `user_id`、`session_id`、`profile_id`、`active_node_id`、`state_version`、`next_turn_index`、`active_request_id` 等字段；`teachingState`、`teachingStateSource` 和 `teachingStateVersion` 与 session 的教学版本成组。静态审查发现 `applySnapshot` 在活动观察过期时保留整个旧 session，却可接受同一快照更高教学版本：成功和历史失败两条路径均需交错测试验证。

如果复现，在有效身份和非回退版本前提下，只将同一可信快照中的教学域字段（至少 state_version、active_node_id、next_turn_index 与教学状态/来源/版本）以一致组更新；保留当前较新活动域的 active_request_id、pending requests、activityGate、epoch 和观察序号。其他 session 字段必须逐项核实归属，不用整个旧 session 或整个过期活动快照掩盖某一领域的更新。会话/账号/画像身份不兼容、session 不存在、版本无效或字段无法证明兼容时不能拼造可信快照；保留旧一致组，保守阻塞并显示可重查提示。该组合只作客户端状态呈现，不改变服务端权威数据，也不能绕开发送前重新获取服务端快照与版本校验。

同版本内容冲突、较低版本、较新活动 running/idle、跨画像/跨账号和下一轮序号应分别验证。成功合并的正常路径与历史桥接失败路径都要检查 session/教学组一致，同时历史失败不能写任何半截消息或游标；所有情况均需保留独立画像 revision 和草稿保护。必要时保证不会把一个不同节点的活动请求伪造为与新教学状态同源；请求真实身份及其 baseline 保留并在无法证明一致时保持不确定门禁。

### 2.3 自动复查的身份及跨 writer 交错

沿用 `recoverSupersededSend` 的既有同账号、同会话、request ID、sequence、payload 和 baseline 校验、`readRequest` 去重及 `confirmCompleted` 的消息关联；不以旧 GET、POST 200、404 或网络错误单独认定完成。验证受控重查在途期间：请求已被替换；同一 ID 的较新 attempt/终态已被接受；其他 writer 新增或更改同 ID 的 linked/request 副本（包括内容及 baseline 冲突）。检查较新状态、草稿及门禁保持，绝不删除其他 writer、重复 POST 或静默清理冲突；同一请求完成仍须可证明的持久消息关联。其他页面并发不具跨标签原子锁，不承诺超出当前 Storage 模型的原子互斥。

## 三、子模块详细实施设计

### 3.1 继续操作票据和错误发布

检查 `continueUnassociated` 的 `historyTicket` 和 `connectSnapshotHistory` 的 `stillCurrent`：前者记录开始时 load sequence、活动 epoch/sequence；后者决定异步桥接是否仍有资格发布。若业务 RED 成立，修正 catch/发布路径使用的判定，输入为当前账号、session、load sequence、request ID/sequence/attempt/association 和活动观察；输出为有效失败、失效结果或需要保守重查。对过期结果不得产生新的请求/历史错误和副作用。与 `applySnapshot` 返回 false、`StaleObservation` 和账号失效之间的语义保持一致，不让新观察在途时旧错误覆盖。当前操作实际失败且仍有效时必须显示历史失败、保留重试入口。

### 3.2 教学与活动的领域式合并

检查 `applySnapshot` 成功与 `historyError` 分支以及 `continueUnassociated`、`confirmCompleted` 写 session/teaching 的入口。若测试证实问题，设计集中使用一致的领域决策：读取当前 session、待应用快照、教学版本、活动票据和现有活动状态；先验证所有身份与版本，再决定教学组是否接纳，以及活动组是否接纳、保留或变为 uncertain。只允许相同会话/账号及兼容画像的有效数据参与组装；写入后 `session.state_version` 与 `teachingStateVersion` 一致，教学来源和活动节点/下一轮序号来自同一版本。最新活动锁和请求集合不可因教学更新丢失；若请求与教学上下文存在无法解释的分歧，则保留请求及不确定门禁而不是伪造相关关系。

历史成功时仍只在桥接连续、ID 内容一致、游标合法的前提下合并；失败时保留 `messages`、`historyIds`、`nextMessageCursor`、`visitedMessageCursors` 和上翻状态，并继续允许有效画像独立更新。无当前 session 的首次失败仍报告加载错误，不用半成品解锁界面。对其他写入口逐个核实是否能造成同样分组失配；仅在测试证明需要且白名单内处理，不改变无关逻辑。

### 3.3 原请求重查交错

以实际页面发送、切换会话、延迟两次 GET 与真实 store/controller 触发复查；通过请求快照和本机副本构造被替换、较新 attempt 成功和不同 writer 同 ID 变化。先断言 POST 次数、权威 ID/attempt、活动锁、完整原文和副本；后断言确认历史的对应消息、精确清理与警告。必要代码变更限定在重新校验请求/候选身份与继续采用既有关联流程，任何失效结果不覆盖新请求，不因本机存储读取失败就默认副本不存在。重查失败应保留用户手动查询出口，不无限重试。

## 四、交付门禁

在批准计划后核对第三轮冻结与目前文件差异，明确保留审查期间新增测试；先逐项建立可信 RED 或证明原行为已满足，再最小修复。所有验证保存原始日志与退出码。完成并冻结源码和测试后重跑前端全量测试及构建，前后 SHA 一致；独立复审完整 Task10，通过后才进行真实浏览器、模型和数据库重启/跨账号持久化验收。未测组合与外部限制如实报告。

## 五、登录异步导航测试计划增补（三层）

### 模块总览

第四轮当前冻结版两次完整测试均在 `Login.test.tsx` 的同一用例失败：认证文字已变为 `2:RETRY`，紧接着检查路由仍看到 `/login`；相同用例隔离执行通过。`review4-final-suite.log`、`review4-final-suite2.log` 和 `review4-login-diagnostic.log` 保留原始结果。源码中 `login()` 先发布账号状态，随后执行 `navigate("/chat")`；两次渲染观察未必同步。这是基于调用与失败现象的合理怀疑，尚不能认定它是唯一根因，也不能仅据隔离通过排除产品缺陷。

### 子模块概述

唯一新增文件白名单 `web/src/pages/Login.test.tsx`，其他产品、测试或依赖文件不因此增补授权。该用例同时验证无效化的旧提交不覆盖重试错误、最终认证成功、实际路由到 `/chat`、网络请求精确次数。补充以用户可观察的路由变化作为异步完成条件，再同时断言认证值和请求次数；不得删除断言、延长全局超时或 mock 导航。若完整等待后仍失败，保留日志并重新调查，不再假定为时序问题。

### 详细实施计划

在原冻结版保留旧失败日志。仅调整此用例对异步完成的等待条件：通过测试框架等待真实路由渲染为 `/chat`，并保留对认证为 `2:RETRY` 与恰好四次请求的独立断言；此前重试错误与旧提交失效断言完全保留。先对该用例定向运行，随后冻结所有 46 项（包括增补的测试文件）并运行完整前端测试和构建，记录原始日志、退出码、前后哈希；有任何失败先查根因，不声称该调整已证明产品正确。完整 Task10 独立代码审查与真实持久化验收门禁不变。先独立审查本增补，再实施。
