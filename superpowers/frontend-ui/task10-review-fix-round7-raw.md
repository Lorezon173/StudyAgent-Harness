# Task10 第七轮审查修复：三层详细设计（raw）

来源：`docs/delivery/study-workspace-goal/evidence/Task10/review6-final-product-code-review.md`；继承 Task10 原计划和前六轮 raw、实施计划、审查与全部门禁。两个问题均为静态调用链推导，审查未运行真实交错，不得声称线上已发生。本 raw 与配套计划须先经独立 subagent 审查通过，之前不编码。

## 一、模块总览

目标：基于新旧关联结果的证据性质而非单纯请求开始顺序，保证同一请求的新可信冲突不会被旧成功解除并清除副本；同时保留新网络失败后旧可信成功的既有恢复。核验多个本机来源时，新来源失效退出是否会错误抑制仍有效旧来源的失败提示。必须先用真实页面、实际控制器和受控网络复现；若某交错不可达，记录具体 UI 可见性、去重和调用链证据，不构造内部状态声称已发生。

沿用 React/TypeScript、现有认证代次、request/attempt/baseline、消息分页及 localStorage 机制，不改后端、API、依赖或副本格式。关联操作仍按账号、会话、请求和 attempt 分域，不以会话级全局序号互相取消不同请求。网络故障、来源失效、可信内容冲突及成功的含义不同：成功必须由 persisted=true 与权威消息关联证明，冲突须是有效身份下可验证消息、ID、payload 或 baseline 矛盾，网络失败/空结果不能被当作可信成功或可信冲突。当前失败与冲突均需可见、保守且可由用户主动安全重查；任何修复不重复 POST、不静默清空副本、不放松认证或消息验证。

## 二、子模块概述

### 2.1 同一请求的新冲突与旧成功

UI 通过“回复已保存，正在同步”中的“重新查询”启动较新关联。先验证：旧关联页挂起，较新关联取得可信快照及可核验的同 ID 不同内容或请求消息不一致，表现为 inconsistent 与警告，然后旧页返回原本正确的消息。静态代码表明旧成功可能覆盖新 inconsistent 并清理本人副本，但尚待真实业务复现。

若成立，关联结果须按证据建立发布顺序：旧任务在较新有效可信冲突已发布之后不能写 matched、覆盖错误或删除副本；较新仅 503、超时、404 或其他无结论失败时，旧任务只要账号/请求/attempt/来源/内容仍有效，仍可成功关联，保留第六轮逆序恢复。不得机械地只允许最新开始的成功；也不得因旧成功忽视较新已证实的矛盾。操作键包含账号 generation、用户、会话、request、attempt；识别请求 sequence、payload、response、baseline 及候选精确身份，避免旧同 ID 操作污染替换请求。对不同 request 的成功、错误和清理保持独立。

### 2.2 不同 writer 来源失效与有意义结果

当前 `associationRuns` 同 request/attempt 的 latest 不区分 source；`recoveryCandidateUnchanged` 在失效或读失败时可更新 `recoveryError` 并让操作提前退出。不同来源若能通过页面并发发起，较新来源变化退出后，旧来源网络失败有可能因 latest 不等而丢失；是否可达及现有恢复警告/重试是否已经充分，须先验证，不推断丢数据。

按实际证据区分每次关联的来源身份（writer、writeId、kind/phase、完整 payload/baseline；无持久副本的内存来源单独标识）、在途/成功/可信冲突/网络失败/来源失效等结果。来源失效本身不能变成成功，不能删除副本或用其清理其他 writer；也不能永久使另一仍有效来源的当前失败被吞掉。若来源变更有现成可见错误，保留该错误并保证原请求有明确可执行的重查出口；当前新可信冲突/新成功及更高 attempt 不得因旧来源错误被覆盖。读失败、写失败和变化的副本仍按原规则保守处理。

### 2.3 冲突门禁与用户恢复

检查 `Chat.tsx` 对 completed/inconsistent 的实际呈现及 `reconcile` 对 inconsistent 的提前返回：现有 UI 对可重查入口和输入锁定是否充分需先真实验证，不能假定“错误文本存在”即能处理。若业务测试证明缺口，按已授权 UI 范围显示明确冲突及主动“重新查询”入口；重查只做原 request GET 和可信历史核验，不自动重复 POST；冲突未解决时阻止发送并保留两来源副本。后续用户主动新校验实际证明一致且身份与当前请求有效时，设计明确安全状态转换与清理条件；仍有冲突或获取失败不得悄然解锁。合法不同请求、画像/历史错误、草稿和用户导航仍各自独立。

## 三、子模块详细实施设计

### 3.1 结果分类与关联次序

检查 `associationRuns`、`confirmCompleted`、`associationCurrent`、`latestRun`、同 ID 冲突分支与 catch、`reconcile` 与来源查询。构建局部请求关联上下文：账号代次与用户、会话 ID、request ID/attempt、启动序号、当时可信 payload/response/baseline、UI request sequence（只用于当前 UI 字段）、来源完整标识及其有效状态。至少区分“较新有效可信冲突”“较新已匹配成功”“较新仅网络失败”“较新来源失效退出”和“仍在途”；不得用 `latest` 单数抹平它们。

如测试证明需修改：让仍有效的旧成功在提交前检查是否已有较新可信冲突；有则保留 inconsistent、阻塞和全部未清理副本；若仅有较新网络失败则旧成功在完整身份及消息验证后仍可提交。新来源失效时撤销或标记其资格，而不是重置所有来源、误删尚在运行的新实例或让另一个账号/attempt 的结果互相影响。记录清理策略与账号换代：仅清理本组该实例，所有都终止后移除状态；避免计数泄漏、ABA 复用和同 ID 不同 attempt 互相干扰。按证据区分实际冲突和暂时网络故障，不能从 404 或 POST 200 推导完成。

### 3.2 来源状态与错误发布

对每次 `sourceCurrent()` 前后确认来源及写入授权，精确保留候选读取失败、变更及冲突提示；发生 source 失效退出时，使仍有效的其他来源具备适当发布自己失败的资格，或确保存在等价、真实可操作的显式错误/重试出口。旧来源错误不可覆盖新有效成功/可信冲突、新 attempt、其他 request、账号和活动状态；查看用户界面，而不仅是断言 store 某字段。若多个来源同 ID 但不同 payload/baseline，分别视作冲突候选而非同一个请求事实；无跨页面原子锁，不承诺消除其他 writer 并发写入。

### 3.3 UI 冲突恢复与验证

明确 completed/inconsistent 的可见提示、保存原文与副本、关闭发送、用户实际可点击的原请求重查；重查需重新查询服务端 request 并用 snapshot/分页验证原始 payload、baseline、turn、user/assistant 消息和 ID 内容。已确认冲突不能用旧页、单一 POST 响应或 404 清除；人工重查拿到一致且身份仍有效的全套证据时才允许转 matched 并遵循原精确清理。不影响其他活动锁和画像/历史/备份错误；如 UI 现状已有正确出口，先记录证据，不多加控件。

以真实页面为主要证据，模拟 fetch/Storage 只控制网络和本机状态；对失败路径/可恢复路径保留退出码，最终冻结全部源与测试哈希前后重算，全量测试与构建，独立审查整个 Task10 后才做真实浏览器、模型、数据库重启、消息读取和跨账号验收。
