3. 决策一：chunk_id 放在哪里？

A：新增 SQL 顶层 chunk_id（推荐）B：只放 metadata_jsonC：暂不持久化
做法migration 增加可空列；正式协议通过后新摄入必填；暂不唯一JSON 内保存，Provider 校验 key只用 row ID / chunk_index
收益DB、检索、attestation、评测共享同一 identity 面能保存，schema 改动小最快得到 prototype
代价 / 风险bytes 协议冻结前不能填临时 production 值易缺失、重命名、被 metadata 覆盖；查询/约束弱无法可靠回查同一 chunk
适用目标正式产品链过渡性内部实现演示原型

推荐 D-004-1：选择 A，分两步实施。

  1. 先批准独立、可空的顶层 provenance 列；不加唯一约束，不改变 append-only。
  2. canonical bytes/range 和测试向量通过复核后，新摄入正式 chunk 才必须写稳定 chunk_id；此前禁止用临时 hash、row ID 或 chunk_index 冒充 production stable ID。

判据：可审计的存储槽位现在就能冻结，最终 hash 算法可以等证据充分后再冻结；两件事无需捆绑。

4. 决策二：range 使用什么基线？

A：0-based + Unicode code point + 半开 [start,end)（推荐）B：1-based + 闭区间 [start,end]C：只留 chunk_index / locator
切片复算直接 text[start:end]需 +1/-1 转换无法精确复算
相邻 / 空范围A.end == B.start，语义统一需额外边界规则无统一规则
跨实现明确单位，不依赖 UTF-8 byte/tokenizer仍需另约定计数单位各格式自行解释
代价修订旧 spec 的“闭区间”草案与旧草案表面一致，但更易边界错放弃可复算 stable ID

推荐 D-004-2：选择 A。

- element 序号：0-based
- element 内 offset：Unicode code point
- 区间：半开 [start, end)
- identity 输入：规范元素范围 + 规范 chunk 文本
- source_locator：仅作人类回查与审计，不作稳定主键

判据：与 Python 字符串切片直接对应；相邻范围和空范围无歧义；比闭区间少一层边界换算。

Warning

本裁决只冻结坐标，不冻结 Unicode normalization form、换行/空白顺序或 hash framing。
