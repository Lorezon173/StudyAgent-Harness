## 2. 关键结论（接手人优先看）

1. **三块框架现状是「哑铃状缺失」**——Query 处理层和重排层在架构上缺位（设计源头就缺位，非实现走样），只有召回层有完整框架（多 provider 协议 + 协调器，但内核仅单路向量）。
2. **三个 P0 接线断点**（比任何增强都优先）：
   - 新栈 `TutorAgent` 不订阅 `RetrievedEvidence`，且种子事件不含 `retriever_search`——**检索默认根本不被触发，结果也没人消费**。
   - `retriever_expand_query` 闭环断路：Orchestrator 发 `ACTION_REQUESTED` 不带 query → 空 query → 空检索。
   - `PgVectorProvider.search` 无 `WHERE scope/user_id`——全局检索所有用户 chunk。
3. **design doc 用「重检索」替代了「重排」**——这是项目独特的设计选择（源于职能正交哲学）。所以「检索后增强」在本项目应走"质量门禁 + 重检索闭环"，而非引入 cross-encoder（除非推翻 design doc）。
4. **职能归属**：三级增强不是 Retriever 单点改造——Query 构造归 Orchestrator/Tutor，召回归 Retriever/Infra，质量评估归 Critic。多数 P0 不在 Retriever 身上。
5. **"20%→0%"指标在项目里无依据**——用户带来的那段外部表述与代码现状不符，是 design doc §3.6 设计意图的浓缩 + 量化包装，用"已实现"口吻表述。

## 7. 待用户决策的开放问题（实现前必须先定）

1. **P0-① 修复路径三选一**：(a) Tutor 增订 `RETRIEVED_EVIDENCE` 取 chunks；(b) Orchestrator 在教学 action 前先发 `retriever_search` 并把证据塞进 payload；(c) 协作环把证据写进 `ws.evidence_pool` 供 Tutor 读。——影响后续所有 RAG 改动的接入点。
2. **是否在种子事件里就发 `retriever_search`**——决定"先检索再教学"是否成为默认流程。
3. **T-① 路线分叉**：坚持 design doc「重检索」路线（推荐，只修 P0-② 即可），还是引入 cross-encoder「重排」路线（推翻职能正交，动设计哲学）。
4. **"低证据高置信度 20%→0%"那段外部表述的来源与用途**——项目内无依据；若用作项目描述需校正口径（改成"规划中"或先跑 RAGAS 拿真实基线）。需用户明确来源。
5. **低分门禁的 fallback 形态**：Tutor 坦白无把握 / 降级 Conductor / 跳过主题。
6. **BM25 是否引入**：需先评估单用户平均文档量。

## 8. 下一步建议（落地顺序）

```
1. 用户就 §7 开放问题做决策（尤其 1/3/4）
2. 修 P0（接线，小工作量）—— 让 design doc §3.6 已设计的闭环真正生效
3. 定义「标准化证据契约」（RetrievedEvidence / RAGQualityAssessed / Tutor 消费协议统一）
4. 跑 RAGAS faithfulness baseline —— 拿"低证据高置信度"的真实基线（替代凭空的 20%）
5. P1 门禁 + 阶段感知 query + 重试上限
6. 跑优化后 RAGAS 对照 —— 拿真实收益数据
7. P2 B-① KG 召回 + RRF 融合
8. （条件性）P3 BM25 / 路线 B 重排
```

**核心判断**：教学场景下「修断点」ROI 远高于「加增强」。design doc §3.6 的闭环图已经画好，只是没接通——先兑现设计，再谈扩展。
