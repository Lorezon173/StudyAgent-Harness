## 四、已核实事实（供修订 B-③ spec 直接使用）

### 1. Extractor 与 PDF 提取命名事实

- B-③ spec 中使用了 `PdfExtractor` 命名；
- 实际代码类名为：`PDFExtractor`；
- 相关索引位置：`app/infrastructure/rag/extractors/pdf_extractor.py`

### 2. `get_extractor` 工厂现状与 spec 描述不一致

- 现有工厂实现位于：`app/infrastructure/rag/extractors/base.py`
- 当前不是 spec 假设的 `if/elif` 分支式 `.pdf` 路由；
- 实际是按 `extensions` 列表匹配类顺序返回 extractor；
- 因此 B-③ spec 中关于 `.pdf` 优先路由与回退的写法需要重构。

### 3. `GraphRetrievalProvider` 当前不存在

- 当前代码中没有现成的 `GraphRetrievalProvider` 实现；
- 它不能在 B-③ spec 中被表述为“既有保持组件”；
- 若在 B-③ 中提及，只能作为：
  - B-① 未来产物，或
  - 跨阶段可选依赖

### 4. 现有 `/knowledge` 与 `KnowledgeStore` 已存在

相关索引位置：
- `app/api/knowledge.py`
- `app/infrastructure/storage/knowledge_store.py`

因此 B-③ spec 不能把上传入口简单写成“新增知识库入口”，而必须补齐：

- 上传 PDF 如何关联 knowledge 条目
- 索引后的 chunk/doc 如何与 knowledge 条目关联
- 删除 knowledge 条目时如何处理索引数据

### 5. `PgVectorProvider.index()` 的入参契约比 spec 当前描述更完整

相关索引位置：
- `app/infrastructure/rag/pgvector_provider.py`

已确认：当前向量索引写入所消费的文档字段不止 `content` / `metadata`，还涉及：

- `doc_id`
- `source`
- `scope`
- `user_id`

因此 B-③ spec 修订时必须新增：

- `ChunkingService -> index()` 字段映射表
- 文档/知识条目归属字段的来源说明

### 6. `RAGCoordinator` 已存在，层次边界需对齐

相关索引位置：
- `app/infrastructure/rag/coordinator.py`

B-③ 当前 spec 中有让 Harness 服务直接持有 `PgVectorProvider` 的倾向；
但现有系统中已存在 coordinator 作为编排入口，修订时必须明确：

- 是否通过 coordinator 完成索引编排
- 或者如果不通过，为什么不破坏现有层次边界

### 7. `max_upload_size_mb` 当前不是既有配置项

相关索引位置：
- `app/core/config.py`

因此 B-③ spec 中若继续出现该字段，应改为：
- **新增配置项**
而不是“已存在配置”

### 8. 图片 embedding 能力当前不能写成既成事实

相关索引位置：
- `app/infrastructure/rag/embedding.py`

当前已核实到的是文本 embedding 路径；
不能把“图片可直接走现有 embedding service”写成已成立事实；
如需保留，应标为：`⏳ 待 spike`

### 9. `/knowledge` 路由的鉴权现状与其他 API 不完全一致

相关索引位置：
- `app/api/knowledge.py`
- 其他带 `get_current_user` 的 API 位于 `app/api/` 下多个文件

B-③ 修订时需要明确：

- 上传端点是否复用 JWT 鉴权
- 是否只给新端点加鉴权
- 是否将旧 `/knowledge` 一并纳入一致性修正（本轮不改代码，只需在 spec 中界定）
