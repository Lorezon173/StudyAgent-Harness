## 四、核心结论概要（详情查原文件）

- **两层架构**：L1 在线（Critic，每事件触发、有决策权）+ L2 旁路（EvalKernel，不影响线上、只出选型建议），经 EventStore 解耦。母 spec `:487-520`。
- **L2 五子模块**：ComponentBench / SystemBench / CollaborationBench / ABController / SelectionReporter。母 spec `:507-516`。
- **可信度基石（§5.1.1）**：黄金集双人标注 + Cohen's κ≥0.6；judge 与被评 Agent 不同族 + 盲评 + judge 自身 κ≥0.6。母 spec `:522-536`。
- **协作级六维**：职能正交违约 / 协作效率 / 决策稳定性 / 冲突消解 / 因果链质量 / 轨迹偏离。母 spec `:636-645`。
- **框架分工**：Retriever 检索质量 → RAGAS；Tutor 教学质量 → DeepEval G-Eval（待落地）。混合 spec §0。

## 五、设计-实现偏差（接手者重点关注，均已核对代码）

1. **`app/api/eval.py:39` `rerun_eval` 仍是全 0 stub** —— 对外 API 当前**不能真跑评估**（Phase 4 未做）。
2. **`EvalStore` 纯内存 LRU（最多 1000 条）**，进程重启即丢；`EvalTable` ORM 表已定义但**全项目零读写**，落库链路未打通。
3. **judge 的 `target_agent_family` 是硬编码常量**（`"anthropic"`），非动态探测被评模型族。「不同族校验通过」是常量恰好与 judge 族不同，非真探测。
4. **`answer_relevancy` 语义偏差**：当前把 `golden_answer` 填入 RAGAS `response` 字段，实际语义是「理想答案与 query 相关性」（几乎恒高、信息量低），非字面「答案切题度」。混合 spec §3.2，Phase 3 待重新评估。
5. **黄金用例数量不足**，远未达 §5.1.1 可信评估所需规模（Phase 2 才扩充）。
