## 审查依据

1. **硬链接与文件身份。** 路径先限定已解析 runtime，再对存在文件要求常规文件且链接数确为 1，无法确认或读取失败即拒绝；两存在路径还要确认不同文件，失败不能当作不同。对第一轮自己的隔离空样本做只读核查：原名与别名 `st_nlink` 均为 2，`samefile=True`，大小 0，说明本机的这些接口可识别已复现的硬链接。计划覆盖外部旧库别名、DB/control 互为别名、control 外部别名、新路径、单链接复用与 stat 失败。再次验证须在可能创建控制文件和打开数据库等敏感操作之前；实现复审应核实这一实际顺序。
2. **竞争边界。** 计划明确要求验收目录独占使用，并声明最后一次检查之后不抵御同权限恶意替换；两次路径检查不是原子打开保证。该前提必须在实际使用中落实，不能将本设计宣称为对抗并发路径替换的安全机制。
3. **计数代际。** 成功控制更新含 drop 字段即同步推进代际，包含同值和置零；仅更新其他字段不推进。请求在调用内层前捕获模式和代际，成功完成后在同一事件循环中、不跨 await 核对代际和剩余次数并消费；可排除旧请求消耗新配置，也保留同代并发按完成顺序限量的语义。内层失败、异常和超限不消耗，符合原计划。
4. **验证及门槛。** 计划要求实质性旧源码 RED、修复后同一测试 GREEN、既有回归和编译，并记录原始日志、终态与哈希；覆盖重置为 0 再为 1、同值重置、仅更新其他字段、并发和失败。测试须让旧请求确实进入并停在内层，再发控制更新，避免时序假阳性。真实硬链接若平台不允许创建，应如实记录受限而不是声称通过。修复仍需独立代码复审，且只有辅助和主产品代码审查均通过后才能进行真实功能验收；真实模型、数据库、浏览器与外键行为不由此计划审查证明。
