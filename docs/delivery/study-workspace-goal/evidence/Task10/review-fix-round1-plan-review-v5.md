## 阻断：另一标签页可在准备副本升级期间误判为可安全新发

raw 第 108、110、114 行将新纯 `prepared` 定义为不构成未决请求的文本副本，允许恢复和继续；第 126 行仅明确限制“重启后”只看到纯准备的情况。当前 `web/src/store/localRecovery.ts:30-31,57-65,68-80,105` 使用按 writer 分键的共享 localStorage，其他标签页可枚举同账号同会话的副本。

可达交错：标签页 A 写出纯准备，标签页 B 读到并缓存该候选；A 随后将自己的副本升级 linked、生成 request ID 并 POST；B 仍持有旧纯准备的本地视图，根据第 114 行的非门禁规则恢复到空草稿并以另一个 ID 发送。即使 B 发送前重新读取，A 的升级仍可发生在 B 最后读取之后；而第 122 行允许 linked 写失败后继续 POST，使共享存储可持续只显示纯准备。单项写入和读回不构成跨标签页的排他协议。若 B 先看到 A 的服务端活动请求，后端会拒绝并发发送；但 A 已完成后空闲时，同一原文仍可被 B 用新 ID 再次发送。

最小修正：将**无法由当前执行上下文证明已取消且不再可能提交**的纯准备候选（包括其他 writer/标签页读取的候选）按第 126 行的不确定边界处理，不把共享副本的阶段当作无提交证明；明确允许的用户复制与警示、发送门禁及与其他未决请求的关系，避免静默自动新发。保留当前代次 A→B→A 确认取消后用户可继续的目标。增加两标签页真实共享 Storage 交错测试，覆盖 B 读取纯副本后 A 升级并完成、以及 A 的 linked 写入失败但 POST 成功；断言 B 不得仅凭旧候选推断未发送或静默重复提交。若选择允许用户知情后主动重新提问，须明确这是用户承担重复风险的显式操作，而不是系统证明旧请求不存在。
