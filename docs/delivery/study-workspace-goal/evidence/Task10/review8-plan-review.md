## 阻断：越过目标回合必须验证响应顺序，不能只看到较小 turn 就当完整证据

raw 2.2、3.2 及计划任务 3 允许在“按后端排序越过目标 turn”时将缺失视为 inconsistent，但仅笼统要求“合法连续”；没有规定检查每页消息的 `(turn_index, role_order, id)` 次序、相邻页之间的严格向旧关系，也没有乱序/跨页回跳测试。当前 `workspaceController.ts:827-842` 的循环以已取得任一 `turn_index < target` 为停止条件；如果异常响应在该页掺入更旧回合但将目标放在后续页，单凭这个条件无法证明已越过目标。后端正常实现按该元组排序并以 cursor 严格向旧，但该计划同时要求对异常响应保守处理，不能把未验证的响应自动等同后端正常排序。

**修订要求：** 明确如何核验 DTO 中每页的消息次序和跨页方向、重复与空页/非法字段，并对不满足条件的响应按不完整/异常处理：不推进可信冲突代次、不自动清副本，保留原文及可重试出口。增加真实控制器/页面测试：页内乱序与后续页回跳（包括先看到低于目标 turn、后续才出现目标），应记录现状并验证不能因异常排序宣称已完成缺失；合法有序跨页和真正越过目标的反向测试仍按原契约处理。cursor 本身保持不透明，不要求解码或假装能够证明超出响应信息的连续性。

## 契约核对和其他范围

- 原计划第 214–216 行的具体描述确实要求可信 baseline 下持续分页到找到两个角色、越过或耗尽；网络中断、未读到目标和版本落后保持未确认，已读完整仍缺角色/内容不符为 inconsistent。第 225 行将“历史记录缺失”和“无可信基线”并列，存在范围歧义；不能据此将所有未完成分页直接归入 unassociated，也不能认定真实数据永久丢失。
- 后端 `SessionService.load_messages` 以 `(turn_index, role_order, id)` 倒序取数并反转为页内正序；只有多于 limit 才给下一 cursor。`turn_commit.commit_turn` 依次 flush 两条消息、状态和 completed，`conversation_service` 外层提交。上述是代码契约，不等于真实 PostgreSQL 或跨多个 HTTP 读取提供单一事务快照的验收证据。
- 证据代次、同一 inconsistent 的双重查、较新网络失败后旧成功、源身份失效、三次以上交错、账号/attempt/不同请求隔离、用户重试和各 writer 副本等均有计划条目。完整可靠的分类是推进该代次的前提，顺序验证问题修订后应重新独立审查。
- 计划仍保留冻结、全量测试与构建、整个 Task10 代码复审以及真实浏览器、模型和数据库验收，不能用模拟结果替代。
