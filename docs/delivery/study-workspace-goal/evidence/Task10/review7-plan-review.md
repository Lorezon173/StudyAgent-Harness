## 审查要点

- **新冲突与旧成功：** 计划要求在真实页面形成两个可核验的关联，先观察新内容冲突，再返回旧成功，核对错误、门禁与副本；对照新 503 后旧成功仍可完成，避免简单用最新启动序号拒绝所有旧结果。游标异常、网络失败与真正可证实的内容矛盾须区分处理。
- **来源变化：** 计划先从页面及真实控制器核实多个 writer 候选能否形成该时序；不可达时要记录按钮可见性、去重和调用链，不能以内部状态注入冒充业务复现。可达且存在问题时需保留来源失效警告、其他有效来源的错误和真实重查出口。
- **冲突恢复：** 检查 inconsistent 状态下的实际输入禁用及原请求重查入口；有缺口时只以新的有效原请求和历史全套证据解除冲突，不自动 POST，也不以 HTTP 状态代替已保存消息。计划覆盖存储故障及没有 requestCandidates 时的门禁。
- **隔离与副本：** 操作身份包含账号、会话、request、attempt、payload/response/baseline 及来源，UI sequence 单独保护；不同 request 不使用全局关联锁。精确核验和清理只影响本 writer 的允许项，另有真实双 Provider 测试及跨页面非原子边界。
- **验证顺序：** 静态推导先复现或记录不可达，保留误判和退出码；完成后冻结源文件、全量测试和构建，再独立全范围代码复审和真实浏览器、模型、数据库验收。
