## 阻断项

1. **门禁状态未接入现有发送与界面，出口超出白名单。** raw 第 45、51 行、计划第 68、71 行要求保守门禁、提示和显式重新查询，但计划第 15、27、39 行白名单排除 `web/src/pages/Chat.tsx`。现有 Chat.tsx:46-47、50-51 只依据具体 request 状态展示查询按钮、错误及 composer busy；一个已 matched/completed 的旧请求不会显示查询入口，新的本地 uncertainty 也不会使 composer 禁用。`workspaceController.ts:375` 的发送 guard 同样没有该状态。仅在 controller/store 增加 epoch 不能实现所承诺的可见门禁与恢复。应明确状态字段、所有读者、按钮调用的查询操作、失败和成功后的可见状态，并经审查调整必要文件白名单。用真实界面测试冲突后按钮可见、发送被阻止、查询失败保持、权威空闲后可发送。

2. **未定义本地请求的精确解锁判据，可能永久锁住原有显式继续出口。** raw 第 36、45 行同时要求 completed/unassociated 可显式继续，又要求没有本地已知运行/未知/待确认请求才解锁；该操作对应的未关联完成请求及其必须保留的恢复副本本身属于尚未关联记录。现有 `workspaceController.ts:367-368` 将 localRequests/requestCandidates 和 pending_messages 视为 unresolved，`Chat.tsx:47` 保留未关联继续入口。计划没有按 request ID、attempt、服务端状态与 association 区分“已确认完成但保留副本”和真正未知或正在运行的其他请求，也没有规定如何由权威查询终态消除旧 running 观察。不能推断实现者会正确排除本人或清理过时门禁。须列出各状态与副本的门禁真值表和转换，规定原完成请求可安全继续但副本仍保留，其他未知/运行请求不可被解除；测试无竞争继续、冲突后刷新、多个不同请求、重复刷新及失败恢复，证明不会死锁或误解锁。

3. **活动 epoch 的证明范围与刷新顺序不完整。** raw 第 45 行将 epoch 不变的本人空闲 snapshot 称为解除门禁依据。它只能证明客户端在该观察期间没有接纳更新，不能证明服务端在 snapshot 生成后没有被另一客户端领取：`app/infrastructure/storage/chat_request_store.py:75-83` 的领取不增加教学版本；`app/orchestration/session_service.py:197-215` 返回读取时的快照而不是未来活动锁的租约。计划应明确这是最后一次可信观察而非后台实时为空的证明，保留 `send` 发起前 snapshot 检查和后端原子 session_busy 兜底，以及冲突时原文与副本不丢；增加模拟另一客户端在空闲 snapshot 后领取请求、发送被服务端拒绝的测试。还须明确每个活动观察在发起时捕获的 epoch 与接纳时递增的顺序，防止两次相反响应因仅比较已接纳观察而颠倒；覆盖独立查询和常规 `loadSession/applySnapshot`，不能只保护两条修复路径。
