结论：**Needs changes**。本版已补充 opaque cursor、页内及跨页方向验证和合法跨页/缓存去重测试，但重复 ID 的证据分类存在冲突，完整耗尽历史的资源及退出策略尚未落实到可验证的行为。

## 阻断 1：相同 ID 内容冲突的分类仍不一致

raw 2.2 将“相同 ID 内容相矛盾”列为可信矛盾；新增第 4 节及计划任务 3 增补则将响应页内或跨页的相同 ID（包括不同内容）判为异常未完成，不推进可信冲突代次。这两处会影响旧成功能否覆盖新观察，不能由实现者自行选择。

**修订要求：** 明确区分同一服务端分页读取过程中重复 ID 与合法已验证页对现有可信缓存的同 ID 异内容等情形，逐项规定是否可形成可信冲突、是否推进代次、可见警告、保留副本及后续重查；同步消除 raw/plan 中相互冲突的表述。增加两个场景分别和旧成功并发的测试，不只断言文案，也要验证 association、门禁、代次效果和副本。

## 阻断 2：要求耗尽全历史但没有具体的有限资源及恢复策略

新增设计要求在目标缺失时继续读取至 cursor 耗尽，以识别后续乱序回跳。对超时、取消或资源限制，仅笼统要求保持未确认并可重试，没有规定谁能取消、何时停止、如何保留或安全重建进度。长会话或服务端持续产生不重复 cursor 的异常情况下，可能发生大量顺序请求而迟迟没有用户可执行的退出；若仅规定固定上限并每次从头重试，超过上限的历史也可能永远无法到达终点。

**修订要求：** 明确有限页数/时间或其他可执行预算、用户取消或离开/账号变化的处理，以及身份与已读页一致性如何保证下的续读或其他有界重查策略；不能因达到限制判作完整缺失、推进可信冲突或清除副本。增加正常超出单批预算仍可进展、异常 cursor 链有界停止、取消/换代和用户可见重试的测试。设计需如实说明跨多个 HTTP 请求没有单一数据库快照保证；如无法安全续读，应明确可恢复路径和限制，不把反复从头卡住称为完成。
