## 阻断 1：逻辑取消后的有效 401 与“不得修改任何状态”冲突

raw 第五、六节要求停止批次后旧 fetch 迟到结果不得修改任何状态，同时保留 `apiGet` 的原有 401 语义且不允许修改 API wrapper。当前 `web/src/api/client.ts` 对当前认证代次的有效 401 会主动失效认证并跳登录；即使相应业务批次已逻辑停止，该认证处理仍可发生。若实施者为满足前一句抑制有效 401，将削弱认证失效规则；若按现有 API 运行，又不满足“任何状态不变”的文字。

**修订要求：** 明确区分业务结果不能写会话、消息、checkpoint 或副本，与当前身份的有效 401 必须执行既有认证失效这一例外；已经换代的旧 401 不得使新账号失效。增加真实 API/页面测试：逻辑停止后当前代次迟到 401 的失效及恢复提示；换代后旧 401 不影响新账号；普通成功/失败迟到均不能提交业务状态。保留不物理中止 fetch 和原有 120 秒超时的事实边界。

## 阻断 2：超长历史硬限制需要与原产品目标对齐

本版设 200 页、10,000 ID 或 4 MiB 总上限，达到任一上限后对合法历史也不再允许自动核查，要求用户保留副本并联系管理员；这是明确的功能限制，不只是有界执行实现。用户此前要求退出后可随时继续对话；本报告未发现用户已授权该类永久受阻例外。计划已诚实标注限制，但不能由独立技术审查将该新产品限制视为已获用户确认。

**修订要求：** 设计一个满足原目标、在资源受限下仍提供安全进展的方案，或由主会话先准备具体可审阅的限制与替代方案，并取得用户对该产品边界的明确决策。不得为解除限制删除未确认副本、伪造消息匹配或放松其他 writer/活动门禁；若需要后端能力，依既有流程重新规划并审查。记录有效长历史、达到上限、用户继续/退出与恢复的实际行为及验证范围。

## 本版已解决的并发问题

- 已将单未决网络读取限制收窄到每个 checkpoint，允许同请求两个独立关联同时进行，保留“新冲突先于旧成功”的真实 UI 测试。source、attempt 和 operation 身份分别保留。
- 增加每请求、页面实例及 checkpoint 数量上限、可见排队和按可入场任务的 FIFO 规则；暂停后底层 fetch 在物理结束前继续计入资源额度，旧 finally 仅释放自身。两个 Provider 的额度仍是各自内存，不声称跨标签锁。
- 保留严格页序、opaque cursor、不同重复 ID 来源分类、已读数据与跨 HTTP 非原子性说明，以及异常、取消、换代和资源上限测试。
