## 阻断 1：在途 IndexedDB 事务与账号换代不具同一原子边界

计划要求逻辑停止或账号换代后旧业务结果不能写 checkpoint，又允许每页先启动 IndexedDB 事务，在事务前后再检查账号和来源。若用户换代发生在事务启动后、提交完成前，事务可能已经提交旧代 checkpoint；事后发现票据过期不能撤销已完成的本地事务。React/store 账号代次、localStorage 和 IndexedDB 没有共同事务，当前文字不足以保证“绝不发生旧写入”。

**修订要求：** 明确在何种阶段可以中止未完成事务；对于已提交或无法确认提交的旧代数据，规定无权展示、无权续用或发布 matched/冲突，并说明同用户重新认证后如何重新验证、何时可安全清理；不得误删原备份或其他 writer 数据。分别测试停止/换代发生在事务开始前、进行中、成功提交后但 UI 发布前，以及关闭/崩溃中途；验证旧代数据不会影响新账号，同时不将本机事务夸大成跨网络/跨标签原子操作。现有有效当前代次 401 例外须保留。

## 阻断 2：每页一条加逐批人工确认使长历史恢复成本过高

新计划固定 `message_limit=1`、每批最多 20 页且每批均需用户再次点击。超过 10,000 条消息的合法历史因此需要超过 10,000 次串行 HTTP 请求及至少 500 次继续操作，还要求在 UI 测试中完整走通。移除 200 页硬上限是进步，但这种实现可能形成事实上的使用障碍，也使验收难以按正常时间完成；没有给出实际性能预算或证明满足用户“随时继续对话”的体验。

**修订要求：** 明确与后端现有分页上限兼容的有界页大小、批次响应性和继续方式，并用可测的请求数及用户操作数验证 10,000 条以上的场景。可以在保留用户可停止、运行额度、公平排队、每批有界内存和原 cursor/身份验证的前提下设计可恢复的自动批次或其他具体策略；不能假称任意单条 HTTP 响应具有固定字节上限，也不能为了速度跳过消息排序、冲突、账号或副本校验。若真实服务无法满足性能，应明确证据和用户可用的替代方案。

## 已核查的修订

- 当前代次有效 401 即使关联已停止仍触发既有认证失效；旧代次 401 不得影响新账号。计划要求两种真实 API wrapper 测试，纠正了上轮认证例外。
- 去掉固定 200 页/10,000 ID/4 MiB 累计总限，按页增量暂存并区分浏览器物理配额、单响应大小、换设备和跨 HTTP 非原子性；不宣称物理存储无限。
- checkpoint 包含请求、attempt、候选来源、head、cursor、缓存版本和证据代次，重新认证后重新查询原请求并核对 snapshot；同设备明文暂存和无法跨设备直接续读均有说明。上述身份设计仍需解决事务时序问题才能形成可执行保证。
- 第六节两次独立关联、每 checkpoint 单在途及队列限制、重复 ID 分类、原始 fixture 调整与独立去重覆盖仍保留。全量回归、冻结、独立全范围代码复审和真实服务验收仍是后续门禁。
