## 阻断 1：历史连续性只覆盖普通加载，继续未关联请求仍会重置已加载页

计划任务 3 第 58–68 行和 raw 第 27–33、49–53 行聚焦 `loadSession/applySnapshot/loadOlder`。当前 `web/src/store/workspaceController.ts:682` 的 `continueUnassociated` 在消息 epoch 未变且无上翻在途时，直接将消息、cursor 和 visited 替换成最新 snapshot。用户先加载多页，再显式点击“保留未关联记录并继续”，即使没有任何并发，旧历史也会消失；若新增连续页元数据不与该入口协调，还会使数据与页链记录不一致。`confirmCompleted` 也会向显示列表合并消息并按现有旧排序规则排序，计划应确保其与新页来源、角色排序和冲突校验一致，但不能把其孤立消息当分页连续性的证明。

**修订要求：** 盘点所有写入消息、cursor、visited 的入口，把 `continueUnassociated` 纳入同一连续性契约，说明如何在不破坏活动门禁及显式继续语义的前提下保留旧页、桥接缺口、处理冲突和失败；明确 `confirmCompleted` 等合并时如何维护来源及排序。增加真实控制器/UI 用例：已上翻多页后继续未关联请求，验证历史、cursor、visited 和后续上翻；覆盖新旧页无重叠、ID 冲突及关联/活动状态，先记录业务 RED 再 GREEN。

## 阻断 2：存储失败后仅有内存副本的完成清理及退出行为未定义

raw 第 23、45–46 行要求删除并读回成功才移除相应内存项。现有批准契约允许备份写入或读回失败时提示风险后继续 POST；`web/src/store/workspaceController.ts:469-495` 将准备内容及请求先存内存，持久化可能失败，且写入返回失败也可能意味着 `setItem` 已成功但读回异常。`flushAll` 在约 452–457 行将 `prepared` 和 `localRequests` 计为未决项。方案未规定匹配完成后没有可识别持久候选时，如何消除确定已完成的内存未决状态并避免错误宣称已删除持久副本；机械执行现有规则可能使退出或切换账号持续失败。

**修订要求：** 区分可证实无对应持久项、能读到精确项和读取不完整/不确定等状态，设计完成匹配后的内存状态、告警、重试及退出路径，不以写入返回失败推断未落盘，也不误删其他 writer。以真实 Storage 接口模拟 prepared、linked、request 各写入失败、读回失败或不一致，随后正常完成并精确关联，验证继续使用、退出备份及恢复风险提示；同时覆盖其他候选不受影响。无法同时保障的边界必须明确说明，不能伪称已清理。

## 阻断 3：跨浏览器重启后的 linked 副本缺少可证实的处理出口

raw 第 25 行排除旧 writer 的副本并称仍有已有显式处理出口。但当前 `web/src/pages/Chat.tsx:36` 对 linked 副本只提供查询原请求/按原请求重试，复制按钮禁用；`web/src/store/localRecovery.ts` 的 `remove` 则拒绝非当前 writer。浏览器进程重启后 recovery 创建新 writer，旧 linked 即使查询到原请求完成并成功 matched，也没有计划列出何种现有操作能够解除该副本对发送的阻塞。不能把跨重启生成的 writer 等同于仍活动的其他页面，也不能据此推断其他页面已经停止。

**修订要求：** 明确设计已验证原请求和历史消息后对旧 writer 副本的知情处理及继续对话路径，同时保护可能仍在运行的其他页面、不同 payload/baseline 的同 ID 记录，不声称 localStorage 的读比对删具备跨页面原子性。增加从创建 linked 副本到重新初始化新 writer、查询原 ID、匹配持久消息、用户可继续的端到端自动化场景，并测试并存的其他 writer 和候选变化。方案可使用明确的保守警告和用户操作，但必须说明实际可访问出口，而不是依赖当前不存在的按钮。
