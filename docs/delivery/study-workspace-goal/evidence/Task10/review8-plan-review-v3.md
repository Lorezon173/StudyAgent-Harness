## 阻断：单请求单页读取与既定并发仲裁及测试不一致

raw 第五节和计划“预算及 checkpoint 契约”要求同一账号/session/request/attempt 同时最多一个当前页 fetch；但原任务 1 要求同一已 inconsistent 请求的第一次关联页挂起、第二次关联页先返回可信冲突、再释放第一次成功；新增重复编号的两类并发测试也依赖旧页和新页同时在途。按字面执行严格单飞，第二个请求不能在旧页挂起时发出，现有测试和证据代次的设计便不能按计划执行。反过来若允许两个关联同时读取，新增单请求并发上限又没有成立。

**修订要求：** 明确该限制是仅约束同一个 checkpoint 的后续批次，还是覆盖同一请求所有关联；依据所选语义同步修正 raw、任务 1、重复编号测试及用户交互。如果全局单飞，需说明不同 source/writer、请求 attempt 与来源失效时为何允许或禁止共享、排队与重试如何工作，并以真实 UI 请求计数证明互斥和失败后可再次核查，同时保留能证明新可信冲突不会被旧成功覆盖的有效业务或可达性证据；不能默默删除已批准的并发保护。若仅限制同一 checkpoint，则须明确独立关联的并发数量、资源预算、取消和各自来源隔离，确保旧 fetch 与新批次不能无界叠加。调整后独立复审。

## 已解决与保留的边界

- **重复 ID 分类：** 已区分同一服务端读取链内部重复为异常未完成、不推进冲突代次；合法有序页对当前可信且未改变缓存的相同 ID 异内容才是可信冲突。新增了旧成功与两类结果并发的测试。实施时须按该最终分类处理，不能将异常页当可信证据。
- **顺序和 cursor：** 验证页内及跨页元组方向，仅原样使用 opaque cursor；缺目标时需已验证的链到合法耗尽，早于耗尽的异常、超时或停止保持未确认。找到并核对完整目标后不声称未来未读页或多 HTTP 请求一致。
- **预算和 checkpoint：** 设计提出单批 20 页或 8 秒逻辑截止、总上限、显式继续与停止、身份/来源/首页和缓存版本校验，以及超限后的可见限制。设计准确说明现有 API 无外部 abort 信号，逻辑停止不等同底层 fetch 物理取消；checkpoint 也不是跨 HTTP 数据库事务快照。上述预算与并发语义协调后仍需执行边界及换代测试。
- **覆盖与验收：** 原不合法重叠页 fixture 的调整须先记录原因，同时保留可信缓存同 ID 去重和冲突保护；全量冻结、独立代码复审与真实验收门禁未变。
