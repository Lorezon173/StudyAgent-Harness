# Task12 浏览器首轮失败诊断

## 范围和结论

原始 21 项运行已终态，21 失败，原始日志和截图保留在 `playwright-original-round1/`。受控用例白屏已复现为测试夹具的请求拦截范围过宽；真实 HTTP 用例的页面已渲染，其拖动后比例不变是另一条失败链路。以下诊断均未修改源码、测试或配置，未使用原测试账号写数据。

## 受控用例白屏：已确认的夹具问题

`web/e2e/workspace-layout.spec.ts:15` 的 `page.route('**/api/**')` 同时匹配 Vite 模块路径 `/src/api/client.ts`。独立浏览器沿用原夹具、访问 `/chat/s1` 时，实际记录：

- 拦截 `GET /src/api/client.ts`；夹具末尾的未知端点分支返回 HTTP 404。
- 浏览器记录 `Failed to load resource: the server responded with a status of 404` 和 `net::ERR_ABORTED`；页面 body 为空。
- 原首例的 error-context 只报告找不到输入框；截图为空白，与模块未能加载相符。auth 的三个 localStorage key 与夹具一致，不能以 key 不匹配解释本次白屏。

最小建议：夹具只处理 pathname 以 `/api/` 开头的实际 API 请求，其他请求继续正常加载。先在计划和独立审阅后修改，再重跑验收；不能据此断言修正后其他断言必然通过。此结论不证明产品页面本身存在启动故障。

## 真实 HTTP 拖动失败：受控复现机制，原现场尚未完全证实

原真实 HTTP 组在 `workspace-layout.spec.ts:121–123` 已显示浮卡，鼠标拖动后轮询服务端 `progress_y_ratio` 仍为 0.5。原始失败快照显示浮卡已展开，但没有记录 pointer 事件目标或拖动前后的坐标，所以不能仅凭原始日志断定具体事件路径。

在独立浏览器使用内存夹具、仅调整拦截边界后，按原用例先读取收起手柄坐标，再移动鼠标到旧中心：手柄从 `x=1257.64, y=416.19, width=13.36, height=74` 变为展开后的 `x=977.64, y=245.06, width=13.36, height=416.27`。旧中心命中画像详情 div，实际 `pointerdown` 也落在该 div；没有发出比例 PATCH。此复现支持原用例的旧坐标因 hover 展开而失效，但不是原现场的事件记录。

进一步分别用有评估和待评估摘要，先 hover 展开、等待详情可见、重新读取手柄坐标后拖动：两次 `pointerdown` 均命中“调整画像位置”，`hasPointerCapture(1)` 均为 true；向下移动 60px 后手柄均移动 60px，并分别发出比例为 `0.9571428571428572`、`0.8594159490827405` 的受控 PATCH，初始值为 0.5。受控响应只证明这两种受控页面的事件和请求链，不证明真实后端持久化成功，也不覆盖全部视口及连续 hover 行为。

最小测试建议：先显式展开并等待布局稳定，再读取当前可见手柄坐标；验证实际命中、捕获及位移后，再核对真实 HTTP PATCH 和 GET。原设计允许展开时按几何重新夹取，当前证据也显示首次悬停会改变手柄位置；其对真实用户操作的影响应单独保留为交互限制候选，不能据此擅自改动产品或宣称所有拖动场景通过。
