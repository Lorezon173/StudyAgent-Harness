- [ ] 关联 checkpoint 使用 IndexedDB 分页事务持久化精确身份、source、冲突证据、元组前沿、原 cursor 与已见完整消息 DTO；续读、跨账号隔离和重启校验以第七节增补为准，不把持久化当作跨 HTTP 原子快照。

- [ ] 验证两批之间每种失效：request ID/attempt/sequence、payload/response/baseline、writer/writeId/来源内容、身份/profile、snapshot state_version、首页内容/cursor、缓存 messageEpoch 和可信冲突代次。变化时不可继续旧链；账号切换不能泄漏旧用户消息，本机读取/删除失败与其他 writer 警告不能被清空。一次中断后的完整重查能在符合预算时推进，不准重新开始后无提示地无限重复前 20 页。

## 任务 1、3、4 并发作用域增补（独立复审 v3 修订）

- [ ] **采用每个独立关联 checkpoint 单页读取，而非同一 request 全局单飞。** 两次用户“重新查询”即使属于同一个 request/attempt 和同一 source，只要配额允许也必须各自形成 operationId、source 验证和独立 checkpoint；因此任务 1 及“新重复 ID/缓存冲突先返回、旧正确页后返回”的真实 UI 交错仍可实际同时发出两次页请求。重复同一 checkpoint 的“继续”不能创建另一条同 checkpoint 读取。
- [ ] 同一 generation/user/session/request/attempt 运行或底层 fetch 未结束的关联操作至多 2 个，全页面至多 4 个，运行/排队/暂停 checkpoint 合计至多 8 个，同来源最多 2 个。每个关联每批 20 页/8 秒；无固定总历史页数/ID/字节阈值，历史数据使用 IndexedDB 增量暂存并受设备物理能力限制；不同标签独立，不声称跨标签原子性。
- [ ] 实现可见 FIFO 排队：未入场的关联不得先发 request GET/snapshot/消息页；队首受本请求 2 个名额限制时，按队列顺序选择首个可入场的其他 request，受阻队首名额释放后优先；跨批继续重新排至队尾以避免长历史独占。每个来源最多两个独立操作，第三次相同来源点击显示“已有核查”而非无限排队；8 项容量满时明确告知并允许用户停止/放弃自身 checkpoint 后再试，必须保留所有未确认请求与本地副本。只为已接收任务提供公平机会，不承诺敌对网络永不返回时绝对及时。
- [ ] 队列条目携带完整账号、session、request、attempt、payload/response/baseline 与 source kind/writer/writeId/内容；排队、入场与每批续读各自验证，来源变化时撤销该条目并保留可见警告与候选，不与其他 writer 共用 checkpoint/授权。已有 `readRequest` 可按原身份共享 in-flight GET，但每个来源必须独立核验返回与副本。证据运行序号在操作真正入场并开始有效验证时分配，按可信结果与证据代次判断，不依据排队点击先后来伪造服务端次序。
- [ ] 每 checkpoint 同时最多一个请求；手动暂停或 8 秒逻辑超时后旧 fetch 仍占额度至结束，丢弃迟到业务结果，但当前有效代 401 保留认证处理。用户暂停时等待显式继续；仅批次到时则底层请求结束后自动排队并重新验证，不叠发读取。取消队列项释放其资源，旧 finally 只能释放自身。
- [ ] 账号换代/离开时旧 checkpoint 和队列不得写新身份；旧底层 fetch 未完仍计全局 4 额度，完成后仅释放自身，用户退出不需等待；跨账号新操作等待资源时必须可见。出现相同 session/request ID 也不能复用旧 operation、source、候选、证据代次或响应。若底层请求永不服从现有超时，应显式保持等待，不虚称物理释放。
- [ ] 每个并行 checkpoint 在 UI 有可区分来源/顺序及各自的已核页数、等待、继续与停止入口；停止其中一个不触碰其他 writer 的候选、运行操作、用户草稿或已确认消息。各项关联的真实冲突/网络失败/来源失效分别显示，不能把两个来源的警告覆盖成无关统一结果。
- [ ] 真实 UI 和受控 fetch 测试并保存证据：同 request 前两个操作两个页均实际在途；新可信冲突先到、旧成功后到保持冲突和副本，反例新 503/源失效后旧成功可恢复；三个同源点击不产生第三个页链且有可见提示；两个来源占满后第三来源排队，释放一个后它按顺序入场；不同 request 在有全局余量时可并行；全局 4 满时第 5 个按上限排队，8 checkpoint 满时显示明确拒绝且无额外 fetch。
- [ ] 使用可控时钟和延迟 fetch 覆盖：停止某 checkpoint 后同 checkpoint 不重发、另一个 checkpoint 在配额内可运行；两名额均被旧挂起占用时等待，旧请求结算后队列先进项可继续；队列取消、同源与跨 writer 公平、不同 request 不饥饿、批次轮转排队、换代与旧 finally 不影响新对象。记录实际 fetch 并发峰值、累积预算、按钮和副本，禁止凭计数桩代替真实控制器/UI。
- [ ] 各 checkpoint 分页持久化各自 cursor/ID/排序前沿并可持续批次前进；仅每批和并发有界，不设永久总历史上限；不解码 cursor、不承诺跨 HTTP 原子快照。任何新增 API wrapper 或后端能力需另行规划并复审，完成后重冻、全量/构建和全范围复审。

## 任务 3、4、5 增补：401 与无固定总上限的持久续读（独立复审 v4 修订）

### 认证失效与业务取消的区分

- [ ] 停止、8 秒逻辑截止、离开或换代使旧结果无权发布业务数据及副本变化；IDB 已开始的事务可能提交，按第八节尽力 abort 并隔离、重验，不宣称绝对无旧代磁盘写入。原请求返回 401 时仍按当前 generation/user/token 处理；旧代 401 不影响新代，保留现有 120 秒超时。
- [ ] 通过真实页面、AuthProvider 和实际 API wrapper、受控延迟 fetch 测试：停止后当前代次 401 导致认证失效、跳转登录及备份成功/失败对应提示；同一 user/token 重新登录换代后旧 401 不清新身份；停止后的 200 和 503 不能改变 session、消息、checkpoint、关联、任何副本或新错误。验证旧 fetch 占用并发名额至实际结算，但不阻止用户立即离开/退出。

### 有界工作内存与无固定总页数上限

- [ ] 移除前文 200 页、10,000 ID、4 MiB 的**累计总历史上限**及“超限联系管理员才可继续”的设计；保留每批 20 页/8 秒及第六节操作并发/队列上限。累计合法历史通过 IndexedDB 按页增量持久化，不为累计页数、ID 或字节设置预先固定的永久产品阈值；用户可以继续任意多个批次直至目标得到可信关联或合法 cursor 耗尽，实际物理配额不足属于可见、可重试的环境限制。
- [ ] 关联核查使用现有 `loadSnapshot(id, 50)` 和 `loadMessages(id, { cursor, limit: 50 })`，一操作内存仅持有固定数量的页、两个目标消息、小型身份与前沿，不将所有已遍历 ID、cursor、消息装入 JS 集合或 React store；已见 ID、访问过的 opaque cursor 等在 IndexedDB 索引单条查询。实际内存上界仍受**单条 HTTP 响应自身字节大小**影响：现有 `apiGet` 先 `response.json()`，后端未提供严格内容字节上限，不能宣称任意响应绝对固定字节内存或设备永不崩溃。若需流式 JSON、服务端过滤或一致性快照，须另行设计审批，不能偷偷扩大本轮范围。
- [ ] IDB 仅作为关联暂存，不覆盖 localStorage 备份，命名空间绑定 user/session/request/attempt/operationId/source writer/writeId，不存 token。每页消息、索引与前沿在单事务写入；提交前失效尽力 abort，已提交或未知的旧数据隔离并按第八节重验，不得发布或清副本；不能承诺 IDB 与账号、网络或其他标签原子。
- [ ] 到达每批 20 页或 8 秒时显示进度，未手动暂停则公平自动排队续批；用户可暂停并继续。配额/IDB 失败明确提示重试或保留退出，恢复后从经重验的已提交前沿继续；无完整前沿提供重新开始，不删其他用户、writer 或原副本。物理设备不足和换设备本机 checkpoint 不可直接续读应如实说明。
- [ ] 目标消息来自不在当前连续历史链的较旧页时，不将整个遍历过程灌入当前 `messages`。保留原 historyIds/cursor 与已载入历史，将通过身份、排序与消息验证的真实 user/assistant 两条作为“已核对的原请求记录”独立展示（真实消息 ID，非合成），后续正常上翻到对应 ID 时去重，不伪装历史连续；原本已在连续缓存中的消息沿现有路径去重。确认/清理仅在全套验证、证据代次及来源均有效后进行，不因暂存完成就删除副本。用户可继续正常按旧 cursor 阅读历史。

### 跨批验证、重启与物理失败

- [ ] 恢复批次前真实请求 `/requests/{id}` 与 snapshot，校验当前账号、session/profile、request/attempt、persisted response、payload/baseline、完整 source 及写入标识，检查 state_version、首页内容和 cursor、缓存 messageEpoch 及关联冲突证据代次。同一账号代次比较原 messageEpoch；重启/重新登录后不可比较已重置的旧数值，应在当前代次建立新 epoch，逐条把当前恢复缓存中与已扫描 IndexedDB 记录重叠的 ID 作完整 DTO 精确比较；不能宣称未重新读取的数据已获得新证据。任一不同或来源读取失败时停止、不套用旧 cursor/页、不清副本；提示会话或本机记录变化，用户可显式放弃**本次 checkpoint**并从新快照重新核查。禁止比较/暴露其他账号的 checkpoint。
- [ ] 页面刷新/崩溃后的恢复入口只在重新认证同一用户后展示；旧 generation/token 不持久存储或复用，创建新代次后重新验证服务端 request/snapshot、head/cursor、原 baseline 与当前可读 source，以及已加载可信缓存；若 checkpoint 中已有可信冲突证据，恢复时维持冲突门禁，不能由崩溃抹去。纯内存来源在重启后无法证明的，保留原有风险提示并要求新证据；若 IndexedDB 页事务部分失败、数据缺失或被浏览器清理，只使用最后可完整验证的提交进度或提示重新开始，不能声称绝对持久。恢复/放弃 checkpoint 不影响任何原 writer 备份。
- [ ] 设计请求证据代次与 checkpoint 的并发/事务交接：两个同请求独立 checkpoint 的可信冲突在有效来源核验后与对应证据代次原子更新；旧成功提交前重新读/校验代次并进行账号/source 与当前 UI 资格核验。若崩溃发生在 IndexedDB 提交和 React/store 更新之间，恢复时从可信持久化证据保守重建或重新验证，不直接清副本或放行。不能将 IDB 内事务泛化为与服务器或其他标签 localStorage 的原子性；回归仍须测试旧失败、新冲突、其他 writer 及第六节并发限额。
- [ ] 真实 UI + 受控 fetch 测试：超过 10,000 条合法消息以每页 50 条自动多批到达目标或耗尽；统计页请求及每批身份重验、点击次数、操作内存页数和并发，验证公平及 UI 响应、暂停与继续；异常无限 cursor 每批有界且可停止。按第八节另行报告真实服务耗时与限制。
- [ ] 使用真实浏览器 IndexedDB（或将真实浏览器测试与可控存储适配器单测分别标记）验证 quota/不可用/事务中断、释放空间后续读，刷新及崩溃后重新认证恢复；验证 source 写入变更、账号换代/同 token 新代次、attempt、snapshot head、messageEpoch、冲突代次变化时拒绝旧 checkpoint。测试其他 writer 数据和用户草稿、恢复副本在全部故障/取消/重启后不被删改。
- [ ] 在实现证据与最终报告中记录存储读写实际结果、软件内存的页数边界、单响应字节/浏览器 quota 的不可保证性、跨 HTTP 非原子性及浏览器清理数据风险；不要以模拟 IndexedDB 或服务端响应冒充真实 PostgreSQL 重启、跨账号拒绝验收。完成所有变更后重新冻结源和测试、全量测试/构建，停止修改交整个 Task10 独立审查。

- [ ] 本增补属于用户此前已授权的会话恢复和消息核对范围；仅使用本地浏览器 IndexedDB 暂存，不向新增外部服务传输内容，不修改全局浏览器权限。IndexedDB 明文学习历史暂存的使用范围和物理约束须在项目文档与结果中如实说明；需要修改服务端协议或全局权限时先停止、补充三层设计并取得适用授权。
