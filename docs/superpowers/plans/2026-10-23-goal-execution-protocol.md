## 3. 批准后首次启动的固定步骤

1. 分别核对规程批准、实施计划批准、Goal明确启动三项授权，引用原始消息，不自行填“已批准”。若只批准部分范围，先更新总目标草稿，不能带着全部目标假定授权。缺任何一项都不执行下面的启动步骤。
2. 比较终稿、raw、两阶段计划和规程的SHA256与本轮待批清单；有意变更重新登记版本，无解释变更先核实。
3. 检查分支与实际git状态；HEAD允许由已登记任务提交正常前进，但分支、未解释的变更和无关提交必须核查。不得reset/clean掉原有文件。
4. 用get_goal确认没有无关活动Goal；有则汇报冲突，不清除或覆盖它。没有则create_goal一次，目标使用第1节批准正文，不设置未请求的token预算。
5. 把批准引用、批准清单、原生状态和执行时间登记到账本，当前任务设Task0。此动作不修改全局skill、hook或应用配置。
6. 装载适用的执行/代码规范技能；按优先子代理实现、主会话审阅推进。在本分支工作，若需隔离工作树先核对继承当前未提交终稿的问题，不能从remote default错误起步。
7. 自动进入Task0，不再为已批准的正常步骤逐项索取许可；工具原生审批仍正常处理。

## 4. 每个任务必须重复的十步循环

| 步骤 | 必做动作 | 必须留下的证据 |
|---|---|---|
| S1 恢复 | 读当前任务、前置完成证据、批准版本与git状态 | 当前task、HEAD、未解释变更检查 |
| S2 界定 | 列本任务允许文件、输入输出、断言与明确非目标 | 子代理任务简报，接口和文件白名单 |
| S3 先证伪 | 为新增行为写有意义失败测试并执行 | 新断言为什么失败；不能拿环境崩溃当业务红灯 |
| S4 实现 | 最小修改，例行实现细节可自行选择 | 文件diff；每项修正登记ADJ或Ruling |
| S5 验证 | 跑本任务必要检查、受影响回归、规定真实门槛 | 命令、环境、时间、退出码、实际结果 |
| S6 审查 | 新审阅者检查规格一致性和代码质量 | 审查结论、发现编号、修复与复核结果 |
| S7 同步 | 更新README、本任务契约/说明及账本 | 文档diff；与原始需求的映射 |
| S8 提交 | 审查diff，仅git add明确文件，普通commit | 提交SHA、明确文件和残留改动；不用amend |
| S9 检查点 | 确认代码/测试/审查/文档/提交均一致 | 将任务标DONE，记录下一task |
| S10 继续 | 自动选择固定顺序下一项 | 简短更新：完成证据、当前项、是否有实质阻塞 |

Task0、K0属于调查/配置决策，不编造失败测试；其S3/S5证据为对应计划中的事实核查及真实可用性结果。纯文档修正也不创建镜像实现的测试。

只在新变化、失败或未解决风险要求时扩测，不重复跑已通过且未受影响的昂贵检查。每轮应做有意义工作，不能只写“继续推进”或重复汇报相同状态。

审查发现的问题按范围修复并复核，不能以“审查者建议”为理由增产品功能。普通文件划分、内部命名、测试夹具修正自行裁决记录；改变用户契约需第6节审批。主会话从工具输出核验，不只相信子代理“完成”声明。

## 5. 账本、状态与跨轮恢复

固定目录：[docs/delivery/study-workspace-goal](../../delivery/study-workspace-goal)。

下表是未来启动后的账本要求，不要求在规程审阅阶段建立活动状态。当前progress.md仅记录文档准备，adjustments.md仅提供模板；status.json和evidence/在用户明确启动后再建立。本轮不初始化运行中的任务或任何原生Goal。

| 文件 | 用途 |
|---|---|
| status.json | 总状态索引、20任务状态、里程碑、批准清单、下一项 |
| progress.md | 逐轮追加式记录：做了什么、证据、当前HEAD和下一动作 |
| adjustments.md | ADJ变更单、裁决、用户批准或拒绝的原始引用 |
| evidence/（执行时创建） | task分目录，保存日志、截图、迁移/请求验证和审查报告 |

如subagent-driven-development创建自己的git-ignored工作目录，登记它的实际路径用于实施简报/审查材料；该技能的ledger与项目持久总账本分别按其规则维护。完成状态必须能由提交和证据核实，不能只存在于聊天或临时目录。

任务状态：PENDING→RUNNING→VERIFYING→REVIEWING→VERIFIED_UNCOMMITTED→DONE。BLOCKED表示该任务确有外部依赖，NEEDS_DECISION表示待用户实质决策；REOPENED表示新证据推翻已完成验收。它们都是项目状态，不等于原生Goal状态。

DONE的必要条件：本任务批准需求满足、必要验证通过、重大审查项关闭、README更新且有真实提交。工具阻止提交时保留VERIFIED_UNCOMMITTED，不重做已通过内容，不将它当DONE继续跳任务。若任务确实无需代码变化，保留“已等价实现”的对照、测试和本次文档/证据提交后才DONE。

每次自动续轮、上下文压缩、用户中途问状态后：

1. 读取get_goal及批准规程，确认仍是同一目标；用户新消息优先作为当前任务的调整，不丢失原任务。
2. 读取status/progress/adjustments及当前task计划，不重新遍历派发所有DONE任务。
3. 核对已完成提交存在、证据与当前代码仍适用；无需因为上下文变短就重跑全部测试。
4. 如git代码与账本冲突，以事实核实，登记REOPENED或未登记的变更，不直接覆盖文件让账本看起来正确。
5. 从固定顺序第一个未DONE项继续；若该项卡住，只推进与它无关的只读准备，不越过它提交后续功能。

### 状态索引的必填字段

启动后status.json必须包含：schema_version、protocol_version；规程批准/计划批准/启动授权三条独立reference；原生goal标识（若实际工具返回）或目标正文摘要；branch、baseline_commit、current_task；proposed_manifest与approved_manifest（文件路径、SHA256、批准版本）；20项tasks（id、status、commit、evidence、review、blocked_reason）；milestones；current_blocker、连续阻塞轮数及最近解锁条件。未知项用null，不猜测id或审批时间。

progress的每轮条目包含当前任务/步骤、实际变更、命令与证据、审查、ADJ编号、HEAD、下一动作。账本更新失败时先保留可恢复记录并诊断，不能依据已丢失状态继续推进多个任务。

## 6. 每一次调整的分类和固定流程

### A类：范围内实现修正，自动执行并事后告知

例如：修复本任务空值错误、补缺少的外键校验、调整内部函数划分、让CSS符合已批准终稿、修订明显错误路径、测试夹具补真实用户。前提是需求、公开API语义、数据含义、顺序和验收标准均不变。

每次有实质影响的修改登记ADJ编号；同一个问题的连续编辑可作为同一变更单的修订，不必为每个按键建立记录。

### B类：契约/范围变化，先做可审阅变更单再请用户批准

例如：修改画像权重含义、恢复承诺、数据库迁移语义、公开接口兼容性、任务顺序、阶段边界、依赖框架、真实服务选择/费用/数据外发，或删除/降低验收。对这类改变不能援引“持续执行”作为默认授权。

流程固定为：

1. 建ADJ-序号，写触发事实与证据，不以猜测当理由。
2. 列原规则和建议新规则，说明为什么原计划不足。
3. 列所有受影响任务、文件、API、数据/迁移和测试。
4. 写最小可行方案、替代方案、失败成本与可回退边界。
5. 给出精确验收变化；如果是在降低标准，必须显式说明。
6. 完成无需依赖该决定的只读核查，交付具体变更单供用户拍板；不先改产品再补批。
7. 获得用户明确同意后，先更新raw来源，再更新计划/规程与批准manifest；记录批准消息，旧版本记录保留。
8. 重新核对依赖与已完成任务的影响，需要重开的标REOPENED。
9. 才执行修改、验证、审查、提交，更新账本，从明确检查点继续。

如用户只批准某方案的一部分，只实施该部分；没有回复不等于同意。与所需决策无关的范围内修复可继续，但不得跳过固定任务顺序。

### C类：外部或不可逆操作，不在本次默认授权内

推送/合并/部署、生产数据迁移或删除、全局设置/权限/skill/hook变更、新的收费服务开通均需用户另行明确授权。准备可审阅内容后才询问，不用这类假设风险阻断已授权的可逆开发。

## 7. 故障、修复与停止纪律

### 普通代码失败

围绕当前任务定位→提出有证据的假设→最小修复→针对验证；不得用测试skip、吞异常或改fake响应凑绿灯。相同失败重复出现而证据没有变化时先换诊断路径；可以继续修，但每轮必须有新证据或实质修复，不无限重跑原命令。

### 平台/审批失败

同一动作每轮最多重试一次，第二次失败停止该动作；已知沙箱故障遵循AGENTS，不通过换壳/换浏览器/改ACL绕过。审批通道成功不等于普通沙箱修复。平台故障期间只推进只读诊断与文档准备，不继续堆变更操作；记录手动执行选项及解锁条件。

### 外部条件缺失

真实模型、PG、浏览器执行或搜索Provider缺失时，写明影响哪条验收、已尝试路径和用户需要提供什么。测试替身只用于测试，不代替真实验收；不将Task13、K0、K5或总验收打勾。

### 原生Goal状态约束

- active：目标未达成且仍有授权范围内的有意义工作可推进。
- paused：仅用户明确要求暂停时调用update_goal(paused)，报告工具返回后停止目标工作；不能把等待审批自行写成paused。
- blocked：相同外部阻塞在至少三个连续Goal轮次仍存在，且不能继续有意义工作，才调用update_goal(blocked)。第一次记录事实，第二次做替代/只读核查，第三次确认没有可行路径；不重复危险或被拒命令来凑轮次。被用户恢复后重新计算连续阻塞轮次。
- complete：只有第8节全部满足才可调用update_goal(complete)。任务难、超时、额度将尽、第一阶段完成或本轮文档写完都不是总目标完成。
- 额度或运行限制：服从实际限制，先尽可能写恢复检查点；不改写预算、不新建Goal规避限制，不建立cron/heartbeat绕过暂停。

确认待决问题时保留项目NEEDS_DECISION并尽可能做不依赖该决定的只读工作；若最终满足原生blocked规则才转换。用户可以随时明确暂停或取消；取消/清除按当时实际可用能力处理，不拿complete冒充取消。

## 8. 全部完成的明确标准

必须同时满足：

1. status中20个任务全DONE，所有实际调整均有记录；没有未批准实质变更，没有未登记产品文件。
2. 第一阶段真实模型多轮连续性、PG重启后恢复、persisted=true/消息/状态/证据可读、两账号拒绝、并发/幂等/失败回滚通过。
3. 第二阶段真实网络来源、本人文档解析、LLM候选、人工编辑/锁定/权重/激活冲突、重启恢复及来源定位通过；未配置Provider时不能满足。
4. 正式React经HTTP服务的浏览器视觉与交互验收通过；与终稿逐项比对，包括固定左栏、完整主区、右上入口、左下账号、A浮卡收展和纵向拖动。仅VM检查不算视觉验收。
5. 最终默认后端测试、固定版本静态检查、前端测试/构建、必要PG integration及浏览器回归通过，时间/环境/命令/结果可查；不引用其他分支的通过数。
6. 最终独立审查无未解决的严重安全、数据丢失、核心功能或验收问题；其余已接受限制记录清楚，不隐藏失败。
7. README/API/运行配置/迁移边界和交付清单一致，当前提交SHA及残留工作区改动明确。第一阶段功能在第二阶段接入后仍可用。
8. 生成最终交付报告与证据索引。先写事实结果再标总Goal complete；如果用户设置了token预算，按工具要求报告最终使用量。

本项目完成不等于上线；推送、发布与部署仍是独立授权事项。

## 9. 状态更新与用户控制

工作中简短说明当前task、刚验证的结果、下一步和必要阻塞，不用每做一项都询问“继续吗”。长命令每30秒主动检查；与用户沟通按当前会话规则及时更新，不能用长等待隐藏停滞。

里程碑报告仅列：DONE证据、当前项、剩余项、ADJ变化、所需决策。没有重要变化时不反复发送同一阻塞通知。用户询问状态先答复再继续；用户新要求若改变范围，先登记变更，不忘记原目标。

## 10. 本次需要用户拍板的五项

| 决策 | 建议批准内容 |
|---|---|
| 范围 | 两阶段20任务全部纳入总Goal，第二阶段真实来源配置未定时如实阻塞 |
| 顺序 | Task0→Task13→TaskK0→TaskK5→总验收，阶段完成自动接续 |
| 执行 | 子代理逐任务实施、新审阅者审查、主会话核验；共享文件不并发写 |
| 调整 | A类自动修正记账，B/C类先给具体变更单由用户拍板 |
| Git与边界 | 只在该分支明确文件本地提交，保留原有改动，不push/merge/部署/全局修改 |

可以只批准规程，也可以逐项修改后形成v1.1。**批准规程不等于批准实施计划，更不等于授权启动。** 未来只有用户明确表示同时批准本规程、所引用的两阶段实施计划并要求启动Goal时，才可合并登记三项授权。用户仅说“文档可以”“规程同意”，只记录规程审阅结果，不创建Goal或执行20项任务。

## 11. Goal能力来源与限制

原生工具已提供create_goal/get_goal/update_goal，本轮读取get_goal返回null。Goal是跨轮持续目标，不需要另装同名skill。规程不尝试给工具新增参数，不宣称程序关闭、系统休眠、额度耗尽时仍能保证推进。
