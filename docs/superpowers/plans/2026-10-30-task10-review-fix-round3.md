# Task10 第三轮独立代码审查修复实施计划

> 执行前：本计划及 raw 先交独立 subagent 审查，通过后按 RED → GREEN 实施；未通过先修订并复审。完成后冻结、完整回归、独立审查整个 Task10，再进行真实验收。设计来源 `superpowers/frontend-ui/task10-review-fix-round3-raw.md`；审查证据 `docs/delivery/study-workspace-goal/evidence/Task10/review2-final-product-code-review.md`；继承已批准第二轮 raw、计划和全部原门禁。

**目标：** 保留连续历史及分页前沿的同时，在桥接失败时独立处理有效快照中的画像和活动；先实际验证 POST 后查询遭后续活动观察取代是否导致准备状态卡住，只有复现后才实施该项修复。

## 范围与硬边界

- 产品白名单：`web/src/store/workspace.ts`、`web/src/store/workspaceController.ts`、必要的 `web/src/pages/Chat.tsx` 提示与查询出口；测试白名单：`web/src/pages/Chat.test.tsx`、`web/src/store/workspace.test.ts`。如果确需其他产品文件，先补充 raw 和计划并经独立审查，不擅自扩大。
- 不改后端、协议、依赖、恢复存储格式；不覆盖用户 README/资源改动，不提交或整文件暂存他人改动。检查 README 是否需更新，仅在确有用户可见功能变化时保留已有内容并最小更新，必要时先交主会话处理。
- 不把 POST 200、网络失败或 404 认定为已保存；不以删除备份、放宽活动门禁或丢弃历史来通过测试。较新活动、账号代次、请求身份和原副本清理约束优先。
- 保存每次 RED/GREEN、失败及全量回归原始日志和明确退出码，放在 `docs/delivery/study-workspace-goal/evidence/Task10/`，不要覆盖旧日志。若在运行中修改文件，该次测试不得作为冻结后的最终证据。

## 任务 1：业务复现历史桥接失败与独立领域丢失

- [ ] 在真实路由、AuthProvider、store/controller 与模拟 fetch 中，载入会话 A 已有消息链及非空旧游标；切离后返回，快照有更高画像 revision、另一 running 请求与不重叠最新页；桥接页返回 503。检查原消息、旧 cursor/已访问游标保留且展示历史错误；同时检查新画像与活动状态可见、输入和发送受保护、未发生第二次 POST。保留实际原实现 RED 和退出码，确认失败是画像/活动被丢弃，而非 mock/选择器错误。
- [ ] 补充同 ID 内容不同、无效/回环游标，以及先取得一个桥接页再失败：不发布部分历史，不误更新游标，独立领域仍按可验证规则处理。保留旧存储副本和草稿；分别检查同版本画像冲突和旧画像版本不回退。
- [ ] 对 `continueUnassociated` 构造已完成未关联请求及旧历史，刷新快照时桥接失败且新快照带更高画像与其他活动：请求仍未关联、未标记继续、不删除副本、不解除门禁，旧前沿保留，独立领域遵循有效性；再模拟成功桥接并验证继续/原游标语义。确认该测试的现有行为，不能假定所有断言必然失败。
- [ ] 交错矩阵：较新的活动观察先于旧桥接失败完成；较新的 load 先完成；切账号后旧响应到达；同会话上翻期间桥接失败；外部活动发生在等待期间。逐项检查旧状态、旧错误不覆盖新状态或泄露到新账号；无可证明安全时保持阻塞。无旧会话时显示加载错误而不是 ready。

## 任务 2：按设计修复历史失败的独立处理

- [ ] 先核验快照身份，再分离画像、活动、教学与消息历史的合并条件。抽取或调整现有函数时维持相同版本和请求合法性约束；活动仅在 epoch、观察序号仍有效时合并，旧 idle 不得清除新 running，新 running 应保守阻止输入/发送并启动合适的请求查询或轮询。
- [ ] 桥接中间页仅临时保存；失败只写适用的历史错误，保留全部旧消息、历史 ID、游标、已访问集合和正在进行的上翻；成功才提交完整可证明连续链并仅清理对应错误。画像 revision 递增及同版本冲突提示独立于历史结果；不可用或越权快照不能写任何域。
- [ ] 对 `continueUnassociated` 应用同一独立处理，但失败不得记为 continued/matched；校验账号、会话、当前请求 ID/sequence/attempt 与活动观察。不能以新活动快照强制成功继续或丢失其他 writer 副本。
- [ ] 运行任务 1 各定向测试至 GREEN 并保存结果；复核成功重试能填补缺口并沿用旧前沿，页面实际展示画像和失败提示，且不会提前解锁发送。每处错误路径保留明确提示。

## 任务 3：先验证 POST 后旧 GET 风险

- [ ] 写真实路由/控制器交错测试：完成准备和唯一一次 POST，延迟该请求的 GET；用户切出又切回同一会话，较新 snapshot 不含已完成请求，先完成新观察后释放旧 GET。控制并记录 snapshot、GET 的起止次序与观察序号对应的行为，确认旧 GET 确实遭淘汰。之后提供该请求权威 completed 状态、真实消息页与对应基线，断言无需重复 POST 即可恢复进度、正确显示服务端已保存的问答；快照消息需满足已有连续历史及关联契约。
- [ ] 在原实现运行并保留日志与退出码：若断言 RED，核查失败确是该业务卡住而非桩、数据或时序问题；若 GREEN，记录观察与原因，补做实际路径核对，不能将此风险声称为已复现，也不为它实施猜测性产品修复。若复现条件与审查推导不同，先更新计划并复审。
- [ ] 条件修复时扩展交错：新快照仍有 running、较新 attempt/已匹配先完成、原请求已替代、账号切换、另一个请求运行、复核 GET 失败/404、共享在途 GET 清理时机。确认无自动重复 POST、旧 GET 不覆写较新状态、失败保留原文和本机副本并可手动重查，不无限立即重试。完成后必须验证服务端消息确实可读且关联后才清副本；本机写入/读回/删除失败仍保留原有警告、跨 writer 精确保护。
