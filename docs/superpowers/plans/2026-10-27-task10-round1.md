## 第一层：模块总览

### 目标边界与架构

基于现有 React 18、TypeScript、Vite、React Router 与 Vitest/RTL，不引入前端状态库或新认证系统。保留一个 workspace store 的账号 generation 和 session 桶，以工作区生命周期内的控制器管理异步请求与保存队列；页面和 hook 作为该控制器的订阅/交互入口。每会话发送、加载、读取与保存各有独立序号和账号票据；切换 URL 不销毁其他会话的在途 HTTP，不允许旧账号结果回填。

`/chat/:sessionId` 是所选会话唯一真源；`/chat` 只做最近会话恢复或空态引导，不再以随机 session 发消息。登录后先读取 `/api/workspace-state` 并捕获路由/身份票据：明确会话 URL 优先，只有用户仍停留 `/chat` 且没有后续主动导航时才能 replace 到已保存 last_session_id；null 时呈现新建入口。加载失败应给重试入口，不因临时网络错误抹掉 last_session_id。主动切换保存该账号最近会话，不让旧保存晚到覆盖新选择。

后端事实：snapshot 返回 session、教学状态、最新消息页、profile/summary、view_state 和所有非 completed requests；消息分页按最新页倒序游标取旧页后组装正序；GET request 和 snapshot 会处理过期租约；POST chat 可指定 session_id、request_id、profile_id 与 expected_state_version，retry 专用接口使用 expected_attempt 和 expected_state_version。教学 state_version、界面 view_state.version、workspace.version 三种版本独立，绝不可交叉使用或以本机旧值覆盖服务端。

Task10 不重新设计学习意图路由或 Task11 画像/知识库正文，也不实现 Task12 浮卡。模型正在后台运行并不保证关闭浏览器后持续生成；超时、断线或 HTTP 200 均不等于已保存。验证消息必须来自 snapshot/messages 或明确 persisted=true 后重读的真实服务端结果。账号鉴权由既有 client 与 AuthProvider 保持，localStorage 中的草稿不含 token/密码。

### 关键不变量与 Review Focus

1. A 发起 POST 后切 B、B 编辑/发送、A 后完成：A 的结果只写 A 桶且不打断 B；换账号或同账号重新登录换 generation 后旧结果不能写回、导航或清新身份。
2. 本地输入与服务器确认分开：只有对应 PATCH 成功并匹配所保存的内容与代际，才标记该版本已保存；输入期间任何响应不能抹掉新内容或删除新备份。
3. 请求断线/超时结果未知：保存原 request_id、payload、base version，先查询现有请求；禁止因缺响应自动创建新 request_id 重发或将临时气泡记为已提交。
4. 默认路由恢复异步时用户已选择 B：旧 workspace GET 或旧 last_session PATCH 不能跳回 A；同一账号多个 workspace PATCH 必须串行且避免覆盖未来浮卡字段。
5. 用户正常退出时认证仍有效直到保存结果明确；服务端冲突、网络错误、本机存储异常均显示真实状态和可选操作，不绕过失败门禁，也不声称异常关闭时最后按键已保存。

## 第二层：子模块概述

### A. 账号与路由恢复

`useWorkspaceController()` 暴露当前 account、selectedSession、load 状态和 `selectSession(id)`、`openLastSession()`、`requestLogout()`；具体网络副作用由共享 controller 持有。首次已认证 bootstrap 读取一次 workspace state，保留 version 与 sidebar 等其他字段；严格区分未初始化、成功无 last session 和加载失败。用户显式 URL 直接获取该 session snapshot，不依赖分组首屏是否已载入该 session；403/404 显示不可访问，保留导航和账号，不把它当作其他账号的有效数据。

记录最近会话使用独立 workspace 保存队列：单飞版本化 PATCH，只提交 `last_session_id`，保留服务端其余字段；在 pending 中后续用户切换只更新队列期望值，完成后以新 version 继续最新值；409 先拉最新 workspace 并显示服务器与本机候选，由用户知情选择使用服务器值或明确以最新 version 保存本机值，不自动覆盖其他设备的 last_session_id；网络失败显示未保存并保留本机恢复候选，不覆盖其他字段。此队列与每 session view 队列独立，最终退出须等待其结果或明确提示失败。

侧栏点击 A→B 或返回浏览历史，立即以同步函数抓取 A 最新草稿/锚点至账号隔离的本机副本并发起 A flush，继续显示 B，不因 A 网络速度冻结会话切换；A 的失败保留在 A 桶并可在回到 A 或退出时重试。路由转去知识库/画像同理。恢复成功、显式选择后可刷新关联画像 summary，但不把其他会话的完整历史合并到本会话。

### B. 快照、分页及状态票据

每个 session 桶保存 `session`、`messages`（唯一真实 message.id）、`messageCursor`、`teachingState` 与 source、`profile`/summary/revision、`view` 的服务器确认版本、draft、readingAnchor、load 状态和请求记录。账号票据仍为 userId/token/generation；每次 load 用 sessionId 与单调 loadSequence；page 请求另外持 cursor/sequence。snapshot/分页只在身份及对应 sequence 仍有效时按桶归位：A→B 不阻止 A 在桶内更新，但 A 的响应不得改 B 的选择、显示或滚动；账号变更清旧账号内存。

snapshot 当前消息页 `items` 已正序；上翻调用 `loadMessages(id,{cursor,limit})`，以 message.id 去重并将旧页前置，保持既有锚点视觉位置；next_cursor 为 null 时无更多。首次 snapshot 的 viewState 不能覆盖从加载开始之后用户已输入的 draft；在加载完成前禁止未初始化 version 的保存和发送，或明确区分加载后的本地编辑。刷新/重登同账号按照服务端最近确认内容恢复，再检测同账号同会话本地较新副本并主动提示“恢复本机草稿”，用户选择前不静默覆盖服务器；其他账号不可枚举或展示该副本。

### C. 发送、未知结果和恢复请求

每个 session 允许一个在途教学请求，但不同 session 可并行。同步 busy guard 覆盖同 tick 双击。点击时先同步捕获原文与草稿编辑序号，按文末发送准备期间保护规则保留内容；提交前确保 snapshot、profile、state_version 和账号有效，创建一次 request_id，记录原文、profile、base version、可信发送前 next_turn_index 与账户票据；`POST /api/chat` 只携当前真实 session_id、profile_id、request_id、expected_state_version 与原文。UI 显示可区分的临时提问和“处理中”，临时项不得加入真实消息数组或模型历史。

HTTP `completed` 只有 persisted===true、请求/会话 ID 匹配且状态可用时，再加载当前 snapshot/messages 以取得真实消息 ID、教学状态及 profile revision，按 message.id 去重，不用返回文本冒充已提交消息。`running`/`failed`/`interrupted` 均来自真实 request 记录；snapshot 可包含多个非 completed 历史请求，应按 request_id 单独显示，不只取第一项。失败/中断气泡保留原始 `request_payload.message`，提供明确重试；重试仅对对应 failed/interrupted 调用 `/retry`，携最新真实 attempt 和当前 state version，后台校验原 base version。`stale_context` 明示上下文已变化，提供“复制原文到输入框”供用户主动新提问，不偷换 request_id 或自动再生成。

POST 网络中断、当前 client 120 秒 timeout 或响应丢失时标记“结果待确认”，先 GET 同 session/request；404 表示尚未查到而不是断言失败，保留同 payload/ID 和本机待确认记录；可显式按原 ID 原 payload 重查/重发，不自动换 ID。`running` 低频查询（例如 3 秒一次，单 request 单飞）；结束/退出/身份切换清 timer 并忽略旧结果。租约到期交服务端 GET 恢复后显示 interrupted；不声称请求跨浏览器关闭仍后台生成。当前 client 超时如需延长必须为教学请求单次显式选项、其余客户端保持原 120 秒，并测试不会超出服务端真实语义；也可以保留120秒并采用上述未知结果恢复。

未知结果的本机持久记录单独以 user_id/session_id/request_id 索引，保存原 message、profile_id、base_state_version、可信基线 next_turn_index（未知时显式为 null）、基线来源/身份与状态，不含 token；发送前需尽力写入该记录，若浏览器存储不可用则明确提示本机恢复不可用，服务器 request_payload 仍可能存在但不能承诺此前未领取的请求可恢复。重登后必须先经本人 session snapshot 确认所有权，再根据 request_id 查询服务器，只有以 v1.2 可证明的基线确认完成并取得对应真实消息后才能删除对应记录。用户允许保留本机草稿退出时，对尚未确认请求也应保留该记录，不能仅备份输入框后宣称请求已保存。

### D. 草稿、阅读锚点、冲突与退出

`useDraftPersistence(sessionId)` 返回 `{draft, readingAnchor, saveStatus, error, setDraft, setReadingAnchor, flush, retry, recoverLocalDraft}`。仅保存可序列化字段与 confirmed view version；`setDraft` 同步更新 session 桶、本机副本，500ms 防抖启动服务器 PATCH；`setReadingAnchor` 将实际可见消息 ID 与 0–1 偏移转为锚点，最多每 1000ms 发一次 PATCH（尾随值必须补存），切换/退出时强制 flush。不存在真实消息时锚点为 null；无效ID不得被伪造发送。视觉滚动恢复等 DOM 渲染结束再执行，并防止旧 session 的布局回调移动当前会话。

每 session 有独立串行单飞保存队列，带 `view_version`、mutation sequence 和待保存值；每次完成先更新服务器确认 version，再检查 snapshot 与当前编辑序号，仅相同内容/序号可标记已保存并删除匹配的本机副本；有新编辑继续以最新version串行保存。429/5xx/网络错误保留草稿和恢复副本并标示未保存；409 不静默覆盖，先保本机原文并显示冲突，由用户选择读取服务器版本或在明确知情下用当前最新服务端 version 重试本人草稿；自动重试不能在未知版本下覆盖另设备输入。

本地副本使用固定命名空间 + user_id + session_id + 本文档 v1.1 定义的 writer_id，值包含唯一 write_id、schema、draft、reading_anchor、对应服务器基础 version 和本机修改序号，不保存认证 token。只有用户同账号登录并且有该会话的服务器所有权后方可读取或提示恢复；退出保留必要副本，其他账号不列出。不使用敏感信息打印或将草稿/真实会话证据提交到 Git。storage 读写失败时显式告知本机副本不可用；不能给“保留本机”成功承诺。恢复选项不得覆盖用户已开始的新编辑。

正常退出由 WorkspaceLayout 接入异步 `requestLogout`，先同步冻结输入并捕获所有有未确认更改的桶与 workspace 更新，flush 所有队列，再根据每一项结果确定：全部服务端确认后调用原 auth.logout；失败时留在页面，提供重试或“退出并保留本机草稿”；仅成功创建可用的本机副本后才允许后者，其他无法本机保存的修改需明确指出且不能假称已保留。仍在生成的教学请求不冒称已完成；退出过程不得以旧 401 清除新登录。认证过期/401 仍走立即失效，不等待已无法鉴权的 PATCH；在旧桶清空前同步尝试保底，若本机存储不可用按 v1.1 的失败提示执行，不能声称已保存。

强关/刷新时只在同步事件中写当前账号本机副本，不依赖 unload 异步网络必达。服务器只保证最近确认版本，本机副本仅在浏览器允许写入且实际成功时可恢复；不说“最后按键保证保存”。

## 第三层：子模块详细实施计划

### 1. 数据结构和原子状态操作

- `beginSessionLoad(id) → AsyncTicket`、`applySessionResult(ticket,patch) → boolean` 沿用统一 generation；明确新增 page、save、workspace load/save 各自序号，不能让同一 load 的晚 snapshot 覆盖已经完成的新请求。必要时补 `loadEpoch` 与本机 revision 保护；后台快照更新时保留较新本地字段。
- 每桶新增真实 snapshot/游标、各 request_id 的 status/attempt/base/message 与可信 next_turn_index 基线及其来源、未知结果、viewVersion、draftRevision、confirmedDraft/anchor、saveError、pendingSaveVersion 和可恢复副本标记。状态值区分 idle/loading/ready/error、dirty/saving/saved/conflict/error、running/completed/failed/interrupted/unknown；枚举映射以实际后端为准，未知状态明确展示而非当成功。
- 对外新增 `applySnapshot(ticket,snapshot) → boolean`、`appendOlderMessages(ticket,page) → boolean`、`setDraft(id,text) → void`、`setAnchor(id,anchor) → void`、`beginSave(id) → ticket|null`、`finishSave(ticket,view) → boolean`、`markSaveFailure(ticket,error) → boolean` 等纯状态动作。输入均包含/绑定账号和 session，完成只更新本人对应桶。视具体实现函数可微调名称，但作用、输入输出及不变量必须保留，不能直接在页面做跨账号副作用。

### 2. 控制器和路由

- 账号 mount 执行 `initializeWorkspace(ticket,routeEpoch) → Promise<void>`，先验证路由 epoch 再导航；snapshot 加载 `loadSession(id,ticket) → Promise<void>` 同时核 session owner/profile 与响应 ID，`loadOlder(id,cursor,ticket) → Promise<void>` 保护滚动锚点和游标。
- `selectSession(id) → void` 在离开前同步保底当前本机副本并启动 flush，再更新 URL；注册共享 `flushAll(reason) → Promise<result>`，返回每桶和 workspace 已确认/失败/本机可用事实，不以页面卸载自动判成功。管理所有计时器与请求序号；StrictMode 重挂、移除监听和账号切换必须幂等。
- `restoreLastSession()` 仅在 `/chat` 且路由 epoch 没变时执行，失败/403/404 区分展示；`updateLastSession(id|null)` 使用串行版本队列，保证最新导航最终生效且不覆盖其他 workspace 偏好。

### 3. 请求发送及恢复

- `sendMessage(sessionId,text) → Promise<void>` 严格校验有效身份、非空长度≤4000、同一一致性快照的 state_version/next_turn_index 与当前桶未占用；稳定生成 UUID/ID，绑定 payload、可信回合基线与请求票据。无网络或返回 `persisted!==true` 不插入已保存消息；无效返回或身份/请求不匹配为明确错误。
- `reconcileRequest(sessionId,requestId) → Promise<void>` 使用 GET 接口核所有权、attempt、status、租约与 response；running 单飞轮询并在页面/账号生命周期结束清理；completed 以 snapshot 重读为准，failed/interrupted 保留临时气泡，404/网络错误保持 unknown，用户可重查并仅在明确操作时复用原 ID/原 payload。
- `retryRequest(sessionId,requestId) → Promise<void>` 严格使用后端专用 retry 和请求当前 attempt/expected_state_version；`copyStaleRequest(sessionId,requestId) → void` 仅把用户自己点击选择的原文放回草稿，不清新编辑、不隐式发起新请求。旧 finally 不解除新的请求 busy；结果按 request sequence 和 account ticket 丢弃。

### 4. 草稿与退出实现

- `writeLocalDraft(identity,sessionId,writerId,snapshot) → success|failure`、`readLocalDrafts(identity,sessionId) → candidates`、`removeMatchingLocalDraft(identity,sessionId,writerId,writeId,contentHash) → void`：owner/session/writer 明确匹配、schema 验证、仅匹配完整写入身份和内容清理；不能枚举其他用户数据或使用名称作为身份。
- `enqueueViewSave(id,kind,value) → void` 和 `flush(id) → Promise<result>` 聚合最新 draft/anchor、严格串行expected version，500ms/1000ms 定时器分别触发；每轮提交快照及返回版本绑定 ticket，本地有新编辑时继续保留 dirty；冲突/网络/storage 失败显示具体状态。
- `requestLogout() → Promise<result>` 串行校验本次账户仍当前、聚合所有 pending save，并按上节显示选择；`logoutAfterLocalBackup()` 仅在所有本地备份成功后清认证。无保存数据的退出不伪造状态；401同步本机保底后立即失效，不能等待鉴权接口成功。

### 第二层增量：子模块契约

#### 1. 身份变更的同步快照与 401

- 将认证变更入口统一到 store 提供的 `prepareAccountTransition(oldTicket, reason) → BackupReport` 与 `transitionAccount(nextIdentity, oldTicket, reason, policy) → TransitionResult`。前者输入旧身份/原因、同步复制所有 dirty session 草稿/锚点、未确认请求及最新 pending workspace last_session_id，输出每项成功/失败及可保留事实；不得捕获 token 写入本机。`isCurrent(oldTicket)` 必须在读取/备份前验证；过期 401 或旧续体直接返回 stale，不备份也不清当前身份。控制器在此前已同步将 pending 数据写入 store；本函数可直接读 store 和纯 `localRecovery` 模块，不依赖 React effect 注册状态或网络请求。
- 在 `startAccount`/`clearAccount`（含 `bootstrapAccount` 实际不同身份的分支）统一入口内，在 `emptyState` 发布之前执行上述同步保底；避免遗漏旁路。`AuthProvider.login` 对主动换账号、同用户重登使用 `reason=explicit_login`：若旧身份有尚未确认的数据且无法建立对应本机副本，则返回可辨识的失败结果，保持旧账号和桶、在当前页面明确展示备份失败，不继续登录副作用或导航。无旧未确认数据可正常切换；成功后 generation 推进、旧账号 localStorage 清理/新 token 写入与 React auth 同步。`Login.submit` 必须检查返回结果再 navigate，保持 Task9 自有成功的清 busy→login→navigate 和普通错误/旧续体屏障，不能先错误跳转。非用户主动的认证失效则应用下段，不复用阻塞策略。
- 当前保护请求 401 继续由 `client.ts` 先核完整 ticket/旧 localStorage 指纹；有效时由 Provider logout 或无 Provider 的 fallback 进入同一个 `reason=forced_401` 同步备份路径。必须在同步备份尝试完成后立即 `clearAccount`、清认证并换代，**即使**存储写入失败也不能保留失效凭证或假称保存；保留未含个人内容的失败标记供用户可见。对非 `/login` 原本硬跳转路径，在失败时使用仅含固定状态标记、不含草稿/用户名/凭证的登录 URL，例如 `?localRecovery=failed`，目标 Login 页面显示“本机恢复副本未保存，未确认内容可能丢失”；成功时常规跳转。若仍在 `/login`，通过认证状态同步公开相同警告，不依赖已经销毁的 workspace 桶。导航失败时在当前 UI 报告失败状态。硬跳转不是 `beforeunload` 服务器成功的证明。
- 注册/卸载：备份函数是 store/纯存储模块的稳定同步入口，非 component 的单次 effect 监听；AuthProvider 与 controller 在 StrictMode setup→cleanup→setup 只管理订阅/计时器，不重新生成身份或重复覆盖副本；每次真正的显式登录必须换代。只有统一 transition 可清桶；旧 API 的对外方法/测试按明确返回值同步调整，不允许使用没有预备阶段的旧 `clearAccount` 分支。

#### 2. 同一 request 的跨来源单调合并

- 每个 `(generation,session_id,request_id)` 有 `attempt`、`serverStatus`、`observationSequence`、`completedResponseVersion`、`messagesConfirmed`、`pendingPayload`；本地 `unknown` 是观察不足，不是可覆盖后端终态的事实。`mergeRequestObservation(ticket,source,observation) → applied|ignored|inconsistent` 校验 user/session/request、profile、原始 payload、attempt、sequence，再执行以下规则；相同消息 ID 去重不等价于请求合并。
- attempt 只允许持平或增大，低 attempt 所有 snapshot/GET/POST 响应一律忽略。更高 attempt 必须来自服务端权威观察，不能由本地点击臆增；普通 POST 的更高 attempt failed/interrupted 是待 GET 复核的候选，详见 v1.2；新 attempt 的 running 可替代旧 attempt 的 failed/interrupted。服务器 `ChatRequestStore.retry` 只允许 failed/interrupted→attempt+1→running；状态不符合或冲突时显示真实 409 并刷新，而非强制递增。
- 同 attempt 下 running 可前进为 failed/interrupted/completed；一旦服务端终态被接受，旧 running、404 或仅缺失该请求的旧 snapshot 不得降级/复活。failed 与 interrupted 如收到同 attempt 互相矛盾的权威响应，标 `inconsistent`、停止重试并提示重新查询，不能凭到达顺序猜测覆盖。completed 必须匹配 request/session/attempt、真实 `persisted=true` 且有效 response version；进入 `completed_pending_messages`，停止轮询并发起最新 snapshot/messages 核对。快照版本至少为该 response 的 state_version；按 v1.2 可信发送前 next_turn_index 精确分页关联该回合，不能靠文本猜测。已认证 GET 完成与消息关联是两种状态；无法建立可信关联时必须保留副本并明确提示，且按 v1.2 的显式处理提供继续发送出口，不能无限锁住。completed 的相同 attempt 不能被任何后续 running/failed/interrupted 回退；来自旧 loadSequence 的 snapshot 只能合并独立且可证明更新的数据，不得用其 pending 列表替换已完成表。
- 不依赖全局 loadSequence 代替 request 的版本栅栏：捕获每次发出的 poll/snapshot 序号与 attempt，先检查统一请求表的最新 attempt/终态。保留响应源及 server version 供诊断；已确认完成但 UI 补消息失败时显示“回复已保存，正在同步/重试”，既不重复发模型也不伪造消息。

#### 3. 同账号多标签的本机版本

- `localRecovery` 为每个顶层页面文档生成一次随机 `writer_id`（使用 `crypto.randomUUID()` 或同等不可碰撞随机值），不从可被浏览器复制到新标签的 sessionStorage 继承；同一文档内 StrictMode 重挂复用，刷新后生成新 writer。每次实际写入生成唯一 `write_id`；候选值结构含 `schema_version`、数值 user_id、session_id、writer_id、write_id、单文档 mutation sequence、base view version、原草稿、锚点和可验证的内容快照/摘要，不含 token/密码。key 使用固定命名空间及经过严格编码的 user/session/writer；同一文档可覆盖自己的旧版本，但各标签有独立 key，另一标签不能覆盖。
- 服务端 PATCH 发出时捕获完整 `{owner,session,writer_id,write_id,mutation_sequence,base_version,exact_content}`；响应成功且身份、序号、内容均匹配时，只删除**该 writer**且仍与原 write_id 和完整内容一致的项。删除前同步读取比较，不因两个标签各自 revision=1 而删除另一标签；不清其他 writer 或刚发生的更改。已确认值与当前本机值不同仍继续保存最新编辑。
- `listLocalDraftCandidates(identity,sessionId) → candidate[]` 仅枚举该数值 user_id 与 session_id 命名空间，先完成服务器所有权确认，再将多个候选及各自本机写入时间/版本展示供用户逐个选择或忽略；不能默认按最大时间覆盖服务器/当前编辑，也不能跨账号扫描/展示。若尚有旧版 `namespace+user_id+session_id` 单键，则按归属和 schema 验证为独立 legacy 候选，成功写入新 writer 唯一身份或用户明确选择后才清旧键；若无旧键不制造迁移。未知请求备份同样增加 writer_id + request_id，恢复时同 request_id 不同 writer 只合并内容一致项，内容冲突保留候选并提示。
- 本机操作捕获 quota/security/序列化错误，每项单独记录成功/失败，不假设存储可用；清理只能在明确确认或用户选择后作用于自身匹配副本，不自动批量清除其他标签。localStorage 候选是便利备份而非私密隔离容器；UI 在登录后按账号过滤，无法把同一操作系统浏览器上的物理存储当作跨用户加密保护。

#### 4. 最近会话与工作区本机候选

- 增设 `workspaceCandidate` 独立 key：namespace + user_id + writer_id，值含 schema、user_id、writer_id、write_id、route mutation sequence、pending_last_session_id（可明确为 null）、base workspace version 和修改时间，不含 token。`setLastSession` 同步记录最后期望值并备份，再放入单飞 PATCH 队列；A→B→C 中旧 B 返回仅推进**该请求**的已确认 version，若当前期望仍为 C 则保持 C dirty 并以最新服务端 version 继续。若 B 失败而 C 已变更，失败回调不能用 B 覆盖 C 本机候选。
- workspace PATCH 网络失败、409 或 in-flight，退出 `flushAll` 的结果必须同时列出 workspace 项和所有 view/request 项。全部服务器确认后正常退出；选择“退出并保留本机”前，**workspace 候选和全部未确认桶/请求**都必须完成有效本机写入并可读回匹配 write_id；任一失败则禁止声称已保留、保留认证和页面供重试。可用副本保留跨会话 B/C、基础版本与失败事实，不能把 session draft 写入成功代替 workspace 写入成功。
- 重登/强关恢复先取当前账号 server workspace、列出该账号的 workspace candidates，逐候选验证 schema 与 user；候选目标非 null 时通过本人 session snapshot 验证所有权，403/404 给出不可恢复提示并保留候选，不导航或自动写服务器。用户显式 URL/已主动导航永远优先，不因迟到恢复候选而跳转。若服务器 version/last_session 已变化，展示服务器与各本机候选，由用户选择只在本机打开目标，或明确用最新 version 更新服务器；不能静默覆盖别的标签/设备。确认服务器接受且当前候选 write_id/内容未变，才清本 writer 对应候选。强关只写本机候选，不承诺服务器保存。

#### 5. 全路径离开与网络边界

- 侧栏、`onCreated` 程序导航和页面内部链接通过同一个 `leaveSession(oldId,reason)`，先同步捕获/备份，再触发后台 flush；React Router 监听 location 变更覆盖浏览器 back/forward 及外部可见的 SPA 导航。back/pop 无法在事件发生前保证异步阻塞：依靠输入时同步 store/本机副本保证最近已成功写入值，location 变化的 layout 阶段捕获旧桶并启动 flush，旧桶在共享控制器中保留。显式 logout 则冻结输入并等待所有 flush。beforeunload/pagehide 仅尽力同步写本机，不等待、不声称网络请求成功；UI 不把强关期间动作写成服务端已保存。
- `withCurrentTicket` 检查完整 userId/token/generation 以及捕获时认证 localStorage 指纹；每个延迟、timer、每个 `await` 后，在发下一个 GET/PATCH/POST/retry **之前**重新检查；身份变化立即停止续体和后续网络调用。client 发请求时从当前 localStorage 读 token，因此只丢弃晚响应不够，禁止将旧 A 的 payload 用 B 的 token 发出；同账号同 token 换 generation 也视为失效。必要的同步检查不改 backend 语义。
- 404 后允许用户显式重查或同 ID/原 payload 重发；同一个 `(account,session,request_id)` 的查与重发由同步 busyRef/sequence 串行协调，连点不会并发两个重发。若首次 POST 已在后台领取，后续同 ID 同 payload 依后端 claim 返回现有状态，绝不额外生成新 ID；`payload_conflict` 表示原 ID 对应内容不符并保留本地原文、不得自动重发，`session_busy` 显示其他活动请求并查询/刷新，`stale_context` 提供用户主动复制为新草稿。查询或重发过程中身份变化立即停止下个网络动作。重发不将原请求凭空标 completed。

### 第三层增量：明确测试与验收

## v1.2：attempt 终态与已提交消息关联的范围复审修订

来源：`docs/delivery/study-workspace-goal/evidence/Task10/round1-plan-review-v1.1.md`；v1.1 原稿 SHA256 `5abee737871741dcdd81e52cad9df7b282254910b889d0b530f9d9318f746b57` 已由主会话归档。原四项阻断与三项并发建议均在独立审查中设计层 ADDRESSED；下列两项补齐真实后端契约。v1.2 与先前文字有差异时以本节和同步修订的正文为准；只改计划，须独立范围复审 PASS 后才可编码。

### 第一层增量：事实、边界与可信依据

- `ChatRequestStore.interrupt` 将正在运行的 attempt N 改为 failed/interrupted 时，同时递增为 N+1 以围栏旧执行；因此普通 `POST /api/chat` 的正常 HTTP 200 可以返回 `persisted=false`、failed/interrupted、attempt N+1。`retry` 随后只对 failed/interrupted 的当前 attempt 再递增；旧的 POST 可能晚于新 retry 结束，不能依据先后覆盖新代事实。后端 `GET /sessions/{id}/requests/{request_id}` 返回归属、原 payload、base、attempt、status；snapshot 读取同会话的未完成请求并先恢复到期租约。
- `commit_turn` 在持有用户 session 和 request 状态栅栏的事务中，取 `session.next_turn_index` 写入一对 user/assistant 消息，再与教学状态、request completed 一起提交并将 next_turn_index/state_version 各递增。`uq_message_turn` 保证同 session、turn_index、role 唯一；但公开 `ChatResponse`、`RequestSnapshot.response_json`、消息 DTO 均没有 request→turn_index/message_id 的直接字段。`turn_count` 是教学提交轮数，不等于任意 legacy 数据的消息 turn_index。不得修改后端 DTO/事务来假装现有证据更强，也不得凭相同文本、当前 next_turn_index、turn_count 或时间戳猜测关联。
- 对本控制器创建或从一个仍在运行的**一致性 snapshot**可信观察到的请求，保存同时满足账号/会话/request/base/active lock 条件的发送前/占用时 next_turn_index，才能在 completed 后通过真实分页和该回合的用户/助手一对消息证实关联。对旧记录、其他设备或缺失/损坏本机记录而无法建立可信基线的情况，后端确实可以证明 request completed，**不能由此证明具体消息关联**；UI 必须展示两种事实，提供安全的继续使用出口，保留本机候选。该限制不缩减 Task10 的消息恢复：实际历史仍须真实分页读取及显示，只是不承诺该条旧请求与某回合无歧义匹配。

### 第二层增量：普通 POST 返回更高 attempt 的权威复核

`handlePostObservation(ticket,response) → accepted|candidate|stale|unknown` 在任意后续网络调用前后核 userId、token、generation、sessionId、requestId、request sequence 以及发送时原始 payload/base。初次 POST 的 attempt N 返回 failed/interrupted、attempt N+1 时，不把它判为 malformed，也不把 persisted=false 当成功：保持原临时内容，记录**候选** attempt/status，停止基于该候选自动重试，排队调用同 request 的 `GET /sessions/{id}/requests/{request_id}`。身份和当前 sequence 在发 GET 前以及返回后均重验；若该 POST 的 attempt 低于已经接受的 retry/GET attempt，直接丢弃且不发多余 GET。

GET 的 RequestSnapshot 需校验当前账号所有权、session_id、request_id、profile_id、原始 message、active_node_id 和 base_state_version 与请求身份一致，再按 authoritative attempt/status 合并：若确认为 N+1 failed/interrupted，展示对应状态并解锁**显式专用 retry**（retry 输入实际 expected_attempt 与当前 state_version）；若 GET 已观察到 N+2 running/更高 attempt 或 completed，采用新的权威事实，不让旧 POST 覆盖。GET 404、网络失败或认证票据失效保持 unknown/可重查，不因一次失败永久隐藏恢复操作；401 则仍由 v1.1 规则同步备份并失效。执行期间身份变化不得发 GET；GET 后若变代不得写新账号状态或启动下一请求。

真正相同 attempt 的 running→终态、终态不回退及相矛盾终态的保护仍沿用 v1.1。更高 attempt 的 failed/interrupted 来自 POST 时先复核；更高 attempt 的可信 GET/snapshot 或用户发起的 retry 服务端结果才能推动状态，不能本地猜测加一。接收 GET N+1 failed 后马上发 retry N+2 时，即使旧 POST N+1 随后到达，也不能回到 failed 或清理 N+2 busy。

### 第二层增量：有可信基线的消息关联

新增 `RequestTurnBaseline`：`{ owner_user_id, session_id, request_id, profile_id, active_node_id, base_state_version, expected_turn_index, provenance, snapshot_sequence }`；其中 `expected_turn_index` 是严格非负整数，`provenance` 为 `before_submit` 或 `observed_running_snapshot`，绑定当前账号但不保存认证 token。配套保留原始 user message、payload 精确身份、writer_id/write_id 与序号；前述字段写入 session 桶和未知请求本机候选，便于同账号重登恢复。对于可靠基线缺失、记录格式旧版或字段不一致，设 `baseline=null` 与可解释的 reason，禁止用 0、`turn_count` 或下一轮当前索引补齐。

#### 本控制器发送

`captureSubmitBaseline(snapshot,ticket,requestId,message) → baseline|error` 从**单次服务器一致性 snapshot**同一 `session` 对象取得 `session_id`、`user_id`、`profile_id`、`active_node_id`、`state_version`、`next_turn_index` 与 `active_request_id`；核本人有效 ticket、owner/id 与当前 URL/桶一致、profile 属于该 session、version/index 为合法值、`active_request_id===null`、无当前未确认状态。以该 snapshot 的 state_version 作为 POST expected_state_version，next_turn_index 原样作为预期回合并绑定刚生成的 request ID 和原 payload；任何本地复用的 snapshot 需核 sequence、账号 generation 和当前桶版本仍一致，否则先刷新 snapshot 并在每个 await 后重新核身份与路由/请求序号。发送前先持久化该基线及原文（失败时沿用 v1.1 的可恢复能力明确告警），再调用 POST。不得先创建 ID 后读取另一版 snapshot 把不同版本任意拼接。

snapshot 后其他标签先提交、改变活动节点或占用会话时，服务端 claim 的 version 校验或 active_request_id 占用返回 `stale_context`/`session_busy`；本地不能把其他请求占用的预期 turn 当作自己成功，必须刷新真实 snapshot，保留该请求原文并依现有冲突 UI 由用户决策，不在未知状态自动换 ID。若跨标签同 version 竞争，只有被 session 原子 claim 的 request 可以进入对应事务；并发失败的一方不能以基线等于别人的 turn 或相同文本当成功证据。若本请求经 failed/interrupted→retry，只有权威 GET 对该 request 的 payload/base 一致且服务端仍允许基于同一 state_version retry 时，原基线可继续使用；状态已推进则 stale_context，绝不重用旧基线。

#### 观察其他设备正在运行的请求

在本人经鉴权的 `SessionSnapshot` 内，只有当 `session.user_id` 等于当前 user、`session.session_id` 与目标匹配，`session.active_request_id===pending.request_id`，该 pending 同 user/session/profile/active_node、status `running`、`pending.base_state_version===session.state_version` 且 session 的 next_turn_index 有效时，才能把**同一 snapshot**中的 index 作为 `observed_running_snapshot` 可信基线；绑定 pending 原始 message、request_id、base 与 attempt，记录来源和 snapshot sequence。不能将不同 GET 与 snapshot 混拼，也不能对 failed/interrupted、非活动请求或不同 base 推算观察基线。后续 attempt 提升或重试前必须重新用权威 request 确认原 payload/base 未改变；一旦冲突则撤销关联基线、保留候选与说明。snapshot 在响应途中变旧并不自行证明消息已经提交，后续完成仍需要 request GET/POST 权威终态和新 snapshot 的版本/消息确认。此路径没有本机原发送记录也可以安全取得**实际已占用请求**的未来分配值；除此之外不得猜测旧请求索引。

#### completed 后的精确查找与解锁

`confirmCommittedTurn(ticket,request,baseline,response) → matched|unassociated|loading_error`：先核当前账号/session/request、服务端权威 completed、response 的 `persisted===true`、response/session/request/attempt 一致、response.state_version 为合法版本且严格等于 `base_state_version+1`（commit_turn 在该请求事务内恰好递增一次）；GET 的 request payload、profile、node、base 与 baseline 完整一致。用最新本人 snapshot 核同 session/owner 和 `session.state_version>=response.state_version`；按后端正序 items 与 cursor 逐页前翻；目标回合的 user 和 assistant 可能跨页，继续直到两者均已取得，或下一页已越过目标回合、或 cursor 耗尽时才判定缺失。网络中断保持未确认，不得据此判缺失。要同时找到该索引恰好一个 role=user 和一个 role=assistant（数据库唯一约束提供保证，客户端遇到异常重复视为 invalid），其内容分别等于原始 request_payload.message 和已保存 response.reply，且均为该会话真实消息，才标 `association=matched`；合并 message.id 去重并保留页序。即使多个其他回合的提问和回答完全相同，也只以可信 index 定位，不用内容搜索冒充 request 映射。

当匹配成功，才关闭**该请求**临时气泡、删除满足 owner/session/request/writer/write_id 和完整内容条件的 unknown 本机副本。若基线可信但分页网络错误、页面尚未载到目标或 snapshot 版本落后，则保留副本并展示“服务器已完成，消息关联尚未确认”，用户可重读；不得合成消息或删除备份。若已读完整页仍缺角色/内容不一致、响应版本异常、请求身份不匹配则 `association=inconsistent`，保留证据、提示重试或检查，不能降为匹配。

对于用户后来新打开设备、旧版记录无 next_turn_index、本机记录损坏或记录由其他设备提交后才被观察且未捕获一致 active snapshot 的 completed：认证 GET 与 response 可以证明**请求已完成及持久化**，最新 snapshot/分页可以展示该 session 的真实历史，但 `association=unassociated`，显示“请求已完成，无法确定其对应历史消息；历史已按服务器内容显示”，保留本机候选供人工处理；不能由文本/时间/当前 next_turn_index/turn_count 猜出“对应此消息”，不能自动清未知副本或伪装为 matched。为避免无限锁住：提供“保留未关联记录并继续”明确操作；再次取得本人最新 snapshot，核 `active_request_id===null`、状态版本和账号票据无误后，解除该 terminal request 对**新发送**的本地互斥，但保留 unassociated 标记、历史与所有未知副本（用户主动发新请求走新 ID 和新 snapshot 基线）。如服务器仍有活动 request、刷新失败或认证失效，不能声称已解锁，提供重查/恢复；该出口只针对服务端已确认 completed 的请求，不允许绕过仍 running/unknown 的并发占用。

## v1.2 补充：发送准备期间的原文保护

用户点击发送的同步事件中，`beginSendPreparation(sessionId)` 捕获当前账号 ticket、session_id、**完整原文**、当前 draft 编辑序号和发送准备序号，立即同步保留 A 桶原草稿及账号/session/writer 隔离的本机副本；本机存储失败按既有策略提示，保留内存值，不假称可跨强关恢复。同步双击守卫从此时生效。准备 snapshot 的 await 期间，**不清输入框，不删除草稿副本，不将该问题当作已提交消息**；原文与序号只属于 A，不读取或修改 B。

采用保守方案：snapshot 尚在准备时若 A→B（包括浏览器前后退或程序导航），该次准备序号失效且不发 POST；返回 A 时，在没有后续编辑的情形继续显示原草稿及“未发送，可重试”；snapshot 请求失败同样保留并提示可重试。若切走或准备期间 A 的草稿又被编辑，保留 A 的最新编辑及其更高序号，不用旧点击内容覆盖；同时为原点击保存独立的待重试候选（与草稿/请求副本分开，绑定 account/session/准备序号及原文），用户可显式选择复制或重试该原文，不能清除后续编辑。账号换代时依 v1.1 身份前同步备份，旧续体不发请求、不触及新账号。

仅当准备返回后仍为原账号 generation、原会话和原准备序号，且已按 v1.2 从同一一致性 snapshot 确认基线并建立该 request 的副本时，才发送该会话 POST。**清草稿时机：**只有当前同一 request 通过本人已验证的 RequestSnapshot 或 GET 请求查询，证明已领取（running、failed、interrupted 或 completed），并核对服务端 request_payload 的身份和原文，才能清除输入框；ChatResponse 本身不含 request_payload，单凭 POST 200 不能清除；清除前比较草稿当前编辑序号与捕获序号、全文与捕获原文均一致，任一不同则保留新编辑。保留该 request 独立副本及临时气泡直至 v1.2 的精确消息关联确认；GET 404、网络错误、发送状态 unknown 或 snapshot 准备失败时绝不清原草稿。成功清除旧草稿时仅清匹配当前 writer/write_id/内容的草稿副本，不能误删新的输入或其他标签副本。

- [ ] 用真实 Provider/MemoryRouter 与 deferred fetch：A 输入原文并点击发送，snapshot pending 时切 B；分别释放 A 的 snapshot 成功与失败，确认 A 均未发 POST、B 输入与消息不变；回 A 原文与原编辑序号仍存在并可显式重试，A 的准备锁已释放且错误/未发送提示真实。
- [ ] 同样序列中在 A 点击后产生一次新编辑（不同内容/更高序号），再切 B 并释放 snapshot；返回 A 显示新编辑且旧点击原文作为独立可恢复候选，旧完成/失败均不能覆盖或清除新编辑，不能发送给 B。
- [ ] A 准备成功、未切换并发 POST 后：GET/响应 confirmed running 或 terminal 且 payload 匹配，仅原编辑序号与全文仍匹配时清旧输入；对照 404、unknown、网络失败和准备失败都不清。POST/GET 等待期间用户在 A 输入新内容，旧请求后续完成不能清新内容、本机新 write_id 或 B 的数据；账号变更后旧续体的下一次网络调用数为零。


## v1.3：准备态候选的可恢复性和清输入证据

来源：独立范围复审 `docs/delivery/study-workspace-goal/evidence/Task10/round1-plan-review-v1.2.md`；原版 SHA256 c89a8fba9053a7fb76074a5da11167b90b31bb4d4473e0c31bf27b57bb8f922d 已归档。以下精化之前规则，发生冲突以本节及已同步替换的正文为准。

### 第一层：目标与边界

发送准备态的原点击内容是独立、可丢失的用户数据；与当前可编辑草稿、已发 request 和工作区候选并列参与保存门禁。继续复用本机 localRecovery、统一账号 generation 和真实 API；不引入后端变更或 Task11/12 功能。服务器请求身份无法验证时不清输入、不伪造确认。

### 第二层：候选与清输入契约

1. 准备候选以 namespace/user_id/session_id/writer_id/prepare_id 编码成专用键，每次写入独立 write_id。值包括 schema、user_id、session_id、writer_id、write_id、prepare_id、初次点击原文、捕获的草稿编辑序号、更新时间与必要状态，不含 token、密码或任意账号的凭据；输入经长度/schema/所有权校验。不同标签和同标签不同准备操作不得相互覆盖；不使用纯文本搜索或局部序号判定同一候选。
2. 点击 A 发送同步捕获候选并尝试写可读回副本；此后同会话新编辑 Y 作为独立草稿保存，原点击 X 保留为准备候选。所有路由离开、同步账号切换前 `prepareAccountTransition`、401 清认证前、`flushAll`、正常退出及 beforeunload/pagehide 将候选纳入快照与备份报告。账号失效必须立即清认证：备份失败以无敏感内容的固定提示标明，不能阻止401；主动换账号或“退出并保留本机”要求所有未确认候选和草稿写入且读回成功，否则不清认证、不声称已保留。强关只尽力同步保存，失败不能承诺恢复。
3. `writePreparedCandidate(identity,sessionId,writerId,prepareId,value) → success|failure` 同步持久化并检验读回；`listPreparedCandidates(identity,sessionId) → candidates` 在当前账号成功通过该 session 的服务端所有权校验后按 user/session 命名空间枚举；`removePreparedCandidate(identity,sessionId,writerId,prepareId,writeId,content) → boolean` 仅在完全一致且该候选被用户明确处理或真实 request 成功接管并创建独立请求副本后清理。不同账号、writer、prepareId、writeId 或更新后的内容均不得清除。重登后以两个独立候选呈现原点击 X 和新草稿 Y，用户选择恢复或忽略，未经选择不静默覆盖任一端。storage quota/security/损坏逐项如实提示，不丢弃其他可用候选。
4. 清除输入前必须取得可信 `RequestSnapshot`：它来自与当前 account ticket 匹配的 `GET /sessions/{id}/requests/{request_id}` 或先前经账号/session/request完整核验且仍适用的同一 snapshot；验证 `request_payload.message/profile_id/active_node_id/base_state_version` 与已固定原请求一致，且服务端状态为 running 或可信终态。`ChatResponse` 不包含 request_payload，POST 200、persisted 或非空回复本身不能证明payload匹配；GET失败、404、账号变更或返回不匹配时保留原草稿和对应本机记录，显示待确认并可重查。即使GET匹配也先比较原草稿序号、完整文本和当前writer/write_id，不能清新编辑或其他标签副本。

### 第三层：可验证步骤

- [ ] 真实 Provider + 共享 Storage + deferred fetch：A点击 X，准备未完成时编辑为 Y，切 B 后分别触发有效401和正常退出；同账号重登、服务器校验 A session 归属后，X准备候选与Y草稿各自可选恢复，B账号不可查看；若X或Y本地写失败，401仍立即失效并显示固定警告，主动退出/换账号不能声称保留或清认证。断言不覆盖相同账号不同writer副本。
- [ ] 原 POST 返回200/completed/persisted=true，但GET RequestSnapshot暂时失败、404或返回payload不一致：输入框及匹配备份不得清除，显示待确认；后续本人GET返回完整相同payload且对应状态有效时，只有未被编辑的原X可清，已输入Y仍保留。POST 200本身不作为payload证明；旧账号GET晚到不能清新账号内容。
- [ ] 两个候选以不同写入标识分别完成/删除、重复点击及两个标签交错，清理一个不影响另一个；损坏/配额异常不得把未保存候选标成功。保留原v1.2跨页消息、版本严格匹配及A→B准备中失败/成功断言，最后复核所有原验收门槛。
