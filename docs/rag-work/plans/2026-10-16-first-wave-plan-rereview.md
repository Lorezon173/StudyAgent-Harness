## T04：兼容回归命令缺少独立离线保证（P1）

**位置：** [plan 步骤 15，第 146 行](2026-10-16-t04-execution-plan.md)，并对照其“不要求 T02 先实现”约束。

步骤 15 直接运行既有 `test_knowledge_ingestion.py`。该文件的 `test_ingest_file_indexes_chunk_documents` 在第 52 行直接构造 `RAGCoordinator()`，其他摄入成功用例也有相同构造；当前没有模块级固定 fake 后端的 fixture。`app/infrastructure/rag/coordinator.py` 第 95～98 行按 settings.rag_backend 装配 PgVectorProvider，而配置可来自环境和 `.env`。

因此，当本机为 pgvector 且 T02 尚未交付离线 fixture 时，这条“兼容回归”会进入产品 embedding/数据库路径。计划中的“若 T02/T03 正在改文件则等待稳定交接”只处理并发改动，不能覆盖 T02 未开始、被阻断或暂停的情况。T04 自身新增测试的 IO 陷阱也不会自动覆盖另一个测试模块。

**受控核验：** 临时将后端设为 pgvector，在 EmbeddingService.embed_many 入口设置抛错陷阱，再通过真实 KnowledgeIngestionService 与 RAGCoordinator 处理合成 TXT。陷阱被调用一次，输入数为 1；实际外部请求为 0、数据库连接为 0。该结果确认外部服务边界可达，没有运行真实服务或证明发生实际写库。

**建议修改：** T04 的独立验收只运行本包纯逻辑用例；把跨包旧用例组合回归明确移到主控集成阶段，由主控在离线隔离和版本稳定后执行。若保留步骤 15，则必须先给出覆盖全部所列测试的可执行隔离机制和验证证据，不能只写“默认 fake”，也不能暗中把 T02 完成增加为 T04 全包硬前置。

**关闭条件：** 在 backend 原本为 pgvector、T02 新接口/fixture 尚不存在的基线上，T04 独立验收仍可执行；所有外部 embedding、LLM、非允许数据库连接均被确定阻断。组合回归的负责者、触发条件和证据入口单独明确。

## T02：数量与维度正确不足以证明逐项向量对应（P2）

**位置：** [EmbeddingService 设计，第 61 行；实施步骤 1.3，第 108 行](2026-10-16-t02-execution-plan.md)。

计划要求每批检查 SDK 响应数量，再映射回非空输入位置；未定义响应 item.index 的语义、有效性和重排规则。当前 `app/infrastructure/rag/embedding.py` 第 89 行直接按 response.data 顺序取向量，第 96 行按输入顺序回填。已安装 SDK 的 `openai/types/embedding.py` 第 21 行提供 index 字段，说明为 embedding 在列表中的索引。

**受控核验：** 两个非空输入；注入纯内存 SDK 替身，返回两条一维有限向量，顺序为 index=1 的 [2.0]、index=0 的 [1.0]，绑定维度也设为 1。现实现返回 [[2.0],[1.0]]，按 index 对应应为 [[1.0],[2.0]]。数量、维度与有限性检查均无法发现这类错配；没有发出外部请求。

这是受控响应下的事实，不是当前真实服务已乱序的证据。风险是兼容服务或畸形响应保持数量正确时，文档与向量静默错配，而且后续清单/计数仍可能一致。

**建议修改：** 在本包定义每批 index 对应规则：非 bool 整数、唯一且完整覆盖 0 至 batch_size-1；按 index 对应输入，或对不符合明确约定顺序的响应安全拒绝。缺失、重复、越界及错误类型均拒绝，再恢复原非空输入位置。现有 FakeEmbeddingItem 默认 index=0，旧多条 fixture 也须同步赋予合法索引，不能只加新用例。

**关闭条件：** 增乱序、重复、缺失、越界、bool 索引、多批次及夹杂空输入的用例；合法响应逐项对应，非法响应在 provider 首次 insert 前失败。不改冻结公开签名或引入 T04 运行依赖。

## T03：runner 对完整但矛盾的 judge 结果缺少验收用例（P2）

**位置：** [metrics 验证器，第 94 行；runner 验收用例，第 144 行](2026-10-16-t03-execution-plan.md)。

生产端 `_collect_judge_scores` 已明确按任一 available=false 设置 judge_degraded，这部分设计正确。runner 是另一个防御边界：其验证器列出单项 value/available/reason 一致和 degraded 等价关系，却未明确检查 judge_degraded 与三个 available 的汇总等价关系；6.1 主要列缺 schema、缺键、bool、NaN 等坏结构。

反例是：健康检索、机械分数合法、所有必需键齐全，三个 judge 值均 null/available=false/reason=unavailable，但 judge_degraded=false 且 degraded=false。此时单项与类型合法，`degraded = judge_degraded or 检索异常` 也成立；若没有汇总关系校验，runner 可能把 20 个这样的受控结果标成 completed，与冻结契约 D1/D2 冲突。

**证据边界：** 这是计划未显式闭合的验收缺口。该验证器尚未实现，本次没有将此反例宣称为已复现的运行时缺陷，也没有把正确的生产端设计判错。

**建议修改：** 明确验证 `judge_degraded` 等价于任一 judge 项不可用，顶层三个 judge 值与对应 judge_scores.value 一致，并继续验证 degraded 关系。增加“完整合法外形但标志矛盾”的 FakeAgent 用例，而不只测试缺字段；不接受矛盾结果来生成 completed。坏 metrics 按既定 D2 合成安全失败项、计数并停止，不新增错误码。

**关闭条件：** 三项不可用却声明未降级、单项不可用却声明未降级、顶层值与子项值不一致均被拒绝；反向误标也按等价关系拒绝。合法 0 和合法负 answer_relevancy 继续有效，真实 judge 不可用的健康 20 题仍为 completed_judge_degraded。
