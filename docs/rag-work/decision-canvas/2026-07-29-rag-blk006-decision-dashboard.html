0. 三分钟决策摘要

BLK-006 解决什么

用户提问 → 检索 → 检索"成功"了，但：
  · 后端其实跑的是 fake（字符匹配），不是真向量检索
  · 或者 provider 全挂了，却被当成"没搜到"
  · 或者异常把 SQL/连接串泄进了事件 payload
→ Tutor 拿到一份"看似有证据、实则不可信"的结果

BLK-006 让检索的结果状态可区分、后端真实性可强制、失败信息不泄密。它是"真实结果与评测"支柱的地基——没有它，Phase 5 baseline 和 Phase 6 grounded answer 都建立在无法分辨真伪的结果上。

为什么现在决策

  • BLK-004（DEC-005/006）已固化 identity 与 range，证据"是谁、从哪来"有了；
  • DEC-003 已冻结 EvidenceProjection 含 retrieval_status 与 safe_summary，但这两个字段取什么值、装什么内容还没定义——正是 BLK-006 要冻结的；
  • DEC-004 要求 empty/failed/Critic 无输出仍产生受控回复，前提是能判定当前是 empty 还是 failed，而这恰是当前代码做不到的。

当前只需判断三件事

待确认推荐为什么与上层目标有关现在不决定的后果
production 后端校验在线 composition 入口显式要求 pgvector + PostgreSQL，不满足 fail-fast防止生产静默跑 fake 被当真能力baseline/E2E 可能测到 fake 还以为通过
outcome 状态枚举{ok, empty, degraded, failed, invalid-request} 五态让"没数据/部分降级/全挂/非法请求"可区分Tutor 无法据状态走受控降级，落入空回复
安全摘要边界payload 只放分类错误码 + 安全摘要；原始异常只进内部日志防止 SQL/连接串/堆栈泄进事件链与 Tutor安全风险 + 评测无法按失败类型分类

5. 决策一：production 后端校验

为什么必须做这个选择

config.py:21 默认 fake，coordinator.py:54-84 不校验。如果生产环境漏配 rag_backend=pgvector，或 DB 误连 SQLite，系统会静默跑假检索/字符匹配，而 Phase 5 baseline 和 Phase 6 E2E 都可能把它当真能力通过。

A：在线 composition 入口显式校验 + fail-fast（推荐）B：全局启动即校验禁 fakeC：不加校验，靠文档约定
做法在线装配 Retriever 时要求 provider class=PgVectorProvider 且 dialect=postgresql；不满足抛错进程启动时若非测试环境就禁用 fake仅在部署文档写"生产要配 pgvector"
保护范围精确覆盖在线热路径全局，但误伤测试/本地开发无强制力
fake/SQLite 是否仍可用是，仅在非在线路径（测试、bench）保留否，需大量改测试是
漏配后果立即失败，可发现启动失败静默跑假，不可发现
实施代价需定义"在线 composition 入口"边界需区分环境、改大量 fixture零
适用目标正式产品链强约束但笨重不可靠

推荐裁决 D-006-1：选择 A。

  • 在线生产 composition（/api/chat、/api/chat/stream 装配的 Retriever 链）必须显式注入 PgVectorProvider，并在装配点校验 rag_backend=="pgvector" 且运行时 dialect 为 postgresql；不满足则 fail-fast，不进入检索。
  • fake、SQLite、多源（OCR/Code）在非在线路径（单元测试、集成测试、离线 bench）继续保留，不受限。
  • 禁止在线路径静默回退 fake；禁止"pgvector 不可用时悄悄用 fake 顶上"。

选择原因：fake/SQLite 是测试刚需，不能全局禁（B 代价过大且误伤）；但在线热路径必须强制真后端（C 无强制力）。A 把"强制"精确落在在线 composition 边界，既保护生产又不破坏测试。

Warning

"在线 composition 入口"的精确代码落点（assembly/依赖注入）由 RAG-C 在 spec 里定义；本决策只冻结"必须校验、必须 fail-fast、不静默回退"。

6. 决策二：outcome 状态归约

为什么必须做这个选择

retriever.py:80-85 只有 empty/low_score/ok，加上失败路径硬编码 timeout。DEC-003 冻结的 EvidenceProjection.retrieval_status 取值、DEC-004 的"empty/failed 受控回复"都需要一个可判定的状态枚举。

候选枚举语义代价
A：{ok, empty, degraded, failed, invalid-request}，low_score 并入 ok 的质量子标记（推荐）ok=正常；empty=真无数据；degraded=部分降级；failed=全挂；invalid-request=非法5 态，清晰；low_score 不占独立状态位
B：保留 low_score 为独立第六态区分"有但分低"状态空间膨胀，且 low_score 本质是质量代理（归 Critic）
C：只加 failed，不区分 degraded最小改动部分 provider 失败与全挂混淆，降级不可观测

推荐裁决 D-006-2：选择 A。

outcome 五态精确定义：

ok               真实 provider 正常返回，有结果
empty            真实 provider 正常返回，无结果（真没数据）
degraded         部分基础设施降级：多 provider 部分失败 / SQLite 字符匹配降级 / embedding 降级但仍可用
failed           全部 provider 失败或基础设施异常（DB 连不上、embedding 服务挂）
invalid-request  缺认证身份 / 无授权 scope / 无效 query（衔接 DEC-001 fail closed，不检索）
  • low_score 不作为独立 outcome 态，降为 ok 的质量子标记（quality: low/acceptable），语义质量继续归 Critic。
  • degraded 必须可观测：哪些 provider 失败、是否走了降级路径，进 sources_used 与内部日志，安全摘要对外。
  • invalid-request 在检索入口拦截（衔接 DEC-001），不进入 provider 调用。

选择原因：A 既满足 DEC-004"区分 empty/failed"的硬要求，又让"部分降级"可观测（C 做不到），还不让质量代理（low_score）污染状态空间（B 的代价）。

7. 决策三：安全摘要与 provider 异常传播

为什么必须做这个选择

retriever.py:58 "reason": str(exc) 把原始异常字符串直接放进 RetrievalFailed payload，会沿事件链流到 Orchestrator、Tutor、API。同时 coordinator.py:111-117 吞掉所有异常，使 failed 无法产生。

A：分类错误码 + 安全摘要对外，原始异常只进日志（推荐）B：保留 str(exc) 但截断C：完全不透出失败信息
对外 payload固定错误码集合（如 backend_unavailable/embedding_failed/db_error）+ 一句安全摘要str(exc)[:N]无 reason
安全性不含 SQL/连接串/堆栈仍可能泄露片段最安全
可诊断性内部日志保留完整异常；外部可按码分类部分无法分类失败
实施代价需定义错误码集合 + 摘要模板小但失去可观测性

推荐裁决 D-006-3：选择 A。

  • RetrievalFailed / EvidenceProjection.safe_summary 只允许出现分类错误码与预定义安全摘要，禁止 str(exc)、SQL、连接串、堆栈进入 payload。
  • coordinator.py:111-117 的 except Exception: continue 改造为：记录失败 provider 与异常（进内部日志），并据此判定 degraded（部分失败）或 failed（全部失败），不再静默吞没。
  • 原始异常、SQL、连接串、堆栈只进结构化内部日志（含 trace_id/retrieval_id 关联），不进事件 payload、不进 Tutor、不进 API 响应。
  • 错误码集合与摘要文案由 RAG-C 在 spec 里枚举（如 backend_unavailable、embedding_failed、db_error、invalid_request），本决策只冻结"分类码+安全摘要对外、原始异常对内"的边界。

选择原因：安全与可诊断性不矛盾——原始异常留内部、分类码对外，既不泄密又能按类型排查（B 仍有泄露风险，C 失去可观测性）。
