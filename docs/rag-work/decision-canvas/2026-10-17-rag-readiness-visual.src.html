这页帮你决定下一步做什么

当前结论：基础接口的一批实现已经验收，但还没有证据证明整套流程能在真实数据库和模型服务上跑通。现在可以同时做两件事：修订执行计划中的问题，以及补齐真实运行所需的文件和资源。

你的选择：确定使用哪个书籍版本、怎样准备运行环境和专用数据库、采用哪种模型版本绑定方式。具体的技术修补由执行计划处理；你不用逐条判断数据库事务或锁的实现。

页面里的“未通过”是什么意思：缺少对应验收证据，并不等于已完成的代码全部无效。比如“0 / 6 道门通过”说的是真实链路相关关卡状态，不是项目完成度为零。

按这四步使用页面
  1. 先看结论图：上路是修计划，下路是准备资源，两路可以并行。汇合后仍要按每道关卡自己的前置条件验证。
  2. 再看“缺口与选择”：找到你关心的缺口，展开“事实、规则、影响与全部方案”。先看不补齐会影响什么，再比较选项。
  3. 有疑问时查依据：点带 ↗ 的原文按钮，查看具体文件和条款。代码默认配置、历史声明和实际测量是不同证据，页面已分别标出。
  4. 最后记录决定：在“加入草案”下拉框选择路线，去“决策草案”下载 Markdown。把草案发回当前对话，说明希望执行哪些选择；网页本身只记录，不会安装依赖、连接数据库或运行任务。

例子：如果你能提供此前使用的同一版本 EPUB，先给 INV-01 选择“提供同一版本的本地源文件”。这只表示准备沿此路线推进；仍需核对文件实际内容的 SHA，不能把选择当作文件已验收。

图形、颜色和数字分别表示什么
矩形
一个任务或待准备的条件。标题说做什么，下面的小字说范围或依赖。
虚线矩形
仍待实施、核验或闭合的部分。虚线不表示可跳过，也不表示没有代码。
菱形 G
验收检查点。前置工作完成并提供合格证据后，才能放行。
箭头
按箭头文字理解。在“验收依赖”图中表示硬前置；首图只概括两路汇合，不替代详细依赖图。
蓝色强调
提示当前阅读重点，不代表验收通过。状态以“已验收”“待核验”“未放行”等文字为准。
⊠ 已确认缺口 / ◇ 待核验
前者已有证据确认某项缺失或不满足；后者尚无足够证据判断能力。待核验不能直接当成不可用。

8 类缺口，分别需要决定什么
页面编号白话解释与决策重点
INV-01 · 原书以前登记的是另一台机器上的 EPUB 路径，本机文件还没核对。决定提供同一版本，还是换版本后重建基线。
INV-02 · 正文语料检索需要的本地正文文件在登记位置缺失。决定恢复原语料，还是从核准的原书重新抽取。
INV-03 · 题集20 题文件和标签存在，但答案依据是否对应实际原书、语料仍未完整核验。原书不变可保留题集待复核；版本变化需重审。
INV-04 · 运行环境当前 Python 环境与锁文件有版本差异，部分库未找到发行元数据。决定建立完整可复现环境，还是先补主链必需依赖；锁定所有版本是建议，不是 spec 逐包强制。
INV-05 · 数据库尚未取得可信登记，无法确认要连接哪一个专用 PostgreSQL 实例、用途和目标。决定准备或登记专用资源，之后再核验。
INV-06 · 写入保护需要证明“谁能写、何时能写、评测时是否阻止改动”。先修相关计划，再验证真实账号和互斥机制；填写声明不能替代保护。
INV-07 · 向量模型尚未核验实际使用的模型服务、版本、参数与索引是否一致。优先考虑可信固定版本；使用不固定别名也有契约允许的路线，但要披露限制。
INV-08 · 验证方式已有离线历史结果不等于当前真实环境通过。决定按任务分别做离线验证、数据库验证和真实评测；允许降级的 judge 评分不能掩盖检索失败。
T、G、P、spec 等缩写对照表

T 是工作包，G 是验收关卡，INV 是盘点缺口，RV2 是审阅问题。它们不是同一套编号。例如，T08 是摄入程序工作包，INV-08 是验证方式缺口；数字相同不表示它们互相对应。

任务编号做什么
T00归档并冻结共享接口和验收约定。
T01只读盘点环境、文件和资源；盘点完成不代表资源就绪。
T02 / T03 / T04分别处理写入确认、评测状态与指标、证明结构与模型指纹。三包已通过此前实现验收。
T05迁移前确认操作的是批准的数据库目标，并明确事务责任。
T06实现在线链路所需的种子、路由和投影等离线可开发部分。
T07在真实 PostgreSQL 中验证事务、权限及相关机制。
T08正式摄入程序：记录意图、执行写入并支持只读恢复判断。
T09把真实评测的准入检查、上下文和报告接起来。
T10补齐日志关联、歧义行审计和错误分类。
T11实际摄入这本书，核对产物并生成证明。
T12执行本书真实 20 题基线，并人工复核。
T13验证真实在线双入口、指纹和当前轮授权证据消费。
T14联合验收、回归并交接 MVP。
关卡通过后能证明什么
G1共享基础能力与相关集成的可信性回归通过。
G2真实数据库环境的相关检查通过。
G3实际索引与正式摄入证明一致。
G4本书 20 题基线达到有效 20、失败 0、未跑 0 的要求。
G5在线流程实际消费当前轮的授权证据。
G6在 G4、G5 后完成联合验收与交接，MVP 完成。
P1 / P2
本轮审阅的问题优先级。P1 优先修关键边界；P2 同轮闭合契约。两类都需按审阅意见修订；P2 不代表直接忽略。
DEC / raw / spec / DAG
分别为已确认业务决策、原始详细规划、冻结规范、任务依赖图。页面展示的是它们的约束与追溯关系，不是四份可以任意选用的方案。
PG / corpus / embedding
分别指 PostgreSQL 数据库、本地正文语料、把文本转换成向量的模型服务。向量用于检索相近内容。
SHA / 指纹
SHA 用于核对文件内容；模型指纹用于核对模型身份和参数。两者解决不同的一致性问题。
writer / baseline / judge
分别指数据库写入者、固定条件下的评测基线、模型辅助评分器。judge 部分评分可按契约降级，检索主链仍必须健康。
现在推荐的推进顺序：先修 T05 的目标与事务问题及 T09 的实际目标绑定；接着闭合 T08 的持久占用、账号与跨包保护协议；再补 UUID 和装配顺序。与此同时准备原书、语料、运行环境和可信资源登记。修订后的计划仍需复核，再按详细 DAG 推进实施与验收。
