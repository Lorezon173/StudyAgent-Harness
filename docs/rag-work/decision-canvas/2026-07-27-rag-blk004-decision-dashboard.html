0. 三分钟决策摘要

我们最终想得到什么

用户提出问题
  → 只检索该用户有权查看的正式产品知识
  → 找到可回查来源的证据块
  → 证据只进入当前这次检索和当前 Tutor 回复
  → 返回一次受控、grounded 的教学回答
  → 能区分“没召回 / 基础设施失败 / 生成失败”，并留下可审计证明

RAG Foundation 当前阶段的最终验收点不是“向量库里有数据”或“跑出了 RAGAS 分数”，而是 Phase 6 能在真实 /api/chat 与 /api/chat/stream 中验证有权限、可追溯、因果隔离的 grounded answer。阶段定义见 docs/rag-work/plans/2026-07-27-rag-foundation-execution-order.md:216-232。

BLK-004 为什么值得现在决策

BLK-004 为每条产品证据建立“出生证明”：它来自哪份文档、哪次切块规则、原文什么范围、检索回来后是否还是同一块。

如果不先冻结这层：

  • 正式摄入无法证明“计划写入的块”和“数据库里的块”是同一批；
  • Retriever 找到的内容无法稳定回查到产品知识源；
  • RAG-D 只能用文本包含关系做弱代理，不能做严格 identity 对齐；
  • Tutor 即使拿到了 evidence，也无法审计证据是否来自当前正式索引；
  • A/B/C/D 可能各自发明不同 ID，后续集成时再返工。

当前只需判断两件事

待确认推荐为什么与上层目标有关现在不决定的后果
chunk_id 存储位置新增 SQL 顶层可空列，暂不唯一让数据库、检索结果、attestation 能围绕同一 identity 核验provenance 继续藏在任意 JSON，Phase 2 的正式契约无法收口
range 坐标语义0-based + Unicode code point + 半开 [start,end)让不同实现能从规范文本复算 chunk 范围stable ID 的 hash 输入仍有歧义，RAG-B 不能提交可靠测试向量
Warning

同意这两项不等于同意最终 hash 算法，也不等于承诺幂等。canonical bytes 与测试向量仍需 RAG-B 补证后再次复核。

ID / locator生命周期回答的问题不能替代什么
source_sha256原始输入文件“输入字节是哪一份？”不能定位某个 chunk
doc_id规范文档“这是哪份逻辑文档？”不能标识文档内的具体证据块
chunk_id特定 normalizer/chunking 版本下的 chunk“检索和评测看到的是哪一块？”不等于数据库 row ID，也不自动提供幂等
source_locator来源格式定位“人到哪里复核？”不作为跨格式稳定主键
ingestion_run_id单次摄入运行“这批数据由哪次运行写入？”不能替代内容 identity
retrieval_id单次逻辑检索“这批 evidence 属于哪个问题？”不能替代 doc_id/chunk_id
parent_id相邻事件因果“这个事件直接由谁产生？”不能表达文档或检索单元身份
benchmark paragraph_id黄金集定位“人工 gold 在 benchmark corpus 哪里？”不能成为 production identity

这张分工表解释了为什么 BLK-004 不能用既有 retrieval_id、数据库自增 ID 或 benchmark paragraph_id 简化掉：它们回答的是不同问题。

4. RAG 子框架全景：模块、职责与 BLK-004 的位置

BLK-004 不是孤立的“表里加字段”，它落在 RAG 子框架的「证据身份段」上。这一节先给子框架本身的完整设计与真实状态，再标出 BLK-004 覆盖的边界。

4.1 子框架是什么、怎么分层

RAG 子框架的任务是把「文件 → 文本 → 块 → 向量 → 检索证据 → 当前 Tutor 回复」串成一条可信产品链。按项目四层架构，它横跨三层（docs/rag-work/specs/2026-07-24-project-chunking-service-spec.md:91-112）：

  • Infrastructure 层：Extractor / EmbeddingService / Provider / Store——只做机械的抽取、向量化、存取；
  • Harness 层：ChunkingService——纯服务，无 IO、不认证、不写库；
  • Orchestration / Agents 层：KnowledgeIngestionService（摄入薄编排）、RetrieverAgent（机械检索）、Orchestrator（evidence 进入 Tutor 的唯一投影边界）。

主控判断

若你的目标确实是“真实、有权限、可追溯的 grounded answer，并能被正式 baseline 与 E2E 审计”，BLK-004 是必要基础，不是局部优化。

若你的实际目标只是“先让单本书能搜到相似文本做演示”，则本方案偏重；可以选择 metadata-only 的临时方案，但只能诚实标为 prototype，不能满足当前 Phase 4–6 的正式验收口径。

9. 决策一：chunk_id 放在哪里？

为什么必须做这个选择

当前表只有顶层 doc_id，而 chunk identity 若长期仅存在自由形态 JSON 中，数据库无法稳定查询、约束或直接核验它。Phase 4 要核对 doc/chunk provenance，Phase 5/6 要引用真实 evidence，因此现在需要先决定正式存储边界。

A：新增 SQL 顶层 chunk_id（推荐）B：仅放 metadata_jsonC：暂不持久化 chunk_id
做法migration 增加可空列；正式协议通过后新摄入必填；暂不唯一继续只在 JSON 中保存只用自增 id 或 chunk_index
上层收益DB、检索、attestation、评测共享同一 identity 面能保存，但审计与查询契约弱最快得到 prototype
实施影响migration、模型、Provider、PG/SQLite fixture 与测试同步Provider 校验 JSON 必填与一致性无 migration
风险bytes 协议冻结前不能填临时 production 值字段易缺失、重命名或被 metadata 覆盖无法可靠回查同一 chunk
幂等承诺无；重复导入仍可追加无无
适用目标正式产品链过渡性内部实现演示原型

推荐裁决 D-004-1：选择 A，但分两步实施。

  1. 现在批准 chunk_id 成为 vector_chunks 的独立、可空顶层 provenance 列；不加唯一约束、不改变 Gate 0 append-only 语义。
  2. canonical bytes/range 和测试向量通过主控复核后，新摄入正式 chunk 才必须写入稳定 chunk_id；此前不得用临时 hash、row ID 或 chunk_index 填充并宣称 production stable ID。

选择原因：把“可审计的存储槽位”与“最终 hash 算法”分开冻结。这样既不提前固化错误算法，又避免核心 identity 永久藏在任意 JSON 中。

10. 决策二：range 使用什么基线？

为什么必须做这个选择

即使 hash 字段顺序固定，如果实现者对“第几个字符”和“结束位置是否包含”理解不同，相同 chunk 仍会生成不同 ID。range 语义必须先于测试向量冻结。

A：0-based Unicode code point、半开 [start,end)（推荐）B：1-based、闭区间 [start,end]C：只保存 chunk_index / 格式 locator
切片复算可直接使用 text[start:end]需要 +1/-1 转换无法精确复算
空范围 / 相邻块天然表示；A.end == B.start需要额外规则无统一规则
Unicode 单位明确 code point，不依赖 UTF-8 byte/tokenizer仍需另约定单位各格式自行解释
跨格式element index + element 内 offset 可统一可实现但转换更多locator 难统一
文档影响修订现有“闭区间”草案与草案表面一致放弃可复算 stable ID
适用目标正式产品链可实现但更易边界出错仅人工定位/原型

推荐裁决 D-004-2：选择 A。

- element 序号：0-based
- element 内 offset：Unicode code point 计数
- 区间：半开 [start, end)
- identity 输入：规范元素序列范围 + 规范 chunk 文本
- source_locator：章节、页码、spine、路径等格式定位，仅 metadata 审计

选择原因：它直接对应 Python 字符串切片，相邻范围可无歧义拼接，空范围也有统一表示；比闭区间少一层边界换算。

Warning

这里只冻结 range 坐标，不冻结 Unicode normalization form、换行/空白顺序或 hash framing。
